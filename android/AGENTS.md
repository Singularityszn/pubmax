# The native shell (Android)

The Android half of every native promise: the manifest, Gradle, the notification icon and the emulator rig. The shared shell seams are [ios/AGENTS.md](../ios/AGENTS.md).

Repo-wide laws and the index of every other area file are in the root [AGENTS.md](../AGENTS.md).

## Manifest, Gradle and brand assets

- **THE ANDROID HALF OF A PROMISE IS A DIFFERENT FILE, AND IT FAILS IN SILENCE.** Every native capability is stated twice, once where iOS reads it and once where Android does, and for a while only the iOS half was written down. The camera had `NSCameraUsageDescription` and NO `CAMERA` line in `android/app/src/main/AndroidManifest.xml`, so every Android capture was refused with nothing on screen; the links had an `apple-app-site-association` and NO `public/.well-known/assetlinks.json`, so an App Link had nothing to verify against. `__tests__/nativeWrap.test.ts` now holds the pairs to each other. THREE rules ride with it. (1) Declaring `CAMERA` implicitly declares the HARDWARE as required and hides the listing from every device without one, so a uses-feature line marked not required sits beside it. (2) A placeholder is OBVIOUS or it is a lie: `REPLACE_WITH_PLAY_APP_SIGNING_SHA256` is the app-signing fingerprint Google holds, not the upload key, and both link manifests take a SHORT edge window so the weekend's real value reaches the verifier in minutes. (3) The seam is `lib/nativeCamera.ts` and it answers THREE WAYS, because `getPhoto` throws identically for a cancel and a denial and only a permission read BACK as denied earns the refusal line; the plugin's Prompt source is fenced against its camera-only source, since Prompt keeps the photo library on the sheet and is the only reason this seam is allowed on a surface `__tests__/profilePhotoPicker.test.ts` sweeps. The surface table in `__tests__/nativeCameraSurfaces.test.ts` is the closed set and the fence sweeps the tree so no OTHER file may call the seam; profile avatars and covers are deliberately absent, a face being almost always a photo somebody already has. Pins: `__tests__/nativeCameraSurfaces.test.ts`, `__tests__/androidPushWiring.test.ts`.

- **THE SPLASH HAS ONE MASTER, AND THE NOTIFICATION ICON IS THREE FILES.** Two ways a brand asset reaches a phone wrong with nothing saying so. (1) `public/store-assets/splash.svg` is the ONE splash treatment, and its own comment carries the owner lock (#520/#523): a splash is not an icon, it keeps the ink-deep field, and ONE splash serves light and dark. `scripts/gen-native-app-icons.mjs` used to restate that in its own markup and got the LIGHT variant wrong, so both platforms launched on the retired full-bleed coral field for every reader whose phone is in light mode; it now reads the master file for both `assets/splash.png` and `assets/splash-dark.png`, so no second opinion about the splash exists. `__tests__/nativeSplashArt.test.ts` is the fence and it reads the SHIPPED bytes, sweeping the resource trees rather than listing files, because `__tests__/storeAssets.test.ts` and `__tests__/brandIconAssets.test.ts` both stop at `public/` and a launching phone does not. (2) Android draws a notification's small icon as a SILHOUETTE of its alpha channel, and FCM falls back to the full-colour launcher icon when the manifest names none, so every push wore a white blob. That promise is THREE files and any one missing is the same silence: `android/app/src/main/res/drawable/ic_stat_pubmaxx.xml` (a VectorDrawable, so one file serves every density, generated from `lib/brandMark.mjs` and taking the small-optics single-slash cut because the double-struck channel closes at 24dp), the two `default_notification_icon` / `default_notification_color` meta-data lines inside `<application>` in `android/app/src/main/AndroidManifest.xml`, and `android/app/src/main/res/values/colors.xml`. `__tests__/androidNotificationIcon.test.ts` holds all three to each other and the colour to the `coral` token in `lib/brandMark.mjs`. TWO gotchas ride with this. `npx @capacitor/assets@3 generate` writes MORE than the icons and splashes: it rewrites `public/manifest.webmanifest` to point at an icons directory of its own and reformats `android/app/src/main/AndroidManifest.xml`, and both must be reverted after every run. And the iOS LAUNCH SCREEN IS NOT A STORYBOARD: the Capacitor template's launch storyboard drew a plain black frame on the iOS 26 runtime whatever it held (a coral root view with no image launched black too, held on screen with `simctl launch --wait-for-debugger`), so `ios/App/App/Info.plist` carries `UILaunchScreen` naming a colour set and an imageset under `ios/App/App/Assets.xcassets/`, both written by `scripts/gen-native-app-icons.mjs` from the same master, and `__tests__/nativeSplashArt.test.ts` holds the plist, the colour and the three marks. Before and after: `docs/proof/mobile-app-design/ios-sim-iphone17pro/launch/README.md`. A LOCAL RIG LOADS A LOCAL BUILD: `PUBMAX_NATIVE_SERVER_URL` is read by `capacitor.config.ts` at `npx cap sync` time alone (`http://localhost:<port>` for the simulator, `http://10.0.2.2:<port>` for the emulator), `cleartext` follows the scheme, and `__tests__/nativeWrap.test.ts` holds the unset case to production.

- **A GRADLE SKIP SAYS SO, AND NO KEY EVER REACHES THE REPOSITORY.** Capacitor generates the Firebase block as a try/catch reporting at Gradle's info level, which nothing prints by default, so a build with no Firebase config produced a binary that installs, runs, looks complete and answers every push registration with `registrationError`. Both optional lanes now announce themselves at Gradle's lifecycle level and both still BUILD, because push and signing are each one feature rather than the app. The real Firebase config, the keystore properties file and every keystore extension are gitignored, and `android/app/google-services.json.example` is the committed placeholder carrying the weekend steps. The upload key signs every release for the life of the app, so it lives outside the tree; a properties file missing any of the four values refuses BY NAME up front rather than failing deep inside the signing task. R8 stays off on purpose: this binary is a WebView shell and Capacitor resolves plugins reflectively by class name, which is what a shrinker removes. `npx cap sync android` is not optional after a plugin lands, and running it found the Android project had never carried `@capacitor/haptics` at all. THE ANDROID BUILD IS `npm run android:build` AND `npm run android:run` (`scripts/android/`), the Play-account-free half of STORE_READINESS's Local verification section, and `scripts/android/toolchain.mjs` is the ONE place JAVA_HOME and ANDROID_HOME are resolved, refusing BY NAME rather than letting Gradle fail deep inside a task about a path. A screenshot of an emulator is not evidence until it settles, TWICE: SystemUI under `swiftshader_indirect` is slow enough to hit its own ANR, and that dialog takes the focused window over a perfectly healthy app, so `scripts/android/run.mjs` waits for the window manager to name OUR activity; and even then SystemUI has not finished applying the status-bar icon appearance, so a shot ten seconds after focus showed white status-bar icons over the light page and read as a contrast bug that was not there a minute later. A DOUBLE HYPHEN INSIDE AN ANDROID XML COMMENT FAILS THE WHOLE BUILD: XML forbids it, `mergeDebugResources` refuses with "The string \"--\" is not permitted within comments", and writing a CSS custom property by name is the easy way in, so `__tests__/nativeWrap.test.ts` now sweeps every XML resource under `android/app/src/main/res/` for one. Proof from the first green build is `docs/proof/android-shell-build/`. Toolchain and the ordered weekend checklist: `docs/STORE_READINESS.md` section 8.
