# The browser suite

Rules about Playwright: the server it drives, the state it must clear and the idioms that stop a spec lying.

Repo-wide laws and the index of every other area file are in the root [AGENTS.md](../AGENTS.md).

## Driving the browser suite

- **`npm run test:e2e`** (Playwright) needs browsers installed first: `npx playwright install --with-deps chromium`. The e2e config builds and starts the app itself.

- **A hand-started server on the e2e port makes Playwright lie.** `playwright.config.ts` owns the env that lets keyless API routes run (`webServer.env`); without it a production build refuses the routes that write. Playwright reuses an existing listener on its port rather than starting its own, so a stray `npm run start` silently becomes the server under test and every later run inherits that gap. Free the port before a real run; to reuse a build deliberately, start it with the config's env and pass `PW_SKIP_WEBSERVER=1`. `PW_NEXT_DIST_DIR` moves the build directory, and the screenshot commands inherit the isolated wrapper's `NEXT_DIST_DIR` unless an explicit `PW_NEXT_DIST_DIR` wins. A local run also trips `scripts/run-with-restored-next-env.mjs` on a CLEAN tree, because `webServer.env` pins `NEXT_PUBLIC_SW_VERSION=local` on purpose and the pack build then stamps every `public/data` venue pack `"revision":"local"` where the committed copies carry a deploy SHA: allow that stamp for the run with `PUBMAX_TRACKED_OUTPUTS=public/data`, and the wrapper git-restores `public/data` and `uk_base/public/data` from HEAD on exit, because a stamp is not a data change.

- **Two workers share one hashed loopback IP, so the e2e server carries a test-only limiter allowance.** Production stays at 8 POSTs / 60s for `/api/plans/generate` and 60 / 60s across `/api/citymcp/*`. Under two Playwright workers those ceilings answer `429` and `expect(browserErrors).toEqual([])` fails even though the product is right. `webServer.env` sets `PUBMAX_E2E_RATE_LIMIT_MAX`; `lib/e2eRateLimitAllowance.ts` raises the in-process budget only when that env is a positive integer. Never change the production numbers. A hand-started server must carry the same env or the suite will 429 itself. Pin: `__tests__/e2eRateLimitAllowance.test.ts`.

- **A hand-started production server must mint Plan claims.** `PLAN_IDEMPOTENCY_SECRET` (or `RATE_LIMIT_SALT`) needs at least 32 bytes or `/api/plans/generate` answers `PLAN_SIGNING_UNAVAILABLE` 503. Playwright's `webServer.env` already generates a fresh 32-byte secret per run.

- **A PRICE SPEC ATTACHES THE BILL, AND THE FIXTURE HAS TO DECODE.** Since `lib/pintDropReceipt.ts` neither write route accepts a priced write with no bill, so every spec that taps `Log it` attaches one through `e2e/helpers/priceBill.ts` (`attachBill` for the one-tap door, `attachSpillBill` for the Spill composer). ONE helper, so the day the picker moves there is one place to follow it and no spec quietly starts asserting against a composer that would refuse a real person. `e2e/fixtures/bill.jpg` is a baseline JPEG that DECODES as well as validates: the old 131-byte file passed the server's byte sniffing but Chromium refused to paint it, so every shot of an attached bill was a broken-image box.

- **Manual planner testing is stateful and constraint-sensitive.** `/api/plans/generate` returns `422` when the intake carries must-have needs the area's data cannot satisfy: honest scarcity, not a broken environment. The intake and a route draft also persist across sessions in `localStorage`, so a prior run's constraints silently leak into the next. Run manual UI planner tests in a fresh or incognito profile; a low-constraint free-text request through "Describe instead" reliably yields a priced three-stop plan keyless. The e2e specs clear this state with `addInitScript`.

- **A browser test never guesses where a pin is.** The pins paint through the MapLibre canvas, so a spec cannot find one in the DOM, and a grid of taps hunting for one is a race the test loses under parallel workers. `components/map/canvas/paintedPinProbe.ts` publishes `paintedMapTapPoints` on `window`: the viewport point of every pin and cluster the map is drawing right now, each checked to have survived symbol collision, to re-query to the same mark, and to carry no app chrome on top of it. It is unconditional, like the `pubmax:pin-reveal` event beside it, because the browser suite runs a production build. The map opens with the pubs gathered, so a spec that wants a pin opens a cluster first. Pins: `__tests__/paintedPinProbe.test.ts`, `e2e/mobile-map-chrome-fit.spec.ts`.

- **COMMUNITY SHEET FIXTURE VENUE.** Specs that mock Pint Drops and assert community-only sheet state (price doors, trust chips, estimate pills) must use `COMMUNITY_SHEET_FIXTURE_VENUE_ID` from `e2e/helpers/communitySheetFixture.ts`, not `venue-1vle947` (The Sir Christopher Hatton gained harvested drink rows). `__tests__/e2eCommunitySheetFixtureVenue.test.ts` fails if that pub gains `uk_prices` or `drink_price_updates` rows.

- **A LONE CLICK IS NOT A WAIT FOR HYDRATION, and the dropped tap looks exactly like missing markup.** A control painted on the SERVER is tappable in the document before React attaches, so Playwright's own actionability check passes and the tap is dropped with nothing on screen saying so; the spec then waits out its whole budget and reports the surface the tap would have opened as ABSENT. That is how `/pal`'s `Meet your Pub Pal` was read as a heading main had deleted when the heading was there all along (#1464), and how `/plan`'s stop-count answered `aria-pressed=false` for a full assertion budget before. The idiom is to retry the TAP rather than assert harder on what follows it: `await expect(async () => { await control.click(); await expect(result).toBeVisible({ timeout: 1_000 }); }).toPass({ timeout: 20_000 })`, as in `e2e/plan-invite.spec.ts` and `e2e/mobile-button-system.spec.ts`. Before changing an assertion that a server-painted surface never appeared, open the page in a browser and click it: a page that answers there is right, and the spec's tap is the defect.

## Browser evidence for agents

- **Take shots, snapshots and page checks with the Playwright CLI.** `npm run e2e:cli -- <command>` runs `playwright cli` from the repo's own `@playwright/test`, so it uses the same Playwright and the same Chromium as the suite. It writes snapshots and console logs to disk and prints a link, so an agent reads only what it needs. Three evidence tasks cost 2,546 tokens on it and 24,003 on the DevTools route.
- **Command shape:** `PLAYWRIGHT_MCP_OUTPUT_DIR=artifacts/playwright-cli npm run e2e:cli -- -s=<lane> open --browser=chromium`, then `goto`, `route`, `screenshot --filename=artifacts/playwright-cli/<name>.png`, `snapshot --filename=artifacts/playwright-cli/<name>.yml` and `close`. Drive a private-port production build, as the rules above say. The artifacts folder is gitignored.
- **Pass `--browser=chromium` and the full folder in `--filename`.** The default channel is Chrome stable, which is absent here. The CLI resolves `--filename` against the working directory, not the output directory.
- **ONE BROWSER CACHE, ONE PLAYWRIGHT VERSION.** Never run a browser install or download from a lane, and never add the separate `@playwright/cli` package: its newer Chromium pruned the suite's revision from the shared cache and broke a running merge gate. A tool that needs another browser gets its own `PLAYWRIGHT_BROWSERS_PATH` under the artifacts folder.
- **Fallback: `chrome-devtools-axi`,** for Lighthouse, performance traces and heap snapshots, which the CLI does not have. With no Chrome, point `CHROME_DEVTOOLS_AXI_BROWSER_URL` at a Chromium started with `--remote-debugging-port`. In 0.1.34 its `wait` and `run` fail with `fn is not a function`; wait with an `eval` of a Promise.
