# Speed budgets and measured findings

Rules about measured speed: the page and API ceilings, the Core Web Vitals baseline and the findings behind them. A ceiling comes down at the next sweep, and goes up only in the commit that needs it.

Repo-wide laws and the index of every other area file are in the root [AGENTS.md](../AGENTS.md).

## Budgets and measured findings

- **THE PRODUCT HAS A SPEED RATING, AND THE PROFILED CAUSE WAS NOT THE BINDING ONE.** The audit's R2 found no numeric Core Web Vitals figure existed: `perf/route-budgets.json` holds four page COSTS on one emulated phone and says nothing about INP, nothing about a cold visit against a warm one, and nothing about the moment the product becomes USABLE. `lib/webVitalsBaseline.ts` is the rules half (pure, unit-tested with no browser) and `e2e/cwv-baseline.spec.ts` over `e2e/helpers/webVitals.ts` is the measuring half, in its own `chromium-cwv` project because two of its six routes are the map and a GL-less box would record the fallback's speed as the product's. `perf/cwv-baseline.json` is the recorded table and `docs/perf/baseline-2026-09-05.md` the method, the tables and the finding. SIX rules. (1) TARGET AND REGRESSION ARE TWO QUESTIONS: a figure outside R2 (LCP 2500 ms, INP 200 ms, CLS 0.1) is DEBT and must carry its reason in the row, because deleting the measurement is how a slow route stops being slow on paper; a figure worse than the recorded one is a REGRESSION and fails whatever the target says. THE SWEEP IS SPENT BY HAND AND NO JOB RUNS IT: GitHub Actions is off by the captain's decision, so `npm run perf:cwv-sweep` is part of the LOCAL merge bar, run before a merge that could move a figure, and `npm run perf:cwv-record` is how the table is re-taken (both are `--project=chromium-cwv`, about an hour of wall clock for a full sweep). A claim that CI enforces this would be a fence nobody spends. (2) A ROUTE'S INP IS THE WORST INTERACTION THE RUN MADE, off Event Timing entries carrying an `interactionId`; the API's threshold floors at one frame, so a route whose control never appeared would record the floor and read as the FASTEST thing on the table, and the sweep fails on any row that never interacted rather than recording that flattery. (3) ONE CDP SESSION PER PAGE: a session per sample left over a hundred live protocol clients on one page and the same cell that took ninety seconds early in a run took twenty minutes late in it. (4) EVERY ARM IS SERVED THROUGH THE SAME INTERCEPTION: Playwright fulfils an intercepted request from the harness rather than from the browser cache, so an intercepted arm is cold on every load and reads `/map` warm at 6392 ms against 2156 ms un-intercepted on one build; `PUBMAX_CWV_LEGACY_MAP_INIT` picks the older script and the shipped one is served the same way, so the tree stays committed while both arms are measured. (5) THE RECORDED TABLE HOLDS TWO DEVICES ON TWO LISTS, AND SAYS SO: mobile carries the whole route list (`REQUIRED_BASELINE_DEVICES`, the audit's own rig) and desktop carries the three routes Astra's 6 Sep audit named (`REQUIRED_DESKTOP_BASELINE_ROUTES`: `/`, `/map`, `/pal`), with `BASELINE_ROUTES_BY_DEVICE` the one table the sweep reads and `__tests__/webVitalsBaseline.test.ts` fencing BOTH halves plus the desktop rig, so a desktop regression fails the ordinary `npm test` the way a mobile one does. What used to make a desktop row impossible was the RECORDER rather than the rig: it wrote its rows wholesale, so recording desktop discarded every mobile row and the only way to keep both was one run of both full lists, which is the sweep that never finished. `mergeVitalsRecords` / `mergeProductTimings` replace the cells a run measured and leave the rest, a still-breached row keeps its own recorded debt reason and the recorder PRINTS each one it carried, and the method block's own coverage sentence is required prose that has to name which half is which. THREE harness rules ride with it: the FIRST navigation of a fresh context reports no paint timings at all (the probe reads NaN, which the table's own fence refuses), so the spec spends one throwaway load first; an unactionable primary action would wait for ever, because the default action timeout here is no timeout, so the click is bounded and a no-show is reported to the fence that already fails on it; and a WARM row is about a warm CACHE alone, so `clearSampleResidue` drops what the previous sample's own interaction left (a `/pal` onboarding draft made the warm sample measure a different SCREEN) while leaving the cache untouched. (6) THE ENGINE WAS NOT THE GATE, AND NOTHING WARMS BEFORE FIRST PINS. MapLibre 6's worker is a module that statically imports a sibling and nothing in the document names either URL, so a cold `/map` discovered the 478 KB shared module three hops late: requested at 8,385 ms, landed at 10,155 ms, against venue rows already merged at 5,995 ms. Warming the pair from `public/map-first-paint-init.js` moved it to 1,168 ms requested and 4,028 ms landed under an interleaved A/B - and the first tappable pin did not move, 14,565 ms against 14,615 ms. It was REVERTED (`9b6dbcd8c`, reverted by `c52bb928b`) for two reasons: it bought nothing a drinker feels, and `__tests__/mapEarlyWarm.test.ts` already forbids that script fetching anything before `pubmax:first-pins`, a rule that exists because bytes pulled early compete with the work they are meant to accelerate. Do not re-add an eager warm there without an A/B that moves the pin. The eight seconds between "everything is in hand" and "a thumb can hit a pin" belong to the ring shard burst, the uk_base pack (`UK_BASE_MIN_ZOOM` is `PIN_MIN_ZOOM`, so the unpriced national layer streams under the priced pins during a cold London open) and the camera settle; that window is the next lane and it is measured, not guessed. Pins: `__tests__/webVitalsBaseline.test.ts`, `__tests__/maplibreCodeSplit.test.ts`; proof `docs/proof/perf-baseline-fix/`.

- **THE RESAMPLE BAND READS BOTH WAYS, AND A ROUTE THAT CANNOT MEASURE ITSELF IN THREE IS MARKED.** Captain 7 September 2026 ("nothing should ever be red"), over two pull requests that went red on routes they had not touched: #1604 on `/crawls` at LCP 320 against 300, on a branch an interleaved A/B had proved equal to or faster than main on that very route, and #1611, a docs-only change, on `/today` at 364 against 300 and `/onboarding` at 908 against 900. NO CEILING MOVED FOR EITHER, and none may: `scripts/check-budget-ratchet.mjs` is still the pawl and the answer to a figure nobody can repeat is more evidence rather than a bigger number. TWO rules. (1) THE ON-THE-LINE RESAMPLE IS SYMMETRIC ABOUT THE CEILING. `routeLandedOnTheLine` fired on any median at or above `ceiling * (1 - margin)`, a band with NO UPPER EDGE, so it bought extra samples on every figure from a hair under the line out to a route three times over it and on nothing sitting comfortably under. Extra samples can only move a median, so a trigger shaped like that spends evidence exactly and only where it can turn a red into a green: a rescue budget rather than a measurement, and the thermonuclear review's P2-4. `medianSitsOnTheLine` (`lib/performanceBudgets.ts`) is the ONE owner of the arithmetic and it asks `|median - ceiling| <= ceiling * pct`, so a figure just under the line and one just over it buy the same evidence and a route far over its ceiling buys none, that being a regression rather than jitter; `samplesDisagree` still covers the run where a box genuinely stalled. The change makes the gate STRICTER: it removes rescue attempts and adds none. Both predicates moved OUT of `e2e/helpers/perfMeasurement.ts` into the pure module, the same reason `resolveCountBoundary` lives there, so the rule is unit-tested with no browser and the budget sweep and the UX lane report cannot drift apart on when a route is measured again. (2) A NOISE FLOOR, AND THE MARK IS EVIDENCE RATHER THAN A PREFERENCE. A route MEASURED wide carries a `noisy` record naming the metric, the widest spread recorded and why, and spends `noisyWarmupRuns` (2) and `noisyResampleRuns` (4) through `resolveRouteRunPlan` rather than the ordinary pair, so it takes a SECOND discarded navigation before its first counted sample and is judged on the median of seven. Four are marked, all on LCP: `/today` and `/crawls` at 51 per cent, `/discover` and `/drinks` at 37, against a method whose tracked width is 12. `/onboarding` is deliberately NOT marked, because it has no recorded wide spread and 908 against 900 is inside the symmetric band already: a mark is for a route whose samples disagree with EACH OTHER, never for one whose answer sits near its line. The fence refuses a mark whose recorded spread is not wider than `sampleSpreadWarnPct`, and refuses a mark arriving as cover for a `ceilingRaises` on the same metric, so the list can only be argued with and shrunk. An unmarked route costs exactly what it did before. The sweep's own timeout reads `plannedNavigations`, the worst case, because a noise floor outside the timeout is a sweep that times out rather than one that measures. The record on #1589 is corrected in the same PR: its body said "No gate is loosened" while it both raised the `/drinks` LCP ceiling on the captain's word and added the one-sided band. - **A VERDICT IS UNANIMOUS OR IT IS NOT A VERDICT, AND AN UNDECIDED CEILING IS SAID OUT LOUD RATHER THAN FAILED.** Captain 11 September 2026, over two green pull requests the sweep held up. The method already resampled, took the median and WARNED when a route's samples sat further apart than the tracked 12 per cent width, and the warning changed nothing: the median was judged anyway. Job 103319591915 and its re-run on the IDENTICAL commit 3ebac98ac printed eight and six breached routes and shared three, while the same block reported `/tonight` spreading 133 per cent and `/activity` server render 400 per cent. So the samples now decide whether their own median is a verdict at all (`judgeBudgets`, `lib/performanceBudgets.ts`): a clock is UNDECIDED only when ALL THREE hold - (a) its samples STRADDLE the ceiling, at least one meeting it and at least one past it, (b) they disagree past `sampleSpreadWarnPct`, and (c) the excess fits inside the spread meant to explain it, `median - budget <= (max - min) / 2` - and is judged on its median otherwise. Condition (c) compares two figures the run already measured and adds no tracked number: a route running 1200 ms on six of seven samples with one warm 290 ms sample straddles a 300 ms ceiling and is far wider than the tracked width, but its median is 900 ms over against a half-spread of 455, so it stays RED. A metric that meets all three did not measure that ceiling, so it is reported UNMEASURED in its own loud table, in the log and in the failure message, and left off the breach list AND off the ratchet table (`bankableRatchetCandidates`, because a run may not refuse a median and bank its slack in the same log, `findRatchetCandidates` staying blind to the verdict). Both edges are asked: a run entirely under its ceiling decided a pass, and server render running 3 to 19 ms against a 150 ms ceiling would otherwise name nearly every route and bury the straddling rows. ONLY A CLOCK IS EVER UNDECIDED (`CLOCK_METRICS`: `serverRenderMs` and `lcpMs`). `requests` and `jsDecodedKB` count work the page CHOSE to do, so a disagreement there is a route loading different things on different navigations rather than a loaded box, and they are judged on their median always - requests 44, 60 and 62 against a ceiling of 46 stays red. The second run of 3ebac98ac measured `/pubs` JS decoded 929 to 1185 and `/plan` 782 to 1106, so those rows may go red: that is conditional loading on two routes, named for the captain and never rescued by a wider width or a bigger number. The anchor is THE CEILING ITSELF and no band around it: the first cut let the fastest sample sit `resampleWithinCeilingPct` over the line, which excluded samples of 320, 800 and 1200 against a 300 ms ceiling, a median two thirds over budget laundered by a fastest sample 10 ms inside the band. `medianSitsOnTheLine` keeps that band, because how many samples to BUY is a different question from what the samples already bought may say. AND THE REPORT READS BOTH WAYS: every route and metric is asked rather than only the rows already over, so a wide run is named whichever side of its line the median fell on, the same evidence never reading as a clean pass one way and as undecided the other - the one-sided shape refused on 7 September. No verdict moves with it and the gate still fails on the breach list alone. THE KNOWN LIMIT, named rather than hidden: A route whose excess over its ceiling is smaller than its own jitter cannot be decided by a single sweep, so it is reported unmeasured every time rather than failed, and a row that keeps appearing there is the signal to spend real evidence on that route. Every unmeasured row prints its median, its ceiling and its excess over that ceiling beside the range its samples ran over, so the same row returning is visible sweep after sweep. NOTHING IS LOOSENED ANYWHERE ELSE. No ceiling moved, the width did not widen, the sweep still declares `retries: 0`, and a run in which no sample ever met the ceiling fails however wide it was. - **Speed is a number, and the number is enforced.** `docs/PERFORMANCE_BUDGETS.md` owns page and hot-read budgets; `perf/route-budgets.json` holds the page ceilings and `perf/api-budgets.json` the API latency ceilings. The `performance-budget` CI job fails a pull request that goes past a page ceiling, while `api-latency-budget` probes a successful main deployment. Take a ceiling DOWN whenever the measured figure sits comfortably below it; take one UP only in the commit that needs it, with the reason and a measured figure. The doc also names the seams that hold the numbers up, the largest of which is a POLICY: the per-request CSP nonce (`proxy.ts`) rules out static generation, ISR and PPR, so a nonce'd page view is a function invocation with no CDN copy to serve instead.

- **A ROUTE THAT REDIRECTS IS MEASURED AS A REDIRECT, NEVER AS ITS TARGET.** The sweep opens each route with `waitUntil: "load"` and a browser follows a 3xx, so the moment a budgeted route starts redirecting its row measures the page it LANDS ON under a ceiling written for the page it used to be. `/onboarding` did it on 7 September 2026: it began answering 307 to `/` and shipping no document (Astra's live walk, finding B6), and the next sweep read the HOMEPAGE'S 45 requests against the 41 that used to buy an almost empty first-run shell, while `/` itself is budgeted at 46 and was inside it. Measured on a production build, the two return the identical count, because they are now the same page. BOTH READINGS OF THAT NUMBER ARE WRONG: calling it a regression takes a ceiling up to hide a measurement pointing at the wrong page, and calling it a win lets any route shed its own ceiling by learning to redirect. So the row says what it is. `redirectsTo` (`lib/performanceBudgets.ts`) declares it, `measurePerfRedirect` (`e2e/helpers/perfMeasurement.ts`) measures it, and the four figures become the redirect's own cost: one request, no script, no paint. THREE rules. (1) THE TARGET KEEPS ITS OWN ROW, which is what stops the page falling out of the budget entirely, and the fence refuses a `redirectsTo` naming a path nothing budgets. (2) THE LANE ASKS THE WAY A BROWSER ASKS: an APIRequestContext sends `Accept: */*`, and the /onboarding rule keys on a document request precisely so an RSC fetch is untouched, so a bare request is answered with the document and the lane would report "it did not redirect" about a route that does.
