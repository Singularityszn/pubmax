That pair is a MEASUREMENT decision and the workflow carries its own reason: on the 2 vCPU box the sweep could not measure itself, the 6 September run spreading LCP samples 37 to 51 per cent on four routes against the method's own 12 per cent width, so a route flipped between pass and fail on one commit. No ceiling moved for it, and the second job shares the size because two figures taken on two different boxes are not comparable. The image is Ubuntu and each job still installs its own toolchain, so `sudo apt-get`, `npx playwright install --with-deps` and the PostgreSQL 16 cluster all behave as before; the Blacksmith migration stays rejected (#747). `.github/workflows/ci.yml` triggers on pull_request and push to `main`, effective RLS stays in `.github/workflows/rls-session.yml`, and branch protection is captain-side. THE PRODUCTION CHECK COMES FIRST AND EVERY ESCAPE SITS BELOW IT, in `lib/supabase.ts` and in `lib/serverEnv.ts` alike: `NEXT_PHASE` is an ordinary environment variable and a Vercel dashboard variable applies to Build and Runtime alike, so an escape read ABOVE `VERCEL_ENV === "production"` hands a deployed production process the in-memory store and skips the startup secret assertions, which is every write answering 200 and evaporating on the next cold start. `lib/analyticsAttribution.mjs` follows the same ordering for the same reason: the inlined build answer first, then the platform's production word, and only then the browser-suite escape, because `currentAnalyticsAttribution()` reads the live process environment on the server and one project variable used to relabel every real drinker event `internal-test`. A keyless CI build sets no `VERCEL_ENV` at all, so it still falls through to the build-phase line. (2) A CHECKOUT WITH `persist-credentials: false` CANNOT FETCH: the budget ratchet's `git fetch origin main` died with "could not read Username for 'https://github.com'", so the step reads the base branch's own remote-tracking ref out of the `fetch-depth: 0` checkout and verifies the ref first, because `scripts/check-budget-ratchet.mjs` reports an unreadable base as "nothing was compared" and exits 0. - **KNIP IS THE DEAD-CODE GATE, AND EVERY IGNORE NAMES THE CALLER KNIP CANNOT SEE.** `npm run deadcode` runs `scripts/deadcode-gate.mjs`, which runs knip over the whole tree with every issue type at `"error"` bar `duplicates` (a judgement, so a warning) and `unresolved` (off) and then, on a branch, fails only the findings `origin/main` does not already have. `npm run deadcode:all` is the unfiltered run, for the merge train and for anyone cleaning inherited debt. `verify` runs `deadcode` after `typecheck` and `__tests__/qualityGateWiring.test.ts` holds both scripts. FIVE rules. (1) THE IGNORE LIST IS NOT KNIP'S OWN: `lib/agentToolingPaths.mjs` is the ONE list of the directories agent tooling writes into this checkout, read by `eslint.config.mjs` AND by knip, which is why the config is TypeScript rather than JSON. Two hand-written copies is how the GitNexus index fell between them: the `gitnexus` MCP server this repo is wired to writes a CommonJS entry file full of `require()` calls, neither list named its directory, and `npm run lint` - so `npm run verify` and the pre-push hook, the documented merge bar - exited 1 on a CLEAN tree on every machine that tool had run against. Being gitignored is not the test for joining that list; `.agents/` and `skills/` are vendored packs this tree commits and are still upstream sources rather than our code. (2) A FILE KNIP FINDS NO CALLER FOR IS NOT AUTOMATICALLY DEAD, so every other ignore entry carries the caller in a comment: a GitHub workflow, a Python subprocess call, a `command()` string in `scripts/local-refresh/scheduler.mjs`, a fence test reading the source as TEXT, or the refresh command a lane names in `data/freshness_registry.json`. Delete only what NOTHING names. (3) A PLAIN .mjs LEAF BESIDE ITS DECLARATION SIDECAR IS ONE MODULE IN TWO FILES: TypeScript resolution sends an import of the .mjs leaf to the .d.mts beside it, so the sidecar reads as a file nobody imports AND the implementation's exports read as exports nobody uses. Acting on either half deletes a LIVE export while `tsc` stays green off the stale sidecar, so the pair leaves the graph together: the sidecars are ignored and `declaredMjsPairs()` in `knip.config.ts` enters each implementation leaf as an entry. (4) A PLUGIN IS WHAT MAKES A DEPENDENCY READABLE: knip only analyses files reachable from an entry, and `convex/*.ts` are entries only because knip's convex plugin says so, so disabling that plugin reports the live `convex` dependency as unused. Never silence a finding by switching a plugin off; the dependency itself is what the finding is about. `postcss` and `playwright` are the two named `ignoreDependencies`: both ARE in `devDependencies`, and the unlisted finding is knip classifying their one caller each (`__tests__/iosFormZoomFloor.test.ts`, `scripts/gen-store-screenshots.mjs`) as production. A false-positive EXPORT uses a `@public` JSDoc tag naming its caller, never an ignore, and the tag needs the same evidence: `npx tsc --noEmit` goes red when the export keyword is removed. (5) VERIFY FAILS ONLY ON FINDINGS THE BRANCH INTRODUCED. A rebase that inherits an unused export from a PR that landed while this branch was open is not this branch's to delete, so the wrapper subtracts origin/main's knip JSON from HEAD's. On main (no commits ahead of origin/main), or when origin/main cannot be read, every finding fails, which is the same gate as `npx knip`. A committed baseline file is not this gate: an empty-on-main baseline is a no-op after rebase, and a non-empty one would let main carry unused exports. `npx knip` on main stays at zero. Pins: `__tests__/knipDeadcodeGate.test.ts`, `__tests__/qualityGateWiring.test.ts`, `__tests__/handWrittenSourceFence.test.ts`. Detail: [`../docs/rules/scripts-ci-gates-and-audits.md#knip-is-the-dead-code-gate-and-every-ignore-names-the-caller-knip-cannot-see`](../docs/rules/scripts-ci-gates-and-audits.md#knip-is-the-dead-code-gate-and-every-ignore-names-the-caller-knip-cannot-see).

Add an entry there only after upgrades and `overrides` are exhausted; never hide an advisory by raising `--audit-level`, omitting dev dependencies, or skipping the step. Lore is HeritageFact source `web`, name and town gated, citations required, lazy sheet only (`/api/harvest-overlay`, `/api/heritage`), never pin or slim; socials are refused; fold-stats mismatches fail loud. London first-party harvest stays at `npm run harvest:run`. Observations only: every stored fact carries `sourceUrl` and `fetchedAt`. Shards live under gitignored `data-harvest/`; the committed sample is `data-harvest/uk_pubs_seed.sample.jsonl`. Pins: `__tests__/ukPubHarvest.test.ts`, `__tests__/harvestFold.test.ts`, `__tests__/harvestOverlay*.test.ts`. - **A URL WE DECIDE TO FETCH IS SOMEBODY ELSE'S STRING, AND THE ALLOW-LIST IS ASKED ABOUT WHERE WE LANDED.** `isHarvestableOperatorUrl` (`lib/harvest/sourcePolicy.ts`) is the predicate in front of every harvested URL, and nobody types those: a menu URL comes from `harvest_venue_overlays.menu_url`, a pub's OSM `website` tag or a link on a page a crawl already read, and the same predicate gates every URL-taking Context.dev call, where a passing URL also spends credit. FOUR CLASSES, and the last is the one a single-URL check cannot see. A REFUSAL IS ABOUT AN OPERATOR, so it matches on a LABEL BOUNDARY: a refused estate host was refused while its own menu SUBDOMAIN was not, which gave every refused estate a way back in that the table still claimed to hold shut; a look-alike domain that merely CONTAINS a refused name is a different operator and is judged on its own permission. A HOST THAT NAMES OUR OWN NETWORK is refused (localhost, loopback, the private ranges, the mDNS and internal suffixes and the cloud metadata address), because a harvested string reaching a server-side fetch is otherwise a question asked of our own infrastructure in a pub's name. THE FAMILY IS DECIDED FIRST AND AN ADDRESS IS READ AS AN ADDRESS: the first cut tested the hostname as a string, so `[::ffff:169.254.169.254]` (which the WHATWG parser normalises to `[::ffff:a9fe:a9fe]`) was ADMITTED while its v4 spelling was refused, and every pub whose name began `fc` or `fd` was refused as though it were a unique-local address. An IPv6 literal is parsed into its eight hextets, judged by first-hextet RANGE (`fc00::/7`, `fe80::/10`, `fec0::/10`, `::1`, `::`), unwrapped where it EMBEDS a v4 address (mapped, compatible, NAT64 `64:ff9b::/96`, 6to4 `2002::/16`) and refused outright when it cannot be parsed. A DNS name that RESOLVES to a private address is not covered by a pre-resolution check, and `harvestRedirectLanding` re-asking the predicate about the landed page is the control that is. CREDENTIALS in a URL are refused, since they are sent to whatever the URL names. And A REDIRECT CHAIN IS RE-ASKED: both price lanes fetch with `redirect: "follow"`, so the HOST picks the last hop; both computed a `finalUrl` and handed it to NOTHING, so a permitted site that 30x-ed to a refused one was read in full and the row was then stamped with the asked-for URL, naming a page that never stated the price. `harvestRedirectLanding` is the ONE owner of that rule and both `scripts/harvest/uk-prices/run.mjs` and `scripts/harvest/uk-prices/ocr.mjs` read it. Pin: `__tests__/harvestUrlAllowList.test.ts`. Detail: [`../docs/rules/scripts-harvest-and-source-permission.md#a-url-we-decide-to-fetch-is-somebody-else-s-string-and-the-allow-list-is-asked-a`](../docs/rules/scripts-harvest-and-source-permission.md#a-url-we-decide-to-fetch-is-somebody-else-s-string-and-the-allow-list-is-asked-a).

- **The Pint Index PUBLISHES what drinkers confirmed, and the producer is a script.** `lib/pintIndexFromConfirmations.ts` builds the live snapshot from confirmed Pint Drops and `npm run build:pint-index-snapshot` writes `public/data/pint_index_snapshot.json`, which was hand-written and empty because nothing produced it. `lib/pintIndex.ts` admission is UNCHANGED and is the gate: the script validates and dies rather than write a snapshot the site would refuse. FOUR rules. (1) Only a LIVE confirmation may be cited, through the same `confirmationIsLive` the venue sheet reads, so the pubs the Index dates and the pubs a standing calls Confirmed are one set. (2) An observation is dated to the NIGHT THE PRICE WAS SEEN, never the day it was confirmed. (3) Every drop is counted somewhere: `PINT_INDEX_EXCLUSION_REASONS` gives an unresolvable pub, a point outside every borough and an unpriced row their own reason and count. (4) The script REFUSES rather than publish an empty Index over a real one: no durable store, a failed read, or a confirmed-drop read at `MAX_INDEX_CONFIRMED_DROPS` each stop it, and a read that answered with nothing is honestly `empty`. Missions point at the pubs the Index cannot date: the `undated` field on `VenueMissionRows` is a TIE-BREAK inside a reason and never a promotion over a stronger one, it reaches no DTO, and the route reads it in ONE `listConfirmedVenueIds` call for the whole page. - **A DEPLOY UPLOADS THE WORKING TREE, NOT THE COMMIT, so `.vercelignore` is what keeps it small.** `vercel deploy` from a CLI uploads the directory it runs in, gitignored files included, so `.gitignore` protects nothing from an upload: measured 2026-09-06, and the last hole in it was the pair nobody thinks of as build output because git tracks them: the two native shells, `ios` at 276 MB and `android` at 53 MB, which Xcode and Gradle build and the web build never reads. The agent trees, the harvest directories and `.next` itself, which the older `/.next-*` glob missed, were closed the same day in #1564. `__tests__/vercelIgnoreCoverage.test.ts` holds one rule with no third answer: a top-level directory over 5 MB is either a DEPLOY INPUT named in the fence with the reason it is one, or it is listed in `.vercelignore`. The environment is the same shape of promise: `.env.example` is where an operator learns what this app can be configured with, so `__tests__/envExampleCoverage.test.ts` sweeps every environment read under `app/` and `lib/` and fails on a name that is neither documented there with its READER named nor on the platform-owned allowlist, where each row says who sets it. `CRON_SECRET` was missing, and it is the whole of the authentication between the public internet and every mutating scheduled route. - **A DEPLOY NAMES ITS OWN COMMIT, AND A CLI DEPLOY HAS TO CARRY IT.** `GET /api/version` answers `deploymentId`, `gitCommitSha`, `gitCommitShaSource` and `builtAt`, so proving "this preview serves the commit I sent" is one public request rather than a trip through the Vercel deployment API. MEASURED 2026-09-05 (preview `dpl_CgDWoXWduiQJyFBwJPEYSHTsdcB8`): a `vercel deploy` from a CLI uploads no git directory and Vercel stamps `VERCEL_GIT_COMMIT_SHA` on NEITHER the build nor the runtime of one, so the old request-time read answered null on exactly the previews a verifier needed, and a builder-side `git rev-parse` answers nothing either. THREE rules. (1) The question is asked ONCE, at BUILD time: `lib/buildInfo.mjs` is the rule (plain ESM with a `.d.mts` sidecar, the `lib/pintIndexCanonical.mjs` idiom, because `next.config.mjs` cannot import TypeScript), `next.config.mjs` asks it, and the values ride in `env`; Next replaces a STATIC process.env member expression with the literal, so the route reads each name directly and never through a variable key. (2) The commit travels WITH the upload: `npm run deploy:preview` (`scripts/deploy-vercel.mjs`) reads `HEAD` on the machine running the command and passes it as a build variable, forwarding every argument; a Git-integration deploy needs none of it and answers `vercel-git`. (3) A DIRTY TREE STAMPS NOTHING, because a CLI deploy uploads the working tree and a marker naming the wrong commit is worse than one naming none; a status that could not be read is an unread tree rather than a clean one. Runbook `docs/DEPLOYMENT.md` "Which commit is this deploy serving". Pin: `__tests__/deploymentVersionRoute.test.ts`. A PRODUCTION-ENVIRONMENT PREVIEW IS ONE COMMAND, `npm run deploy:preview:prod-env` (`scripts/deploy-preview-prod-env.mjs`), and it BUILDS IN THE CLOUD: it pulls the production environment, drops what it may not carry, and deploys through the command above, so the commit stamp and the project print are not restated. THREE rules ride with it. (1) The revision is one rule, `lib/dataRevision.mjs`, read by `next.config.mjs` and `scripts/lib/slimShards.mjs` alike, because a pulled production environment carries `VERCEL_GIT_COMMIT_SHA=""` and no deployment id and BOTH used to refuse; the working tree names the revision (12 characters, since Next refuses a deployment id over 32) and only a build with no environment and no git refuses. (2) A `[SENSITIVE]` placeholder is DROPPED, never forwarded, because Vercel refuses to hand a secret-typed value back and a forwarded placeholder is INLINED into the client bundle; every platform-owned name is dropped too, `VERCEL_ENV` above all, since `proxy.ts` and `app/robots.ts` key indexability on it. `scripts/lib/previewProdEnv.mjs` is that policy and the command prints both lists.
