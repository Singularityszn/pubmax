# Account removal that removes, and the portable copy beside it

Proof for the contribution battle test's release blocker (D01), the orphaned
Moment bytes (D09) and the missing export (L04), 5 September 2026.

## What was wrong

| Item | The defect |
| --- | --- |
| D01 | `DELETE /api/account` answered 503 `STORE_UNAVAILABLE` for every account. GoTrue's admin delete fires the `0078` tombstone trigger, which deleted from `storage.objects` directly, and Supabase now refuses that at the statement level (`protect_objects_delete`, SQLSTATE 42501) whether or not a row matches. Behind it, `private_social_accounts.supabase_user_id` was `on delete restrict`, refusing every onboarded account a second time. The App Store account-removal door shipped in #1482 removed nothing. |
| D09 | The trigger removed avatars, covers, wall and message photos and nothing under `night-moments/<owner>/`, so a deleted account's Moment bytes stayed in the bucket. |
| L04 | The only self-serve export was Pal memory JSON. Nothing exported Moments, prices, Pint Drops or messages. |

## What changed

- Migration `0145` (+ rollback) takes every storage delete out of the trigger,
  moves the Social binding to `on delete set null`, and suspends and unbinds the
  Social account row rather than deleting it (the Crew tables reference it with
  restrict). The trigger owns rows and columns; it never touches bytes.
- `deleteOwnAccount` removes the account's own objects through the Storage API
  FIRST (avatars, covers, Moment photos, wall photos, message photos; the table is
  `lib/accountOwnedObjects.ts`), while the rows that name them still exist, then
  deletes the auth row. A removal that fails leaves the account in place and
  answers a retryable 503. A second DELETE is 410 Gone carrying `deleted: true`
  (that last claim was unreachable in production until the follow-up below).
- `GET /api/account/export` answers the verified bearer's own Memories, Moments,
  prices, Pint Drops and sent messages as one JSON file, and refuses the whole
  file when a lane could not be read. The You tab carries `Download your data`
  beside `Delete account`.

## The Postgres proof

`__tests__/accountRemovalMigrationEffective.test.ts` starts a PostgreSQL 16
cluster, applies every migration before `0145`, installs a replica of Supabase's
guard trigger (the report's rolled-back probe as a fixture), and shows:

```
BEFORE 0145  delete from auth.users  ->  42501 for an account with photos
                                         42501 for an account that never onboarded
AFTER  0145  delete from auth.users  ->  ok for both; profile tombstoned; wall rows gone;
                                         message keeps its words, loses its photo columns;
                                         Memories and Moments cascade; Social account
                                         suspended:null with its Crew row still there;
                                         storage.objects untouched by SQL (4 rows stay)
ROLLBACK     restores restrict + the old trigger -> 42501 again; forward re-applies -> ok
```

## Follow-up: the 410 was unreachable

Verification scout verify-preview-4 (section 7.3) measured the repeat DELETE
answering 401 `UNAUTHENTICATED` rather than 410: the route resolved its caller
by asking GoTrue for the ACCOUNT, and the first delete had already removed the
auth row. The route now verifies the bearer against the project JWKS and takes
the caller from the token's own claims, so the idempotent answer is reachable.
Measurement and reasoning: `docs/proof/api-envelope-contracts/README.md`.
