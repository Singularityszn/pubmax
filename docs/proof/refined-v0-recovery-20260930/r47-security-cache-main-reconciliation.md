## Exact invariants and conflicts

The device identity rule is `docs/rules/lib-identity-accounts-and-sessions.md:11`: live signed-in account owns device artifacts; viewer-naming/routing stays neutral until identity answers. The account-switch rule at line 15 separates refused credentials from an unavailable provider. Account visibility at line 55 and the actual projection code control private fields. `app/api/profiles/[handle]/route.ts:202-231` returns links only for full projection but includes counts for both; `profileVisibility.ts:169-172` is the link discriminant. Do not add a private-count restriction while retaining the link repair.

Main and Core share the canonical self-link checks at `ProfilePageClient.tsx:434-435`, `:895`, `:1077-1085`. The missing Core render-key guard concerns data already delivered under a prior entitled revision, not a newly invented rule that public links are always secret. Limited private-account links are withheld; public-account links remain public. Pending-body React cleanup and already-painted link retirement are distinct tests. No live cross-account disclosure is proved by these fixture results alone.

The cache delta intentionally distinguishes delivery from retention: `loadSurfaceJson` still calls a live caller's callback after the boundary, but generation mismatch prevents persistence. Private consumers remain responsible for caller cancellation/revision rejection. Clearing `inFlight` permits a new same-key request; the old finalizer/release must not delete that new entry. `subscribeDeviceIdentity` (`deviceAccountIdentity.ts:166-192`) admits relevant identity storage keys and whole-storage clear, not arbitrary cross-tab writes. Keep that existing narrow event contract.

No-store for the feed is warranted by the actual mutable memory store plus clock, not a theory that public responses are private. Expiry-aware TTL alone would not invalidate a cached answer when operations approves a pending memory candidate. Main has no approval-driven shared-cache invalidation. Snapshot broadcast, reviewer eligibility and pending/rejected exclusion stay unchanged.

Auth cancellation is not equivalent to unavailable or banned. Preserve the Main provider's explicit banned status and Core's protection of newer logins. The Core provider's `AccountOnboardingHost` and handle-normalizer import changes are separate coupled module/payload ownership changes; copying this entire older provider without their corresponding owners would be unsafe. Port the cancellation cohort into the current release provider and preserve Main's existing identity/policy behaviour. Do not delay auth bootstrap or substitute a lazy whole-provider boundary.
