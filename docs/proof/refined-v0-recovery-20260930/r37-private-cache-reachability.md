## Exact private-card read path

`app/u/[handle]/ProfilePageClient.tsx:406-440` reads `accountRevision`, the live user and canonical viewer handle. Its `viewerHandle` is empty without a user; `useViewerHandle` (`components/auth/useViewerHandle.ts:33-44`) returns no handle until canonical identity resolves and then uses the provider's account handle, not old device storage.

The profile-card effect (`ProfilePageClient.tsx:776-879`) captures `requestRevision`, creates a caller AbortController, awaits `getAccessToken` only for a nonempty viewer handle, then calls `loadSurfaceJson` with key `/api/profiles/<routeHandle>?viewer=<viewerHandle>` and that token. This particular read uses plain native `fetch` in its `fetchImpl` (`:814`), not `authedActionFetch` or `authedActionJson`. Its pending request therefore has the shared cache request signal and effect cleanup, but no provider-account signal supplied by the authenticated transport.

Server entitlement is independent of the viewer query: `lib/profileVisibilityBoundary.server.ts:75-113` verifies bearer identity, matches the profile's actual `userId`, or checks both follow edges using that verified user's canonical handle. A private stranger gets the allowlisted limited projection; full-card fields withheld from strangers are explicitly listed in `lib/profileVisibility.ts:78-86`. The relevant old response can genuinely contain owner/mate-only card fields such as bio, workplace and cover URLs. This is not an auth identity response; auth/identity cache-path refusal does not exclude this card.

The callback (`ProfilePageClient.tsx:824`) says `return;` when its caller signal is aborted or the revision ref differs. The helper calls the callback and writes unless its result is exactly `false` (`lib/surfaceDataCache.ts:397-399`). Thus **if a non-aborted callback rejects only on revision mismatch, its undefined return is not a cache veto**. That local implication is definite; its timing reachability in this component is a separate question.

## What normal revision cleanup actually protects

`accountRevisionRef` is updated in a passive effect (`ProfilePageClient.tsx:460-464`), not synchronously during the provider's account boundary. The profile read effect depends on that revision and returns `controller.abort()` (`:878-879`). The installed React passive flush runs passive unmount/cleanup before passive mount/setup (`node_modules/react-dom/cjs/react-dom-client.development.js:20130-20134`). In an ordinary revision effect restart, the old controller is therefore aborted before the new ref-setting effect runs. Once the awaiting cache continuation resumes, its own signal check (`lib/surfaceDataCache.ts:386`) suppresses the old callback/write.

Consequently this review does **not** establish an ordinary React-update interval with a new revision ref, an un-aborted old controller and a revision-rejected callback. Do not manufacture that tuple through a test-only ref mutation and label it a product leak. Changing the callback to return false would make its intent explicit, but would not by itself prove or repair every earlier boundary interval.

The unresolved interval is earlier: provider/device boundary occurs while the old caller remains live, before its cleanup/ref effects commit. The old card transport does not observe provider-account abort, and its old ref may still accept the response. Cache clear has no generation fence, so a decoded old response could repopulate its **old viewer key** after the clear. Whether React's actual external-store scheduling or cleanup closes that interval needs a mounted deferred-body regression. Source alone does not establish a user-visible disclosure.

Provider ordering is explicit: `components/auth/AuthProvider.tsx:397` calls `setProviderIdentity` before rebinding/announcing device identity (`:403-405`), resetting canonical identity (`:409-410`) and setting the new session (`:423`). The context's revision comes from the provider external store (`:325-328`); it is not the same thing as this component's later revision ref. `lib/authProviderRevision.ts:93-107` aborts the old account controller synchronously. That protects strict authenticated transports, but does not directly abort this plain card fetch.

## Same-key joins: private cross-owner claim is not established

For a fixed private target T, canonical viewers A and B normally request `T?viewer=A` and `T?viewer=B`. These are different in-flight/cache keys. The ordinary profile ownership contract rejects reuse of an existing handle by another account (`lib/profileStore.ts:1372-1387`; durable claim result checks at `:970-997`). Do not invent two simultaneous canonical owners of one handle to create a same-key test.

An unresolved or signed-out viewer uses `/api/profiles/T` without a bearer. That key may be shared by anonymous and unresolved viewers, but it cannot legitimately carry an owner/mate private projection from this caller: token attachment requires a nonempty canonical viewer handle. A stale old private `T?viewer=A` write would violate boundary retention even when B never reads that key. It is not proof B receives A's private card.

Same account logout/re-entry, token/revision changes, duplicate mounted views for the same viewer and revisiting the same target can reuse a key. They are useful lifetime/dedupe controls, not cross-owner disclosure by themselves. Handle change/reassignment would require a separately established permitted journey; this review did not prove one. Canonical target route and viewer normalization cannot be replaced with arbitrary query text in a browser fixture.

## Immediate owner-only cover caller

`components/profile/ProfileCoverPhotosEditor.tsx:88,107-137` caches `/api/profiles/<handle>/covers`, with no viewer suffix, through `authedActionFetch(...requiresIdentity:true)`. Its own cleanup sets `active=false` and aborts; its inactive callback likewise returns undefined. Unlike the card, this transport composes the provider account signal (`lib/authedFetch.ts:186-198,331-332`). Native pending body consumption therefore aborts when provider identity changes. `authedActionJson` additionally checks signal/revision after decoding (`:390-405`); the cover's native Response path has no equivalent post-decode check in the cache owner.

The actual editor mounts under `isOwnProfile && editing` (`ProfilePageClient.tsx:894,1272`), so switching to B normally removes A's editor, and B's own editor requests B's different handle URL. Server covers GET checks actual caller ownership (`lib/profileCoverPhotoRoute.server.ts:138-157`). The unscoped cover key is a real owner-only cache use, but these gates do not establish a reachable successful cross-owner same-key join. The post-decode/pre-cleanup interval remains a focused local test target, not a demonstrated private image-byte leak; approved image serving has its own public contract.

Other `loadSurfaceJson` calls inside this page are public Pint Drops (`:571`) and public published crawls (`:654`). Owner unlisted crawl data uses a separate authenticated, no-store read and is not surface-cached (`:684-730`). Do not treat those public cache callbacks as private or suppress them wholesale.
