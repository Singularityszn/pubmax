What you've built

A price-aware, story-led UK pub-crawl map — and a working lesson in how modern software is layered, trusted, and shipped.

Next.js 16 · React 19 · TypeScript MapLibre · Supabase · Vercel London + 8 cities

Section 02

The 60-second product

Imagine a living map of British pubs where every pin knows what a pint costs, what the room feels like, and whether the story is sourced history or a mate's note.

Pubmaxxing sits at the intersection of three things most pub apps keep separate:

  • Price — observed pint prices, colour-coded cheap → mid → expensive.
  • Setting — by the water, gardens, walkable route shape, last trains home.
  • Story — heritage era, listed status, editorial picks, and community Pint Drops (photo + price + passed-down note), each wearing a visible provenance badge so legend never pretends to be archive.

London is the flagship. Eight more cities ship browseable maps (Manchester, Liverpool, Oxford, Durham, Glasgow, Bristol, Cambridge, Bath). You plan a crawl, share it via URL, drop a pint, build a passport, and — when the keys are set — talk to The Landlord, an AI that answers only from retrieved facts and honestly refuses to invent.

For you as product owner: the “product” is not just screens. It is a trust contract (provenance), a map experience (MapLibre), and a thin server that never lets the browser write to the database directly.

Section 04

Architecture layers

Think of the system as four floors in one building. Requests enter at the top; secrets live at the bottom. Pure domain logic sits in the middle — testable without a browser.

Three kinds of code (mental model)

  • Pure domain (lib/) — functions that take data in and return data out. No network, no React. Easy to test. Example: buildCrawlRoute, validatePintDrop.
  • Client map / UI (components/) — runs in the browser. Owns interaction, MapLibre WebGL, optimistic updates. Must treat every user input as untrusted until the server says otherwise.
  • Server routes (app/api/) — the only place that may use the Supabase service role, hash IPs, mint signed photo URLs, and assert environment secrets.

Section 05

The four ideas that run through everything

If you remember only four product-engineering principles from Pubmaxxing, make them these.

IDEA 01

Provenance never flattens

Sourced editorial, community contributions, anecdotes, and demo seeds stay visibly distinct. The badge is the trust signal. Never merge a historian’s note and a mate’s yarn into one undifferentiated string.

IDEA 02

Seams light up with keys

No Supabase → in-memory stores and honest production-503s. No OpenRouter → The Landlord reads facts back instead of narrating. The app never pretends to have durability or intelligence it doesn’t.

IDEA 03

Content-hashed stable IDs

A venue ID is an FNV hash of name + address + coords — not “row 47 in the JSON.” Seeds and curated crawls survive dataset reordering because identity follows content.

IDEA 04

One write path

One Pint Drop API, one URL sync for crawls, one map mount lifecycle. Single seams keep invariants enforceable — and keep agents from inventing parallel half-broken paths.

Section 06

Walkthrough: Drop a pint

The community’s core write. A drinker adds a photo, a price, and a note. The UI feels instant; the server stays honest.

  1. Optimistic UI The composer shows the drop immediately so the night feels alive. This is a preview — not truth yet.
  2. Server validation (trust boundary) validatePintDrop strips control chars, caps lengths, checks price £0–£20, requires price or note. The client’s claimed provenance is ignored.
  3. Rate limit Durably keyed on handle + salted IP hash so one noisy phone can’t flood the map.
  4. Store + photo Photo uploads to a private bucket under a deterministic key; then the DB row lands. Failure after upload triggers orphan cleanup.
  5. Signed URL + DTO The API returns a safe DTO (data transfer object) with a time-limited photo URL — never a raw private path forever.

Section 07

Walkthrough: Plan a crawl

Planning is mostly pure client-side domain logic over a slim pin pack — fast, shareable, and deterministic.

  1. Slim pins load The map fetches a compact venue index for the city (not the full editorial dump). London + OSM city packs keep the first paint light.
  2. Filter Style, price band, amenities, heritage, near-water — filterVenues applies predicates. Unknown price ≠ expensive.
  3. Build the route buildCrawlRoute is a greedy nearest-good-neighbour walk: seed strong pubs, grow by score minus distance cost, pick the best whole route. Simple on purpose — not a travelling-salesman solver.
  4. URL sync encodeCrawl / decodeCrawl write the crawl into the query string (single write path, debounced). Share the link; a friend opens the same night.
Product insight: the crawl lives in the URL, so “share” is free. That only works because IDs are content-hashed and decode is forgiving (clamps numbers, drops unknowns, never throws).

Section 08

Walkthrough: Sign in & identity

Identity turns a browser session into a passport someone can follow and share.

  1. OAuth with PKCE Sign-in starts with a provider (e.g. Google) using Proof Key for Code Exchange — a one-time secret so intercepted redirects can’t steal the session.
  2. Callback → JWT /auth/callback exchanges the code for a JSON Web Token (JWT). That token proves “this browser is this user” on later API calls.
  3. Link a handle The profile claims a public @handle. Ownership checks on the server ensure you can only edit your own passport.
  4. Share passport + OG buildPassport assembles the public surface; Open Graph card routes render social previews when you paste /u/[handle] into Slack or iMessage.

Messages, follows, activity, and admin moderation all hang off the same identity spine: JWT ownership on the server, public handle on the passport.

Section 09

Trust & security model

Security here is not a bolt-on checklist. It is the product’s honesty contract made technical.

  • Provenance is assigned server-side from evidence, never client assertion.
  • JWT ownership gates edits to profiles, lists, and private actions.
  • Private Storage + signed URLs so takedowns and expiry mean something.
  • assertServerEnv FATAL — missing production secrets crash loud rather than run half-configured.
  • Rate limits (durable RPCs) + admin token for moderation.
  • Heritage honesty — The Landlord rejects answers that cite facts it was never given.

Section 10

Software engineering fundamentals

Ten ideas every product owner benefits from recognising — each with a Pubmaxxing example you already ship.

Client vs server

Client code runs on the user’s device. Server code runs in your infrastructure. Only the server may hold secrets and make authoritative decisions.

Here: MapLibre paints pins in the browser; app/api/pint-drops decides whether a drop is stored.

Pure functions

Same input → same output, no hidden side effects. Easy to test, easy for agents to change safely.

Here: buildCrawlRoute, filterVenues, scoreVenue live in lib/ with Vitest suites pinning behaviour.

Trust boundary

The line where untrusted input becomes trusted state. Re-validate everything that crosses it.

Here: validatePintDrop is the boundary. HTML is stripped; provenance is re-derived.

DTO vs raw DB

A DTO is a shaped, public-safe object. Raw DB rows may contain private fields you must never leak.

Here: store adapters toDTO withhold URLs for hidden drops and mint signed photo links.

Optimistic UI

Show the result before the network confirms — then reconcile or roll back.

Here: dropping a pint updates the feed instantly; a failed API call reconciles against the server DTO.

Env secrets & NEXT_PUBLIC_

Anything prefixed NEXT_PUBLIC_ is baked into the browser bundle. Real secrets must omit that prefix.

Here: service-role Supabase key and ADMIN_TOKEN are server-only; public anon keys (if used) are the only browser-safe ones.

RLS as second line

Row Level Security is Postgres policies that limit who can read/write rows — even if application code slips.

Here: deny-all writes for clients; public SELECT only for visible content. Server uses service role after validation.

Content-hashed IDs

IDs derived from content stay stable when arrays shuffle. Index-based IDs break seeds and bookmarks.

Here: stableVenueIdFromKey (FNV-1a) powers curated crawls like Prospect of Whitby.

Idempotency (reports)

Repeating the same action shouldn’t corrupt state. Concurrent reports must not lose counts.

Here: report_pint_drop RPC atomically increments and hides at threshold 2 — one report never hides alone.

Fail loud vs fail soft

Fail loud when continuing would lie (missing prod DB). Fail soft when a non-critical feature can degrade (Landlord without an LLM key).

Here: production-503 without Supabase; structured fact readback without OpenRouter; rate limiter fails open but logs loudly.

Section 11

Why we are NOT adopting Effect-TS

You may hear that Effect is the “correct” way to do typed async in TypeScript. For Pubmaxxing right now, adopting it would slow the whole system down.

DO NOT ADOPT

Effect is a power tool for complex, typed asynchronous orchestration — retries, dependency injection, structured concurrency. It shines in large teams with Effect experts and gnarly workflow graphs.

This app already has the seams that matter: ValidationResult-style validation, a PintDropStore interface with swappable adapters, and pure domain functions. Those are the 80% of Effect’s value without the dialect.

AI coding agents get slower on unfamiliar Effect idioms. Every PR would pay a translation tax. Adopt only much later if hired Effect experts hit real orchestration pain that the current interfaces cannot express.

Verdict: do not adopt Effect-TS now. Ship product on the seams you have.

Section 12

How agents ship faster HERE

Speed does not come from new frameworks. It comes from sharp docs, small seams, and tests that pin the honesty contract.

  • Docs as ground truth — teach.md, PRDs, ADRs, and this page tell agents what “done” means before they invent architecture.
  • Pure lib/ seams — change filterVenues without touching MapLibre lifecycle.
  • Single write paths — one Pint Drop API, one crawl URL encoder; agents extend instead of duplicating.
  • CI that bites — npm run ci = validate-data + lint + typecheck + coverage + audit + build. Vercel runs this as the deploy gate.
  • Honest fallbacks — agents can add features that degrade without keys instead of hard-requiring infrastructure on day one.

Section 13

What you own vs what agents own

Clear ownership keeps velocity without surrendering product judgment.

You own

  • Product thesis & trust contract (provenance honesty)
  • Which cities / surfaces ship next
  • Tone of heritage vs community voice
  • Go / no-go on frameworks (e.g. Effect)
  • Secrets, admin token, production env
  • Accepting risk trade-offs (fail-open rate limit, etc.)

Agents own (with review)

  • Implementing features inside existing seams
  • Tests that pin invariants
  • Refactors that keep pure domain pure
  • Docs updates when behaviour changes
  • CI green — lint, types, coverage, build
  • Not inventing parallel write paths or flattening provenance
Rule of thumb: if a change alters what users should trust or believe, that is your call. If it alters how code reaches an already-decided behaviour, that is agent territory — under the gates above.

Section 14

Glossary

App Router
Next.js file-based routing under app/. Folders become URLs; page.tsx is the screen.
JWT
JSON Web Token — a signed ticket proving who is signed in, checked on the server.
OAuth / PKCE
Sign-in via a provider. PKCE adds a one-time secret so stolen redirects can’t finish login.
Provenance
Where a claim came from: sourced, contributor, anecdote, or demo — shown as a badge, never flattened.
RLS
Row Level Security — database policies that restrict which rows a role may read or write.
DTO
Data Transfer Object — the shaped payload sent to clients, scrubbed of private fields.
Optimistic UI
Updating the screen before the server confirms, then reconciling with the real response.
Signed URL
A temporary, cryptographically authorised link to a private storage object.
FNV / content hash
A fingerprint of content used as an ID so identity survives reordering.
Idempotent
Doing the same operation twice leaves the system in a correct state (e.g. atomic report counts).
Service role
A privileged Supabase key that bypasses RLS — server-only, never shipped to the browser.
MapLibre
Open-source map engine (WebGL) that draws pubs, clusters, and brass route lines.
Edge runtime
Lightweight Vercel execution used for things like OG image generation.
CI
Continuous Integration — automated checks before code can ship (npm run ci).
