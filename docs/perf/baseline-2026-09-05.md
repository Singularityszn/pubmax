# Core Web Vitals baseline, 5 September 2026

The audit's R2 found the product had no numeric speed rating. `perf/route-budgets.json`
holds four page COSTS on one emulated phone; nothing held LCP, INP or CLS, nothing held a
cold visit apart from a warm one, and nothing at all held the moments the product becomes
USABLE rather than merely painted. This is that measurement, the profile that followed it,
and the honest result of acting on the profile.

`perf/cwv-baseline.json` is the machine-readable table the fence defends.
`lib/webVitalsBaseline.ts` owns the rules and is unit-tested with no browser
(`__tests__/webVitalsBaseline.test.ts`). `e2e/cwv-baseline.spec.ts` is the sweep.

## Method

| | |
| --- | --- |
| Build | local production build (`NEXT_DIST_DIR=.next-prod`), keyless, served by `next start` |
| Browser | Playwright Chromium with SwiftShader, so the map gets a real WebGL2 context and the sweep measures the map rather than its fallback |
| Mobile rig | 390x844, 4x CPU throttle, Slow 4G (150 ms RTT, 1474.56 kbit/s down, 675 kbit/s up: Chrome's own preset, the same figures Lighthouse applies and `scripts/perf-baseline.mjs` pins) |
| Desktop rig | 1440x900, no CPU throttle, Fast 4G |
| Runs per cell | **3**, median. Not the 5 originally planned: the harness could not complete a five-run matrix on this box in the time available, and three measured cells are worth more than five planned ones |
| Cold | HTTP cache, cookies and storage all cleared before the measured load |
| Warm | an unmeasured priming load first, then the measured one |
| INP | the worst interaction the run produced, off Event Timing entries carrying an `interactionId`. The API's `durationThreshold` floors at 16 ms, so a route whose interaction finished inside one frame reports no entry and is recorded at 16 rather than at 0 |
| Targets (R2) | LCP <= 2500 ms, INP <= 200 ms, CLS <= 0.1 |

**What this rig is not.** The box was shared with other work throughout, at load averages
between 9 and 70 on 18 cores. Absolute figures carry that noise, and the before and after
tables below were taken at different moments and are NOT a controlled comparison. Where a
causal claim is made it comes from the interleaved A/B, which alternates both arms inside
one process so shared load moves them together.

### The re-measurement that had to be thrown away

A bounded after-fix re-measurement of the `/map` cells (both devices, cold, 3 runs, a fresh
browser per sample) was taken at 16:58 with the box at load average 70. It is reported here
and deliberately NOT used as a ceiling:

| Device | first pin (median) | LCP (median) | CLS (median) |
| --- | ---: | ---: | ---: |
| mobile | 28,773 ms (2 of 3 samples never painted a pin inside 75 s) | 25,172 ms | 0.027 |
| desktop | 14,485 ms | 13,044 ms | 0.091 |

A fence seeded from a 25 second LCP is a fence that permits catastrophic regressions, so
these figures stay in the record and out of the ceiling.

## The profile: what a cold /map is actually waiting for

Full trace in `docs/proof/perf-baseline-fix/trace-map-cold-before.txt`. Cold, 390x844, 4x
CPU, Slow 4G, empty cache:

| moment | ms |
| --- | ---: |
| venue rows merged (`pubmax:first-pins`) | 5,995 |
| MapLibre chunk finishes (1024 KB decoded / 273 KB transferred) | 6,800 |
| worker's shared module **first requested** | 8,385 |
| shared module lands (478 KB / 133 KB) | 10,155 |
| first painted, tappable pin | **16,484** |

MapLibre 6 is ESM-only and its worker is a module that statically imports a sibling.
Nothing in the document names either URL, so the browser cannot discover them until the
1 MB chunk has downloaded, parsed and run. The 1,585 ms between the chunk landing and the
shared module being requested is dead wire time. And the venue data had been ready since
5,995 ms: the reader was not waiting for the data.

## The attempted fix, and the measurement that rejected it

The attempt was to cache-warm the worker pair from `public/map-first-paint-init.js` at low
priority the moment it runs, collapsing that three-hop discovery. Measured by interleaved A/B on `/map`: four
pairs, both arms in one process, order alternated each pair so shared load moves them
together. Raw output in `docs/proof/perf-baseline-fix/ab-map-first-pin.txt`.

| | before | after |
| --- | ---: | ---: |
| shared module requested (median) | 8,308 ms | **1,168 ms** |
| shared module landed (median) | 10,358 ms | **4,028 ms** |
| first painted, tappable pin (median) | 14,565 ms | 14,615 ms |
| first pin, per pair | 24915 / 13894 / 15206 / 13924 | 15697 / 15604 / 13229 / 13626 |

**The mechanism is fixed and the bottleneck did not move.** The engine's shared module
landed 6.3 seconds earlier, ahead of the venue rows rather than four seconds behind them,
and the first tappable pin was unchanged: 50 ms apart on a metric whose own spread across
four runs is 11 seconds.

**So the change was dropped, and this branch does not carry it.** Two reasons, and either
would have been enough:

1. It bought nothing a drinker can feel. The profiled cause was real and is not the binding
   constraint.
2. It broke a contract this repo already had. `__tests__/mapEarlyWarm.test.ts` asserts that
   `public/map-first-paint-init.js` fetches NOTHING before `pubmax:first-pins`, and the warm
   fired on load. That rule exists for the reason the A/B then demonstrated: bytes pulled
   early compete with the very work they are meant to accelerate. Keeping the warm would
   have meant rewriting a tested law to make room for a change with no measured benefit.

What survives is the measurement: the three-hop discovery is real, it is worth about six
seconds of engine readiness, and it is NOT what a cold `/map` is waiting for.

## Where the real gate is, for the next lane

With the shared module landing at 4.0 s and the venue rows merged at ~6.0 s, the first
tappable pin still arrives at ~14.6 s. Roughly eight seconds sit between "everything needed
is in hand" and "a thumb can hit a pin". The before-fix trace shows what occupies that
window, and none of it is the engine:

- the ring shard burst, about twenty `venues_slim.cell.*` requests starting at 11.3 s;
- `/data/uk_base/manifest.json` at 13.7 s and a uk_base pack landing at 16.1 s, 385 ms
  before the first pin. `UK_BASE_MIN_ZOOM` is `PIN_MIN_ZOOM`, so the unpriced national base
  layer streams at the same zoom as the priced pins it sits under, competing for the last
  of a throttled wire during a cold London open;
- `pubmax:camera-intent:area` at 13.4 s and `pubmax:pin-entrance-settled` at 14.1 s.

That is the next lane, and it now starts from a measurement rather than a guess.
