# Deploys and uploads

Moved from [`scripts/AGENTS.md`](../../scripts/AGENTS.md). Authoritative policy detail lives here; the area index stays short.

<a id="a-vercelignore-replaces-the-gitignore-fallback-so-a-heavy-directory-absent-from-"></a>

- **A `.vercelignore` REPLACES the `.gitignore` fallback, so a heavy directory absent from it is uploaded.** Thermonuclear review P1-4: the file existed, so Vercel stopped falling back to `.gitignore`, and `/.next-*` reads as a glob covering the build directory while matching only the suffixed local copies, leaving `.next` itself, the largest of them, in the upload. `npm run deploy:preview` uploads the working tree, so every agent-tooling checkout and harvest shard went with it. The file now names each one and carries the rule in its own header. `__tests__/coreUiAudit.test.ts` holds the list and still refuses `/data/` and `/public/`, which ARE build inputs.

<a id="a-deploy-uploads-the-working-tree-not-the-commit-so-vercelignore-is-what-keeps-i"></a>

- **A DEPLOY UPLOADS THE WORKING TREE, NOT THE COMMIT, so `.vercelignore` is what keeps it small.** `vercel deploy` from a CLI uploads the directory it runs in, gitignored files included, so `.gitignore` protects nothing from an upload: measured 2026-09-06, and the last hole in it was the pair nobody thinks of as build output because git tracks them: the two native shells, `ios` at 276 MB and `android` at 53 MB, which Xcode and Gradle build and the web build never reads. The agent trees, the harvest directories and `.next` itself, which the older `/.next-*` glob missed, were closed the same day in #1564. `__tests__/vercelIgnoreCoverage.test.ts` holds one rule with no third answer: a top-level directory over 5 MB is either a DEPLOY INPUT named in the fence with the reason it is one, or it is listed in `.vercelignore`. A SECRET-BEARING PATH IS LISTED WHATEVER ITS SIZE: ops review OPS-7 found the local env files, the Clerk directory (which `.gitignore` itself says can include secrets), the root MCP config and the Tavily, context, Codex and data scratch directories all gitignored and all absent from `.vercelignore`, and the dirty-tree check in `scripts/deploy-vercel.mjs` and the release reads `git status --porcelain`, which never shows a gitignored file, so each would have uploaded unseen; Vercel's own default skips only the local env files. They are listed with the database dumps, `!.env.example` keeps the valueless template, and the same fence holds the list. The environment is the same shape of promise: `.env.example` is where an operator learns what this app can be configured with, so `__tests__/envExampleCoverage.test.ts` sweeps every environment read under `app/` and `lib/` and fails on a name that is neither documented there with its READER named nor on the platform-owned allowlist, where each row says who sets it. `CRON_SECRET` was missing, and it is the whole of the authentication between the public internet and every mutating scheduled route.

<a id="a-deploy-names-its-own-commit-and-a-cli-deploy-has-to-carry-it"></a>

- **A DEPLOY NAMES ITS OWN COMMIT, AND A CLI DEPLOY HAS TO CARRY IT.** The [build identity reference](../DEPLOYMENT.md#which-commit-is-this-deploy-serving) owns the response fields and authentication requirements. MEASURED 2026-09-05 (preview `dpl_CgDWoXWduiQJyFBwJPEYSHTsdcB8`): a `vercel deploy` from a CLI uploads no git directory and Vercel stamps `VERCEL_GIT_COMMIT_SHA` on NEITHER the build nor the runtime of one, so the old request-time read answered null on exactly the previews a verifier needed, and a builder-side `git rev-parse` answers nothing either. THREE rules. (1) The question is asked ONCE, at BUILD time: `lib/buildInfo.mjs` is the rule (plain ESM with a `.d.mts` sidecar, the `lib/pintIndexCanonical.mjs` idiom, because `next.config.mjs` cannot import TypeScript), `next.config.mjs` asks it, and the values ride in `env`; Next replaces a STATIC process.env member expression with the literal, so the route reads each name directly and never through a variable key. (2) The commit travels WITH the upload: `npm run deploy:preview` (`scripts/deploy-vercel.mjs`) reads `HEAD` on the machine running the command and passes it as a build variable, forwarding every argument; a Git-integration deploy needs none of it and answers `vercel-git`. (3) A DIRTY TREE STAMPS NOTHING, because a CLI deploy uploads the working tree and a marker naming the wrong commit is worse than one naming none; a status that could not be read is an unread tree rather than a clean one. Runbook `docs/DEPLOYMENT.md` "Which commit is this deploy serving". Pin: `__tests__/deploymentVersionRoute.test.ts`. A PRODUCTION-ENVIRONMENT PREVIEW IS ONE COMMAND, `npm run deploy:preview:prod-env` (`scripts/deploy-preview-prod-env.mjs`), and it BUILDS IN THE CLOUD: it pulls the production environment, drops what it may not carry, and deploys through the command above, so the commit stamp and the project print are not restated. THREE rules ride with it. (1) The revision is one rule, `lib/dataRevision.mjs`, read by `next.config.mjs` and `scripts/lib/slimShards.mjs` alike, because a pulled production environment carries `VERCEL_GIT_COMMIT_SHA=""` and no deployment id and BOTH used to refuse; the working tree names the revision (12 characters, since Next refuses a deployment id over 32) and only a build with no environment and no git refuses. (2) A `[SENSITIVE]` placeholder is DROPPED, never forwarded, because Vercel refuses to hand a secret-typed value back and a forwarded placeholder is INLINED into the client bundle; every platform-owned name is dropped too, `VERCEL_ENV` above all, since `proxy.ts` and `app/robots.ts` key indexability on it. `scripts/lib/previewProdEnv.mjs` is that policy and the command prints both lists. (3) NEVER `--prod`, NEVER `--target` AND NEVER `--prebuilt`, all refused: `--target production` (in any spelling, `--target=…` and `-t` included) is a production deploy that skips the release checks, and a macOS prebuilt upload ships darwin-only sharp binaries and a whole-project trace, which is why `lib/venueIndexOsm.ts` marks its `process.cwd()` calls (measured: `/recap/[storyId]` traced 10,044 files before the marker and 295 after). Runbook `docs/DEPLOYMENT.md` "A preview built with production values, in one command"; pin `__tests__/previewProdEnvDeploy.test.ts`.

<a id="a-production-release-is-one-command-and-it-ends-at-the-smoke-verdict"></a>

- **A PRODUCTION RELEASE IS ONE COMMAND, AND IT ENDS AT THE SMOKE VERDICT.** Use the [release procedure](../DEPLOYMENT.md#one-release-command) for staging, promotion, smoke-run selection, and failure handling. Never promote a Preview build. Promotion does not rebuild the artifact, so Preview environment values would remain in production. Every release effect arrives through `deps`, so tests can check the order and refusals without network access. Pin: `__tests__/releaseProduction.test.ts`.

<a id="the-release-refuses-when-production-lacks-a-migration-and-the-check-compares-names"></a>

- **THE RELEASE REFUSES WHEN PRODUCTION LACKS A MIGRATION, AND THE CHECK COMPARES NAMES.** The audit of 6 October 2026 found 192 repo files against 196 ledger rows with 88 matching versions: the captain applies migrations by hand, under other timestamps and sometimes bare names, so a version comparison reports noise. `npm run check:migration-ledger` (`scripts/check-migration-ledger.mjs`, rule in `scripts/lib/migrationLedger.mjs`) reads the live ledger and fails when a repo file's full name and bare slug are both absent. `npm run release:prod` runs it before any upload. THREE rules. (1) READ-ONLY: one fixed `select` through the Management API's read-only query endpoint. (2) A NAME THE LEDGER ALONE HOLDS IS REPORTED, NEVER A FAILURE: writing those bodies into the repo is separate work. (3) NO TOKEN MEANS NO RELEASE: `SUPABASE_ACCESS_TOKEN` unset refuses, and the token never appears in an error. Pin: `__tests__/migrationLedger.test.ts`.

<a id="production-is-asked-every-five-minutes-and-only-a-route-that-fails-twice-is-an-outage"></a>

- **PRODUCTION IS ASKED EVERY FIVE MINUTES, AND ONLY A ROUTE THAT FAILS TWICE IS AN OUTAGE.** Launch plan R3 (1 November 2026) found nothing that told anybody when production was down. `.github/workflows/uptime.yml` runs `scripts/ci/uptime-check.mjs` on GitHub's shortest schedule, every five minutes, at minutes 2 to 57 so the busy top of the hour cannot drop it. It reads `/api/health` (200, `ok` true and the database `ok`) and `/api/version` (200, `ok` true) on `PRODUCTION_SITE_ORIGIN` from `lib/siteUrlConfig.mjs`, the constant the app reads, so the workflow names no host of its own. FIVE rules. (1) TWO STRIKES: a failed route is asked once more 30 seconds later, longer than the 15 seconds the health route holds its answer, and only a route that fails both times fails the run. A route that answers the second time is a flap, printed as a warning on a green run, because an alert nobody can act on teaches people to mute alerts. A status other than 200, a body that is not JSON or does not say ok, a redirect (`/api` is never canonicalised) and no answer within 15 seconds are all failures. (2) THE ALERT IS THE ONE WE ALREADY HAVE: a failed scheduled run reaches `.github/workflows/alert-on-failure.yml`, which names "Production uptime" among its watched workflows and posts the run link to the `PUBMAX_ALERT_WEBHOOK_URL` repository secret. The monitor reads no secret and sends no credential. A hand-dispatched run never alerts, and during an outage the post repeats with each failed run, about every five minutes. (3) THE LOG PRINTS NO BODY, AND NO VALUE THE NETWORK CHOSE unless it matches a narrow pattern (a deployment id, an `x-vercel-mitigated` word, an error code), because a GitHub log line that starts with `::` is a workflow command. (4) TWO FILES, NOT THE TREE: the job checks out the script and the constant alone, sparse, because the full checkout is over a gigabyte and the job runs 288 times a day. The fence holds the sparse list to the script's import closure and refuses a package import, because no `npm ci` runs. (5) IT IS A FLOOR, NOT A PAGER: GitHub can start a scheduled run late or drop it, runs a schedule only from the default branch, and turns a schedule off after 60 days with no repository activity, so an external monitor on `/api/health` stays the optional second opinion in the [deployment runbook](../DEPLOYMENT.md#uptime-monitor). Vercel's Attack Challenge Mode answers the monitor with a challenge, which reads as down and names the firewall. Runbook: the [launch-week section](../SOFT_LAUNCH_RUNBOOK.md#8-launch-week-16-and-17-november-2026) of `docs/SOFT_LAUNCH_RUNBOOK.md`, section 8.6. Pins: `__tests__/uptimeMonitor.test.ts`, `__tests__/alertSink.test.ts`.
