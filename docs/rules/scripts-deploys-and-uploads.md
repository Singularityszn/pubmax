# Deploys and uploads

Moved from [`scripts/AGENTS.md`](../../scripts/AGENTS.md). Authoritative policy detail lives here; the area index stays short.

<a id="a-vercelignore-replaces-the-gitignore-fallback-so-a-heavy-directory-absent-from-"></a>

- **A `.vercelignore` REPLACES the `.gitignore` fallback, so a heavy directory absent from it is uploaded.** Thermonuclear review P1-4: the file existed, so Vercel stopped falling back to `.gitignore`, and `/.next-*` reads as a glob covering the build directory while matching only the suffixed local copies, leaving `.next` itself, the largest of them, in the upload. `npm run deploy:preview` uploads the working tree, so every agent-tooling checkout and harvest shard went with it. The file now names each one and carries the rule in its own header. `__tests__/coreUiAudit.test.ts` holds the list and still refuses `/data/` and `/public/`, which ARE build inputs.

<a id="a-deploy-uploads-the-working-tree-not-the-commit-so-vercelignore-is-what-keeps-i"></a>

- **A DEPLOY UPLOADS THE WORKING TREE, NOT THE COMMIT, so `.vercelignore` is what keeps it small.** `vercel deploy` from a CLI uploads the directory it runs in, gitignored files included, so `.gitignore` protects nothing from an upload: measured 2026-09-06, and the last hole in it was the pair nobody thinks of as build output because git tracks them: the two native shells, `ios` at 276 MB and `android` at 53 MB, which Xcode and Gradle build and the web build never reads. The agent trees, the harvest directories and `.next` itself, which the older `/.next-*` glob missed, were closed the same day in #1564. `__tests__/vercelIgnoreCoverage.test.ts` holds one rule with no third answer: a top-level directory over 5 MB is either a DEPLOY INPUT named in the fence with the reason it is one, or it is listed in `.vercelignore`. The environment is the same shape of promise: `.env.example` is where an operator learns what this app can be configured with, so `__tests__/envExampleCoverage.test.ts` sweeps every environment read under `app/` and `lib/` and fails on a name that is neither documented there with its READER named nor on the platform-owned allowlist, where each row says who sets it. `CRON_SECRET` was missing, and it is the whole of the authentication between the public internet and every mutating scheduled route.

<a id="a-deploy-names-its-own-commit-and-a-cli-deploy-has-to-carry-it"></a>

- **A DEPLOY NAMES ITS OWN COMMIT, AND A CLI DEPLOY HAS TO CARRY IT.** `GET /api/version` answers `deploymentId`, `gitCommitSha`, `gitCommitShaSource` and `builtAt`, so proving "this preview serves the commit I sent" is one authenticated request using an existing target-configured `CRON_SECRET`. An unauthenticated request returns `ok` and `deploymentId` so a stale tab can reload, and never the commit, its source or the build time. MEASURED 2026-09-05 (preview `dpl_CgDWoXWduiQJyFBwJPEYSHTsdcB8`): a `vercel deploy` from a CLI uploads no git directory and Vercel stamps `VERCEL_GIT_COMMIT_SHA` on NEITHER the build nor the runtime of one, so the old request-time read answered null on exactly the previews a verifier needed, and a builder-side `git rev-parse` answers nothing either. THREE rules. (1) The question is asked ONCE, at BUILD time: `lib/buildInfo.mjs` is the rule (plain ESM with a `.d.mts` sidecar, the `lib/pintIndexCanonical.mjs` idiom, because `next.config.mjs` cannot import TypeScript), `next.config.mjs` asks it, and the values ride in `env`; Next replaces a STATIC process.env member expression with the literal, so the route reads each name directly and never through a variable key. (2) The commit travels WITH the upload: `npm run deploy:preview` (`scripts/deploy-vercel.mjs`) reads `HEAD` on the machine running the command and passes it as a build variable, forwarding every argument; a Git-integration deploy needs none of it and answers `vercel-git`. (3) A DIRTY TREE STAMPS NOTHING, because a CLI deploy uploads the working tree and a marker naming the wrong commit is worse than one naming none; a status that could not be read is an unread tree rather than a clean one. Runbook `docs/DEPLOYMENT.md` "Which commit is this deploy serving". Pin: `__tests__/deploymentVersionRoute.test.ts`. A PRODUCTION-ENVIRONMENT PREVIEW IS ONE COMMAND, `npm run deploy:preview:prod-env` (`scripts/deploy-preview-prod-env.mjs`), and it BUILDS IN THE CLOUD: it pulls the production environment, drops what it may not carry, and deploys through the command above, so the commit stamp and the project print are not restated. THREE rules ride with it. (1) The revision is one rule, `lib/dataRevision.mjs`, read by `next.config.mjs` and `scripts/lib/slimShards.mjs` alike, because a pulled production environment carries `VERCEL_GIT_COMMIT_SHA=""` and no deployment id and BOTH used to refuse; the working tree names the revision (12 characters, since Next refuses a deployment id over 32) and only a build with no environment and no git refuses. (2) A `[SENSITIVE]` placeholder is DROPPED, never forwarded, because Vercel refuses to hand a secret-typed value back and a forwarded placeholder is INLINED into the client bundle; every platform-owned name is dropped too, `VERCEL_ENV` above all, since `proxy.ts` and `app/robots.ts` key indexability on it. `scripts/lib/previewProdEnv.mjs` is that policy and the command prints both lists. (3) NEVER `--prod` AND NEVER `--prebuilt`, both refused: a macOS prebuilt upload ships darwin-only sharp binaries and a whole-project trace, which is why `lib/venueIndexOsm.ts` marks its `process.cwd()` calls (measured: `/recap/[storyId]` traced 10,044 files before the marker and 295 after). Runbook `docs/DEPLOYMENT.md` "A preview built with production values, in one command"; pin `__tests__/previewProdEnvDeploy.test.ts`.

<a id="a-production-release-is-one-command-and-it-ends-at-the-smoke-verdict"></a>

- **A PRODUCTION RELEASE IS ONE COMMAND, AND IT ENDS AT THE SMOKE VERDICT.** A CLI deploy reports nothing to GitHub, so `deployment_status` never started `.github/workflows/prod-smoke.yml` for it: the audit of 6 October 2026 found the workflow had zero runs while the live deploy came from a CLI. `npm run release:prod` (`scripts/release-production.mjs`, steps in `scripts/lib/releaseProduction.mjs`) deploys through `scripts/deploy-vercel.mjs`, promotes, waits for `/api/version` on the live origin to name the new deployment, dispatches `.github/workflows/prod-smoke.yml` on `main` and waits for the run. THREE rules. (1) THE RELEASED COMMIT IS THE TIP OF `main`, because a workflow dispatch names a branch and the suite checks out that branch's head; a dirty tree or any other `HEAD` is refused before an upload. (2) THE VERDICT IS THIS RELEASE'S: a run counts only when it was created after the dispatch and its `headSha` is the released commit. (3) EVERY EFFECT ARRIVES THROUGH `deps`, so the order and every refusal are tested with no network. Runbook `docs/DEPLOYMENT.md` "One release command". Pin: `__tests__/releaseProduction.test.ts`.

<a id="the-release-refuses-when-production-lacks-a-migration-and-the-check-compares-names"></a>

- **THE RELEASE REFUSES WHEN PRODUCTION LACKS A MIGRATION, AND THE CHECK COMPARES NAMES.** The audit of 6 October 2026 found 192 repo files against 196 ledger rows with 88 matching versions: the captain applies migrations by hand, under other timestamps and sometimes bare names, so a version comparison reports noise. `npm run check:migration-ledger` (`scripts/check-migration-ledger.mjs`, rule in `scripts/lib/migrationLedger.mjs`) reads the live ledger and fails when a repo file's full name and bare slug are both absent. `npm run release:prod` runs it before any upload. THREE rules. (1) READ-ONLY: one fixed `select` through the Management API's read-only query endpoint. (2) A NAME THE LEDGER ALONE HOLDS IS REPORTED, NEVER A FAILURE: writing those bodies into the repo is separate work. (3) NO TOKEN MEANS NO RELEASE: `SUPABASE_ACCESS_TOKEN` unset refuses, and the token never appears in an error. Pin: `__tests__/migrationLedger.test.ts`.

<a id="the-only-database-backup-is-a-private-copy-on-the-captain-s-mac"></a>

- **THE ONLY DATABASE BACKUP IS A PRIVATE COPY ON THE CAPTAIN'S MAC, AND IT IS NEVER A WORKFLOW ARTIFACT.** Production is on the Supabase free plan with no backups and no point-in-time recovery (audit of 6 October 2026), and the repository is public. `npm run backup:offplatform` (`scripts/backup-offplatform.mjs`, rules in `scripts/lib/offPlatformBackup.mjs`) writes a `pg_dump` of the `public`, `auth`, `storage` and `supabase_migrations` schemas plus a sync of the `pint-drops` bucket to a directory on the Mac. `npm run backup:install-launchd` (`scripts/install-backup-launchd.mjs`) installs it as a weekly launchd agent that reads its secrets from `~/.config/pubmax/backup.env` (mode 0600, refused otherwise), and the captain or firstmate runs that installer; no agent runs it (captain, 6 October 2026). FOUR rules. (1) THE DIRECTORY IS OUTSIDE EVERY GIT CHECKOUT, or the script refuses, judged from the nearest directory that exists so a path not made yet cannot slip inside one; dumps are mode 0600 and git ignores the dump extension. (2) A DUMP COUNTS ONLY WHEN `pg_restore --list` FINDS TABLE DATA: it is written under a partial name and renamed after that check. (3) EACH RUN PRUNES AT 7 WEEKS, BY AGE, SO NO COPY REACHES 8, except the newest dump and the bucket files it names, so a restore is always possible. `pruneBackupCopy` deletes every dump older than `PRUNE_AFTER_WEEKS` however many runs there were, and every partial dump older than the newest dump, which a killed run leaves behind. The week of slack covers a weekly run that fires late on a Mac that woke late. Each run stamps a bucket file's mtime while its object is still in the bucket, a file last seen before the oldest kept dump is deleted, and a folder left empty goes too, because folder names are ids. Pruning runs only with the backup, so the weekly schedule keeps the window, and the privacy page says data you delete, a deleted account included, can stay in backups for up to 8 weeks. (4) THE PASSWORD TRAVELS AS `PGPASSWORD`, never in an argument list. A restore drill has not been run: `docs/DR_RUNBOOK.md` holds the steps, the drill log, the rebuild from zero, account lockout, the key rotation order and domain loss. Pins: `__tests__/offPlatformBackup.test.ts`, `__tests__/backupLaunchdInstaller.test.ts`.
