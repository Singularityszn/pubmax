<a id="the-product-has-a-speed-rating-and-the-profiled-cause-was-not-the-binding-one"></a>

- **THE PRODUCT HAS A SPEED RATING, AND THE PROFILED CAUSE WAS NOT THE BINDING ONE.** The audit's R2 found no numeric Core Web Vitals figure existed: `perf/route-budgets.json` holds four page COSTS on one emulated phone and says nothing about INP, nothing about a cold visit against a warm one, and nothing about the moment the product becomes USABLE. `lib/webVitalsBaseline.ts` is the rules half (pure, unit-tested with no browser) and `e2e/cwv-baseline.spec.ts` over `e2e/helpers/webVitals.ts` is the measuring half, in its own `chromium-cwv` project because two of its six routes are the map and a GL-less box would record the fallback's speed as the product's. `perf/cwv-baseline.json` is the recorded table and `docs/perf/baseline-2026-09-05.md` the method, the tables and the finding. SIX rules. (1) TARGET AND REGRESSION ARE TWO QUESTIONS: a figure outside R2 (LCP 2500 ms, INP 200 ms, CLS 0.1) is DEBT and must carry its reason in the row, because deleting the measurement is how a slow route stops being slow on paper; a figure worse than the recorded one is a REGRESSION and fails whatever the target says. THE SWEEP IS SPENT BY HAND AND NO JOB RUNS IT: GitHub Actions is off by the captain's decision, so `npm run perf:cwv-sweep` is part of the LOCAL merge bar, run before a merge that could move a figure, and `npm run perf:cwv-record` is how the table is re-taken (both are `--project=chromium-cwv`, about an hour of wall clock for a full sweep). A claim that CI enforces this would be a fence nobody spends. (2) A ROUTE'S INP IS THE WORST INTERACTION THE RUN MADE, off Event Timing entries carrying an `interactionId`; the API's threshold floors at one frame, so a route whose control never appeared would record the floor and read as the FASTEST thing on the table, and the sweep fails on any row that never interacted rather than recording that flattery. (3) ONE CDP SESSION PER PAGE: a session per sample left over a hundred live protocol clients on one page and the same cell that took ninety seconds early in a run took twenty minutes late in it. (4) EVERY ARM IS SERVED THROUGH THE SAME INTERCEPTION: Playwright fulfils an intercepted request from the harness rather than from the browser cache, so an intercepted arm is cold on every load and reads `/map` warm at 6392 ms against 2156 ms un-intercepted on one build; `PUBMAX_CWV_LEGACY_MAP_INIT` picks the older script and the shipped one is served the same way, so the tree stays committed while both arms are measured. (5) THE RECORDED TABLE HOLDS TWO DEVICES ON TWO LISTS, AND SAYS SO: mobile carries the whole route list (`REQUIRED_BASELINE_DEVICES`, the audit's own rig) and desktop carries the three routes Astra's 6 Sep audit named (`REQUIRED_DESKTOP_BASELINE_ROUTES`: `/`, `/map`, `/pal`), with `BASELINE_ROUTES_BY_DEVICE` the one table the sweep reads and `__tests__/webVitalsBaseline.test.ts` fencing BOTH halves plus the desktop rig, so a desktop regression fails the ordinary `npm test` the way a mobile one does. What used to make a desktop row impossible was the RECORDER rather than the rig: it wrote its rows wholesale, so recording desktop discarded every mobile row and the only way to keep both was one run of both full lists, which is the sweep that never finished. `mergeVitalsRecords` / `mergeProductTimings` replace the cells a run measured and leave the rest, a still-breached row keeps its own recorded debt reason and the recorder PRINTS each one it carried, and the method block's own coverage sentence is required prose that has to name which half is which. THREE harness rules ride with it: the FIRST navigation of a fresh context reports no paint timings at all (the probe reads NaN, which the table's own fence refuses), so the spec spends one throwaway load first; an unactionable primary action would wait for ever, because the default action timeout here is no timeout, so the click is bounded and a no-show is reported to the fence that already fails on it; and a WARM row is about a warm CACHE alone, so `clearSampleResidue` drops what the previous sample's own interaction left (a `/pal` onboarding draft made the warm sample measure a different SCREEN) while leaving the cache untouched. (6) THE ENGINE WAS NOT THE GATE, AND NOTHING WARMS BEFORE FIRST PINS. MapLibre 6's worker is a module that statically imports a sibling and nothing in the document names either URL, so a cold `/map` discovered the 478 KB shared module three hops late: requested at 8,385 ms, landed at 10,155 ms, against venue rows already merged at 5,995 ms. Warming the pair from `public/map-first-paint-init.js` moved it to 1,168 ms requested and 4,028 ms landed under an interleaved A/B - and the first tappable pin did not move, 14,565 ms against 14,615 ms. It was REVERTED (`9b6dbcd8c`, reverted by `c52bb928b`) for two reasons: it bought nothing a drinker feels, and `__tests__/mapEarlyWarm.test.ts` already forbids that script fetching anything before `pubmax:first-pins`, a rule that exists because bytes pulled early compete with the work they are meant to accelerate. Do not re-add an eager warm there without an A/B that moves the pin. The eight seconds between "everything is in hand" and "a thumb can hit a pin" belong to the ring shard burst, the uk_base pack (`UK_BASE_MIN_ZOOM` is `PIN_MIN_ZOOM`, so the unpriced national layer streams under the priced pins during a cold London open) and the camera settle; that window is the next lane and it is measured, not guessed. Pins: `__tests__/webVitalsBaseline.test.ts`, `__tests__/maplibreCodeSplit.test.ts`; proof `docs/proof/perf-baseline-fix/`.

<a id="until-the-pins-have-painted-the-wire-belongs-to-the-pins"></a>

- **UNTIL THE PINS HAVE PAINTED, THE WIRE BELONGS TO THE PINS.** The lane the entry above named, now measured and closed. Profiled cold on the audit's own rig (390x844, 4x CPU, Slow 4G): the scene was built at 7,722 ms and the first tappable pin did not arrive until 13,512 ms, because in between the map opened 57 `venues_slim` shard-cell ring requests, a 190 KB ambient POI read and (on a returning visit) the uk_base manifest and its packs, while MapLibre's own worker module, 133 KB and about 720 ms of wire, QUEUED behind them for 3,775 ms. Only once that module lands can the worker parse the pubs source, ask the style for a glyph range and place a symbol, so every one of those optional bytes sits in front of the first pin. `lib/mapFirstPinStreams.ts` is the rule and the CLOSED set of held lanes (`slim-shard-rings`, `uk-base-layer`, `ambient-poi-overlay`, `london-restaurant-pack`); `components/map/useMapSecondaryStreamHold.ts` owns its clock; `PubMap` derives the answer ONCE and hands `PubMapCanvas` a prop, because two copies of a rule about one wire are two answers. FOUR rules. (1) NOTHING IS DROPPED and nothing new is fetched: every byte still arrives, the moment the map has something a thumb can hit. (2) HELD IS NOT SUSPENDED: a suspended uk_base layer is EMPTIED and answers `suspended`, because a view took the map away from it, while a held one keeps its `loading` answer and has simply not been asked yet. (3) A HOLD IS NEVER A CAGE: a painted pin, the shell deciding there is no canvas at all (the F08 lane, where nothing will ever announce one) or the hold's own ceiling each end it, and that ceiling is DERIVED from `MAP_CANVAS_READINESS_CEILING_MS` rather than typed, so a hold cannot outlive the shell's own patience for a canvas. (4) A RING ASKED FOR WHILE HELD IS REMEMBERED rather than dropped, and runs against the camera the reader has when the hold ends. Six diagnostic marks name the engine's own share of that window (`pubmax:map-constructed`, `map-style-load`, `map-icons-ready`, `map-scene-built`, `pubs-source-loaded`, `pins-visible`), so the next reader profiles rather than guesses. Interleaved A/B, five pairs, both arms in one process: the first tappable pin fell from 15,589 ms to 10,679 ms (median) on a first visit and from 15,908 ms to 12,644 ms for a returning one, every pair favouring the hold. The local rig serves HTTP/1.1, so it overstates the size of the win and the doc says so. Method and both tables: `docs/PERFORMANCE_BUDGETS.md` "The first pin on a cold, throttled /map"; proof `docs/proof/map-first-pin/`. Pin: `__tests__/mapFirstPinStreams.test.ts`.

<a id="the-resample-band-reads-both-ways-and-a-route-that-cannot-measure-itself-in-thre"></a>

- **THE RESAMPLE BAND READS BOTH WAYS, AND A ROUTE THAT CANNOT MEASURE ITSELF IN THREE IS MARKED.** Captain 7 September 2026 ("nothing should ever be red"), over two pull requests that went red on routes they had not touched: #1604 on `/crawls` at LCP 320 against 300, on a branch an interleaved A/B had proved equal to or faster than main on that very route, and #1611, a docs-only change, on `/today` at 364 against 300 and `/onboarding` at 908 against 900. NO CEILING MOVED FOR EITHER, and none may: `scripts/check-budget-ratchet.mjs` is still the pawl and the answer to a figure nobody can repeat is more evidence rather than a bigger number. TWO rules. (1) THE ON-THE-LINE RESAMPLE IS SYMMETRIC ABOUT THE CEILING. `routeLandedOnTheLine` fired on any median at or above `ceiling * (1 - margin)`, a band with NO UPPER EDGE, so it bought extra samples on every figure from a hair under the line out to a route three times over it and on nothing sitting comfortably under. Extra samples can only move a median, so a trigger shaped like that spends evidence exactly and only where it can turn a red into a green: a rescue budget rather than a measurement, and the thermonuclear review's P2-4. `medianSitsOnTheLine` (`lib/performanceBudgets.ts`) is the ONE owner of the arithmetic and it asks `|median - ceiling| <= ceiling * pct`, so a figure just under the line and one just over it buy the same evidence and a route far over its ceiling buys none, that being a regression rather than jitter; `samplesDisagree` still covers the run where a box genuinely stalled. The change makes the gate STRICTER: it removes rescue attempts and adds none. Both predicates moved OUT of `e2e/helpers/perfMeasurement.ts` into the pure module, the same reason `resolveCountBoundary` lives there, so the rule is unit-tested with no browser and the budget sweep and the UX lane report cannot drift apart on when a route is measured again. (2) A NOISE FLOOR, AND THE MARK IS EVIDENCE RATHER THAN A PREFERENCE. A route MEASURED wide carries a `noisy` record naming the metric, the widest spread recorded and why, and spends `noisyWarmupRuns` (2) and `noisyResampleRuns` (4) through `resolveRouteRunPlan` rather than the ordinary pair, so it takes a SECOND discarded navigation before its first counted sample and is judged on the median of seven. Four are marked, all on LCP: `/today` and `/crawls` at 51 per cent, `/discover` and `/drinks` at 37, against a method whose tracked width is 12. `/onboarding` is deliberately NOT marked, because it has no recorded wide spread and 908 against 900 is inside the symmetric band already: a mark is for a route whose samples disagree with EACH OTHER, never for one whose answer sits near its line. The fence refuses a mark whose recorded spread is not wider than `sampleSpreadWarnPct`, and refuses a mark arriving as cover for a `ceilingRaises` on the same metric, so the list can only be argued with and shrunk. An unmarked route costs exactly what it did before. The sweep's own timeout reads `plannedNavigations`, the worst case, because a noise floor outside the timeout is a sweep that times out rather than one that measures. The record on #1589 is corrected in the same PR: its body said "No gate is loosened" while it both raised the `/drinks` LCP ceiling on the captain's word and added the one-sided band. Pins: `__tests__/performanceBudgets.test.ts`, `__tests__/performanceBudgetGate.test.ts`; method and the measured before/after table are `docs/PERFORMANCE_BUDGETS.md` "The noise floor, and which routes carry it".

<a id="a-verdict-is-unanimous-or-it-is-not-a-verdict-and-an-undecided-ceiling-is-said-o"></a>

- **A VERDICT IS UNANIMOUS OR IT IS NOT A VERDICT, AND AN UNDECIDED CEILING IS SAID OUT LOUD RATHER THAN FAILED.** Captain 11 September 2026, over two green pull requests the sweep held up. The method already resampled, took the median and WARNED when a route's samples sat further apart than the tracked 12 per cent width, and the warning changed nothing: the median was judged anyway. Job 103319591915 and its re-run on the IDENTICAL commit 3ebac98ac printed eight and six breached routes and shared three, while the same block reported `/tonight` spreading 133 per cent and `/activity` server render 400 per cent. So the samples now decide whether their own median is a verdict at all (`judgeBudgets`, `lib/performanceBudgets.ts`): a clock is UNDECIDED only when ALL THREE hold - (a) its samples STRADDLE the ceiling, at least one meeting it and at least one past it, (b) they disagree past `sampleSpreadWarnPct`, and (c) the excess fits inside the spread meant to explain it, `median - budget <= (max - min) / 2` - and is judged on its median otherwise. Condition (c) compares two figures the run already measured and adds no tracked number: a route running 1200 ms on six of seven samples with one warm 290 ms sample straddles a 300 ms ceiling and is far wider than the tracked width, but its median is 900 ms over against a half-spread of 455, so it stays RED. A metric that meets all three did not measure that ceiling, so it is reported UNMEASURED in its own loud table, in the log and in the failure message, and left off the breach list AND off the ratchet table (`bankableRatchetCandidates`, because a run may not refuse a median and bank its slack in the same log, `findRatchetCandidates` staying blind to the verdict). Both edges are asked: a run entirely under its ceiling decided a pass, and server render running 3 to 19 ms against a 150 ms ceiling would otherwise name nearly every route and bury the straddling rows. ONLY A CLOCK IS EVER UNDECIDED (`CLOCK_METRICS`: `serverRenderMs` and `lcpMs`). `requests` and `jsDecodedKB` count work the page CHOSE to do, so a disagreement there is a route loading different things on different navigations rather than a loaded box, and they are judged on their median always - requests 44, 60 and 62 against a ceiling of 46 stays red. The second run of 3ebac98ac measured `/pubs` JS decoded 929 to 1185 and `/plan` 782 to 1106, so those rows may go red: that is conditional loading on two routes, named for the captain and never rescued by a wider width or a bigger number. The anchor is THE CEILING ITSELF and no band around it: the first cut let the fastest sample sit `resampleWithinCeilingPct` over the line, which excluded samples of 320, 800 and 1200 against a 300 ms ceiling, a median two thirds over budget laundered by a fastest sample 10 ms inside the band. `medianSitsOnTheLine` keeps that band, because how many samples to BUY is a different question from what the samples already bought may say. AND THE REPORT READS BOTH WAYS: every route and metric is asked rather than only the rows already over, so a wide run is named whichever side of its line the median fell on, the same evidence never reading as a clean pass one way and as undecided the other - the one-sided shape refused on 7 September. No verdict moves with it and the gate still fails on the breach list alone. THE KNOWN LIMIT, named rather than hidden: A route whose excess over its ceiling is smaller than its own jitter cannot be decided by a single sweep, so it is reported unmeasured every time rather than failed, and a row that keeps appearing there is the signal to spend real evidence on that route. Every unmeasured row prints its median, its ceiling and its excess over that ceiling beside the range its samples ran over, so the same row returning is visible sweep after sweep. NOTHING IS LOOSENED ANYWHERE ELSE. No ceiling moved, the width did not widen, the sweep still declares `retries: 0`, and a run in which no sample ever met the ceiling fails however wide it was. Eleven of the fourteen breached rows those two runs printed stop being breaches; the three that remain are `/today` at 352 ms fastest against 300, `/crawls` in the second run running 308 to 408 against 300 on a route already marked noisy that had spent its extra samples, and `/historic` agreeing with itself at 408 against 400, which is a route on its line rather than a runner on a bad morning. Excluding beats resampling until the spread closes: extra samples can only move a median, so a loop that stops when the spread closes stops when the noise stopped SHOWING, which is the objection the captain upheld against the one-sided rescue band, and the sweep's timeout is derived from `plannedNavigations`, a worst case no until-condition has. Pins: `__tests__/performanceBudgets.test.ts` (the two runs replayed row by row); method `docs/PERFORMANCE_BUDGETS.md` "A ceiling a wide run cannot decide".

<a id="a-red-route-and-a-slow-box-look-the-same-in-a-breach-table-so-the-job-measures-t"></a>

- **A RED ROUTE AND A SLOW BOX LOOK THE SAME IN A BREACH TABLE, SO THE JOB MEASURES THE MERGE BASE BESIDE IT.** Captain 11 September 2026, choosing between merging three pull requests past a red check, making the job advisory, recalibrating every ceiling and BUILDING THE INSTRUMENT: four Performance budget runs produced four DIFFERENT failing route sets on branches whose diffs cannot touch a route, two runs on the identical head `fe2b740dd` disagreed, and against the last green job (103065258121, PR #1638) 43 of 44 budgeted routes measured about a third slower on the shared pool, `/choose-city` 208 to 332 and `/messages` 572 to 888. The instrument is `lib/performanceAbEvidence.ts` (the arithmetic, pure and unit-tested with no browser), `e2e/performance-budget-ab.spec.ts` (the measuring) and `scripts/perf-ab.mjs` (the merge-base worktree, the second build and both servers), wired as an `if: failure()` step in the same `Performance budget` job. WHAT IT PROVES: that this box measured the branch no slower than the code the branch started from, which is the evidence the standing law asks for before a red check is re-run on the captain's word. WHAT IT CANNOT PROVE: that a route is fast, that a ceiling is right, or that the branch is innocent of anything the A/B did not measure - both arms can sit far over a ceiling and the verdict still reads NOT SLOWER THAN BASE, because no ceiling is in that comparison at all. FIVE rules. (1) IT MOVES NO CEILING AND GATES NOTHING: the breach list `judgeBudgets` decides still fails the build, an undecided ceiling is never handed to the A/B because it is not a breach, the script exits 0 whatever it finds, and the job stays blocking, because advisory was the option the captain rejected. (2) THE NAVIGATIONS INTERLEAVE, A, B, A, B, AND THE PAIR ALTERNATES WHICH ARM LEADS: all of A then all of B on a drifting box lands the whole drift on one side and reports it wearing the branch's name, and a drift that only ever moves one way would otherwise settle on whichever arm is always second. (3) A GREEN SWEEP PAYS NOTHING: the sweep hands its breach list on only when it has one (`PERF_AB_BREACH_FILE`, owned by `lib/performanceAbEvidence.ts`, written under the gitignored test-results directory), the script stops before it creates a worktree or starts a build without one, and the job's wall is 55 minutes rather than 35 only because a RED run now does more. A RED run spends a NAVIGATION BUDGET rather than a route count, because a marked route costs more than twice a quiet one: `abNavigationBudget` prices eight ordinary routes at what the A/B ITSELF spends on one rather than at the sweep's own worst case, routes are filled WORST FIRST by how far each figure sits past its own ceiling, and a route is measured only when its WHOLE plan fits, because half a route's samples is a median nobody can defend. The budget, the per-route cost and the test's own timeout live in the pure module beside `compareArms`, and the timeout allows one navigation what the HARNESS allows it (`ROUTE_READY_TIMEOUT_MS` plus the method's drain ceiling) rather than a figure typed beside it. That allowance bounds ONE navigation and cannot bound the run, so the measuring also carries a WALL-CLOCK DEADLINE of WHAT IS LEFT of the job's own `timeout-minutes` less the upload's share (`abMeasuringDeadlineMs`, `abUploadReserveMs`, mirrored as `PERF_AB_JOB_WALL_MS`): a run bounded only by the wall is a run GitHub cancels, and a cancelled job never reaches the upload. The job records its start (`PUBMAX_PERF_AB_JOB_STARTED_MS`) and hands its wall to the script (`PUBMAX_PERF_AB_JOB_WALL_MS`), which passes both on ONLY when it was given them, so a hand run races no wall and its report says it measured unbounded rather than naming a deadline nobody set, so a sweep or a merge-base build that overran shrinks the measuring rather than leaving it a share of a wall already spent, and a wall already gone yields no measuring at all. EVERY phase the script spawns is bounded by that same remainder - the merge-base `npm ci`, its build, the wait for both arms and the measuring itself - because an unbounded subprocess upstream of a deadline makes the deadline decorative, and the browser launch, both arms' preparation and their teardown all sit outside the spec's own deadline-checked loop; each runs in its OWN PROCESS GROUP and the group is what is signalled, because `npm` and `npx` are wrappers and a signal to the wrapper leaves `next build`, the Playwright runner or its browser holding the processor and the step's output open; and the measuring keeps a TEARDOWN MARGIN (`abTeardownMarginMs`, the WORST WHOLE SAMPLE that may be in flight - the load, the readiness gate, a second gate on a route declaring one and the drain, which `abSampleAllowanceMs` owns - plus a fifth of the upload's share for both arms closing and the last write; the Playwright timeout reads the same sample figure) so the spec's own stop always arrives before the script's kill and that write survives; a margin shorter than the allowance a sample is bounded by would let the kill land mid-load, which is the loss it exists to stop. The servers are started in their own process groups too, and the deadline is asked before EVERY warm-up load as well as before every sample, because a route admitted on no observed pace can otherwise spend four warm-up navigations past its own stop; a route the deadline stops while warming reads NOT COMPARED and is named under STOPPED PART WAY THROUGH, exactly like one stopped mid-measurement. A bounded phase that overruns names itself and how long it had, leaves the run without an A/B and still exits 0. `__tests__/performanceAbEvidence.test.ts` runs the script against a wall with a hair under and a little over the module's reserve left, so the share the script mirrors cannot drift from `abUploadReserveMs` in either direction. `__tests__/ciReleaseGateWorkflow.test.ts` holds the job's `timeout-minutes`, the figure handed to the script and the module's mirror together. The deadline is asked THREE ways, because one asked only at the top of a route bounds when the last route starts rather than when the run ends: a route is ADMITTED only when its own whole plan fits what is left, priced at this run's own measured pace (`abRouteFitsDeadline`), and the deadline is asked again between the arms and between the samples, where a route stopped mid-measurement keeps fewer samples than it planned and so reads NOT COMPARED under the rule already in force. Each of the A/B's own navigations is bound at that same allowance on its own pages (`page.setDefaultNavigationTimeout`, the sweep's method untouched), because a load bounded only by the test's total is one hung `page.goto` free to eat the wall and the upload with it; bounded, it fails its sample and the arm reads NOT COMPARED. A deadline that expires stops the measuring, keeps every row already taken and says in the report that the DEADLINE ended the run rather than the budget, naming what it NEVER STARTED apart from what it STOPPED PART WAY THROUGH. Every count in that report is what the run MEASURED and SPENT rather than what the selection planned or the budget admitted, the planned budget keeps its own sentence, warm-ups AND counted samples are charged only when they really loaded a page, and `abNavigationsForRoute` prices a budgeted redirect such as `/onboarding` at NOTHING for the same reason, so the plan and the spend agree and the budget can never drop a redirect for navigations it does not make. The admission check asks a different question and so reads `abWorkUnitsForRoute`, which counts every request and load a route will make: a redirect priced at nothing for the CLOCK left the run with no observed pace, and the route after it was admitted however little time remained, and a breached path with no row in `perf/route-budgets.json` is reported as the two files disagreeing rather than as budget pressure. The report states how many routes breached BEFORE how many were measured, NAMES what the budget could not reach, is rewritten after EVERY route so an aborted run keeps what it measured, and says PARTIAL while it is. A VERDICT COSTS THE WHOLE PLAN ON BOTH ARMS: an arm that lost samples reads NOT COMPARED and every row prints what backed each median, because a median of one wearing the same label as a median of seven is the laundering this lane exists to stop. Three more: the A/B honours each route's own noise floor on BOTH arms, so a marked route is judged on the median of seven exactly as the sweep judges it; it declares `retries: 0` for the same reason the sweep does; and it stops before any worktree, install or build when the merge base IS this head, since two arms on one commit is a comparison of nothing, or when anything already answers on either arm's port, since a server this script did not start would be measured and labelled as this branch. (4) BRANCH SLOWER COSTS TWO TESTS AND NEITHER ALONE. The RELATIVE band is the method's `sampleSpreadWarnPct` for EVERY route without exception: a route's own `measuredSpreadPct` records spread WITHIN one arm and must never widen a question about the gap BETWEEN arms, since the A/B already answers arm noise twice, through the median of seven a marked route's run plan buys and through interleaving with an alternating lead, so a gap that survives both is not jitter. The ABSOLUTE test is that metric's own `sampleSpreadFloors` entry, as `samplesDisagree` uses it, CAPPED BY THE ROUTE'S OWN CEILING times `resampleWithinCeilingPct`: BRANCH SLOWER costs both the relative gap and the absolute one, because 8 ms of server render against 9 ms is 12 per cent and is jitter, and a wrong BRANCH SLOWER sends somebody hunting a regression that does not exist. The cap exists because the 250 ms lcpMs floor sits ABOVE the whole 300 ms ceiling of `/crawls` and `/today`, so an uncapped floor read a real 220 ms regression as NOT SLOWER THAN BASE and then named it runner drift, exonerating the branch in the words the standing law uses to re-run a red check. The fraction is the band `medianSitsOnTheLine` already treats as jitter about a ceiling, so a gap smaller than it cannot be evidence against that same ceiling, and no floor or ceiling moved for any of it. <a id="speed-is-a-number-and-the-number-is-enforced"></a>

- **Speed is a number, and the number is enforced.** `docs/PERFORMANCE_BUDGETS.md` owns page and hot-read budgets; `perf/route-budgets.json` holds the page ceilings and `perf/api-budgets.json` the API latency ceilings. The `performance-budget` CI job fails a pull request that goes past a page ceiling, while `api-latency-budget` probes a successful main deployment. Take a ceiling DOWN whenever the measured figure sits comfortably below it; take one UP only in the commit that needs it, with the reason and a measured figure. The doc also names the seams that hold the numbers up, the largest of which is a POLICY: the per-request CSP nonce (`proxy.ts`) rules out static generation, ISR and PPR, so a nonce'd page view is a function invocation with no CDN copy to serve instead.

<a id="a-route-that-redirects-is-measured-as-a-redirect-never-as-its-target"></a>

- **A ROUTE THAT REDIRECTS IS MEASURED AS A REDIRECT, NEVER AS ITS TARGET.** The sweep opens each route with `waitUntil: "load"` and a browser follows a 3xx, so the moment a budgeted route starts redirecting its row measures the page it LANDS ON under a ceiling written for the page it used to be. `/onboarding` did it on 7 September 2026: it began answering 307 to `/` and shipping no document (Astra's live walk, finding B6), and the next sweep read the HOMEPAGE'S 45 requests against the 41 that used to buy an almost empty first-run shell, while `/` itself is budgeted at 46 and was inside it. Measured on a production build, the two return the identical count, because they are now the same page. BOTH READINGS OF THAT NUMBER ARE WRONG: calling it a regression takes a ceiling up to hide a measurement pointing at the wrong page, and calling it a win lets any route shed its own ceiling by learning to redirect. So the row says what it is. `redirectsTo` (`lib/performanceBudgets.ts`) declares it, `measurePerfRedirect` (`e2e/helpers/perfMeasurement.ts`) measures it, and the four figures become the redirect's own cost: one request, no script, no paint. THREE rules. (1) THE TARGET KEEPS ITS OWN ROW, which is what stops the page falling out of the budget entirely, and the fence refuses a `redirectsTo` naming a path nothing budgets. (2) THE LANE ASKS THE WAY A BROWSER ASKS: an APIRequestContext sends `Accept: */*`, and the /onboarding rule keys on a document request precisely so an RSC fetch is untouched, so a bare request is answered with the document and the lane would report "it did not redirect" about a route that does. (3) IT ASSERTS THE REDIRECT rather than tolerating its absence, so a declared route that quietly starts serving a document again fails here instead of passing every ceiling on one request. A ceiling of 0 on a redirect row is the honest one and not a missing ceiling, which is the one narrowing the every-metric-positive fence takes. Pin: `__tests__/performanceBudgets.test.ts`; method `docs/PERFORMANCE_BUDGETS.md` "A route that redirects is measured as a redirect".

<a id="the-basemap-already-rides-a-cdn-so-the-first-tile-is-won-in-the-engine-not-on-th"></a>

- **THE BASEMAP ALREADY RIDES A CDN, SO THE FIRST TILE IS WON IN THE ENGINE, NOT ON THE WIRE.** The OpenFreeMap host is served by Cloudflare from London: tiles carry `public, max-age=315360000` on immutable dated paths and answer `cf-cache-status: HIT`, and only the style and TileJSON carry `max-age=86400`. Measured cold from London on 3 October 2026, style plus TileJSON plus first tile is about 200-350 ms, and a Cloudflare MISS tile still answers in under 200 ms. The 8,568 ms first tile the September review recorded on its throttled phone rig is the MapLibre chunk (4,939 ms), map construction (6,562 ms), style parse (7,304 ms) and scene build (7,915 ms) before it; the tile's own share is mostly decode on a throttled CPU. So a second CDN of ours in front of OpenFreeMap was proposed, measured and DROPPED: it buys tens of milliseconds at best, adds a host that needs its own preconnect (`app/layout.tsx`), CSP (`proxy.ts`) and service-worker entry (`public/sw.js`), and a paid edge that lapses would leave the map waiting out `STYLE_LOAD_TIMEOUT_MS` before the CARTO fallback. Do not re-propose a tile CDN without first re-reading those headers; if they still say HIT and ten years, the answer stands. First-paint work goes to the engine's own time: the style round trip, construction to first frame, and keeping any pin entrance off the critical path. Fetching the MapLibre chunk earlier is not on that list: rule (6) above measured an engine warm that moved its arrival by six seconds and left the first tappable pin where it was, so a preload or intent warm of the chunk needs an A/B that moves the first tile or the first pin. Record, measurements and the ranked list with file references: `docs/perf/tile-cdn-2026-10-03.md`.
