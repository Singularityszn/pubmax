# Identity, accounts and sessions

Moved from [`lib/AGENTS.md`](../../lib/AGENTS.md). Authoritative policy detail lives here; the area index stays short.

<a id="the-password-ask-is-separate-from-password-creation"></a>

- **The password ask is separate from password creation.** `CreatePasswordPrompt` runs in the deferred shell under the shared prompt budget. `lib/passwordPrompt.ts` owns its once-per-account marker and offers it only after a claimed handle and `hasPassword: false` answer. `SetAccountPassword` remains the only password setter. Pins: `__tests__/passwordPrompt.test.ts`, `__tests__/createPasswordPromptRender.test.ts`.

<a id="the-signed-in-account-is-the-only-identity-authority-on-a-device"></a>

- **The signed-in account is the only identity authority on a device.** `lib/deviceAccountIdentity.ts` owns the artifact set and the owner stamp; `AuthProvider.updateSession` rebinds it on every auth event before children re-render, and a different or unstamped account loses the whole set atomically. Sign-out drops set and stamp together, in that order. Identity is TRI-STATE: a surface that NAMES or ROUTES the viewer stays neutral until the live session answers, never a cache, never a confident "nobody" from a failed read (`components/auth/useViewerHandle.ts`, `components/auth/useViewerSession.ts`, and the shared `providerHasAnswered` in `lib/authProviderRevision.ts`, which only `authenticated` or `signed-out` pass). `ensureSupabaseBrowser()` can REJECT, so `lib/authClientLoad.ts` retries it and answers `unavailable`, and `bootstrapAuthSession` preserves failed reads the same way, publishing nothing and asking for `requestDeploymentSkewCheck`. A Night Profile MIRRORED off an account leaves with it; one typed here stays. Writes announce themselves, because a same-tab `localStorage` write raises no `storage` event. Every browser write to an actor-gated route sends its bearer token so the SERVER derives the actor (`resolveMessageHandle` + `gateHandleAction`). Pins: `__tests__/deviceAccountIdentity.test.ts`, `__tests__/gatedActorAuth.test.ts` (tree-wide), `__tests__/viewerSessionSeam.test.ts`, `__tests__/viewerSessionSurfaces.test.tsx`, `__tests__/followRoute.test.ts`, `e2e/account-switch-identity.spec.ts`.

<a id="a-device-may-hold-several-accounts-and-exactly-one-of-them-owns-it"></a>

- **A device may hold several accounts, and exactly one of them owns it.** `lib/deviceAccountSessions.ts` is the lane: one key, one REFRESH token per account id, capped at `MAX_DEVICE_ACCOUNTS`. It sits deliberately OUTSIDE `DEVICE_IDENTITY_LOCAL_KEYS`, which is dropped whole on every account change, and that is safe only because every row names its own account id and a row is only ever activated by minting THAT row's own session. The swap is `lib/deviceAccountSwitch.ts`: exchange the stored token at GoTrue's own `/auth/v1/token`, then `supabase.auth.setSession`, so the ordinary auth event runs the ONE atomic device-identity pass unchanged. Never refresh through the live client instead, because `auth.refreshSession` tears the stored session down on a failed refresh. The resume cookie mirrors the ACTIVE account only. An outcome is THREE-WAY: a token GoTrue REFUSED is deleted and its row reads "Signed out"; a read we could not run keeps the token. Sign-out is SCOPED (`SignOutScope`), offered only above one account, and awaits `clearPersistedSession`. `components/auth/AccountDeviceControls.tsx` is the ONE control, shared by the nav card and /login's signed-in card, because `.siteNavBar .authUser:not(.authUserNav)` is hidden at 640px while compact Sign in (`.authUserNav`) stays in the bar; `/login?add=1` is the only thing that makes a live session see the form; a held profile card carries the HANDLE it is about. Pins: `__tests__/deviceAccountSessions.test.ts`, `__tests__/deviceAccountSwitch.test.ts`, `__tests__/accountSwitcherRender.test.ts`, `__tests__/loginAddAccount.test.ts`, `e2e/account-switch-identity.spec.ts`.

<a id="everybody-who-joins-is-taken-to-be-an-adult-on-one-recorded-tap"></a>

- **Everybody who joins is taken to be an adult, on ONE recorded tap.** Captain decision 2026-08-10. `accountIsAdult` (`lib/adultGate.ts`, a leaf that no Social module reaches into) is THE ONE adult gate, over the stored date of birth and the recorded self-assertion (`adult_self_assertions`, migration `0103` + rollback; `lib/adultSelfAssertionStore.ts`, written only by `POST /api/identity/adult-assertion` from the caller's own bearer token). Social renders it as one line plus one button in the empty-state idiom (`SocialAccessBoundary`), never a dialog, with `socialSurfaceName` naming the surface. During live default `/social` is indexable and in the sitemap (`socialDocumentRobots`, `socialListedInSitemap`); `PUBMAX_SOCIAL_FRIENDS_LAUNCH=0` restores preview and noindex state. Pub photo walls ask the SAME question through the SAME function. NOTHING else may branch on an assertion: it is not a capability. `PATCH /api/identity/onboarding` CREATES the `private_account_identities` row rather than refusing for its absence; no profile is 409, a first save with no date of birth is 400. <a id="contributing-asks-two-questions-and-the-age-one-is-the-10-aug-rule-s"></a>

- **CONTRIBUTING ASKS TWO QUESTIONS, AND THE AGE ONE IS THE 10 AUG RULE'S.** Captain 5 Sep 2026 ("one rule"), over battle test finding P01: `resolveContributionIdentity` demanded a stored date of birth, and `/api/identity/handle/claim` stores none, so an account claimed that way was sent to a surface that could not answer, on the price path and on every other route behind that gate. The gate asks `accountIsAdult` (`lib/adultGate.ts`), the ONE adult gate, so the recorded one tap IS the age answer where nobody has given another and a stored date of birth decides in BOTH directions. ONE EXCEPTION, added 5 Sep 2026 over review finding F-6: the gate used to ask `needsAdultSelfAssertion` ALONE, which is true only when NOBODY has answered, so an account whose stored date of birth said 2012 walked through the price door while the pub photo wall beside it refused the same account through `accountIsAdult` - one product answering the alcohol-age question two ways, under a sentence claiming an 18+ confirmation nobody had asked for. An under-18 stored date of birth is now refused at EVERY contribution door, which RETIRES the any-age contribution reading the price-submit tests used to pin; `needsAdultSelfAssertion` is still asked for the one thing it says, whether a tap is the ACTUAL thing in the way, and that is what `contributionAdultRefusal` (the pure leaf, the ONE place the branch is chosen, shared by `resolveContributionIdentity` and `app/api/venue-photos/route.ts`) reads to pick between `adult_check_required` with its tap and `adult_check_failed` with `CONTRIBUTION_UNDER_18_REFUSAL`, which offers none. THREE rules. (1) A MISSING HANDLE AND A MISSING AGE ANSWER ARE TWO FINDINGS: `lib/contributionGateStatus.ts` is the pure leaf holding the closed status set (`sign_in_required`, `onboarding_required`, `adult_check_required`, `adult_check_failed`), the ONE sentence each refusal spends and the ONE narrowing (`readContributionGateStatus`); `lib/contributionIdentity.server.ts` re-exports every name, `lib/analyticsEvents.ts` derives its `contribution_gate` steps from it, and no surface may restate the list. (2) THE AGE DOOR RECORDS THE TAP WHERE IT WAS RAISED: `ContributionGateDialog`'s third mode POSTs `/api/identity/adult-assertion` (the same route Social's boundary spends) and then RESUMES the held action, so the price a drinker already typed goes where they sent it. (3) A DOOR THAT ASKS PRINTS NO ALARM LINE (`contributionGateError` drops the gate's OWN refusal sentence, keeps one it did not write), and the dialog is a BODY-LEVEL PORTAL, because the desktop map drawer it opens from is a transformed box and was the containing block for its fixed backdrop. `/api/pint-drops` asks for a linked handle and a verified actor and has never asked for a birth date; a source fence keeps it that way. THE OTHER HALF OF THE RULE IS THE CLAIM CARD, and without it the gate was a door nobody could reach: `AccountOnboardingForm` held `Claim handle` disabled until a date of birth was typed and `PATCH /api/identity/onboarding` answered 400 to a blank one, so every account this build could make held a birth date and the recorded-tap state existed only for legacy rows. A date of birth is now OPTIONAL wherever one is typed, and `readOptionalDateOfBirth` (`lib/privateIdentity.ts`, a pure leaf) is the ONE reading of it: absent covers undefined, null and a blank string, so nothing typed is nothing to save, while a value that is not a date is still `Enter a valid date of birth.`. The `date_of_birth` column of `private_account_identities` is NOT NULL, so an absent answer is an absent ROW rather than a null column: `completeOnboarding` falls to `identityHandleStore().claim`, the RPC `/api/identity/handle/claim` already spends, no migration stands between this code and a deploy, and `complete` is read off the row the claim really wrote rather than stated. What a save of OTHER private details still needs is a date of birth to build that row around, which is the one place the answer is not optional and is why the column is the thing to change if it ever must be. /privacy and /terms moved in the same commit, because "date of birth is needed to finish signup" was a data-path claim. <a id="a-linked-social-is-the-owner-s-own-public-handle-and-oauth-is-the-narrower-quest"></a>

Manual is therefore true for every provider, and a provider must never be unlinkable because nobody registered an app. `validateSocialLink` takes a typed username OR a pasted profile link and lands both on ONE canonical URL per platform, refusing a host that is not that platform however plausible. These links are PUBLIC by design and are the one public addition to `/api/profiles/[handle]` (`publicSocialLinks`); email, date of birth, gender and full name stay behind the owner-authenticated read (`__tests__/profilesRoutePrivacy.test.ts`). The nav chip, the signed-in card on `/login` and a thread header all wear a person's own face and name through ONE hook, `components/auth/usePublicProfileCard.ts`, which holds the answer against the handle it is about and answers a card read in the last minute from the tab's own snapshot with no request, because SiteNav renders on every page. The owner changing their photo or name announces it (`announceProfileCardChanged`) so no surface keeps the old face for the rest of the minute. The chip is named from the card, then the provider, then the claimed handle, and never from the first letter of the login email (`__tests__/usePublicProfileCard.test.tsx`). <a id="founding-membership-buys-belonging-and-never-a-capability"></a>

<a id="a-starter-pack-is-a-bundle-of-people-who-are-already-here"></a>

THE RULE is that nothing is invented: a borough pack takes accounts whose own public `homeCity` NAMES that borough, matched as a whole phrase, so a district is not another name for the borough it sits in and under-inclusive is the safe side. A pack under the member floor does not show at all, and a pack that cannot show answers the same 404 as an unknown slug. Membership rides the SAME closed row set the people directory reads (`listClaimedProfiles`) plus `listFoundingMembers`. Following a pack is ONE action through the ONE edge write, `followOnce` (`lib/followWrite.server.ts`), shared with `/api/profiles/[handle]/follow`; the pack route spends ONE rate limit for the whole pack and reports a per-member outcome with a summary naming the number that did not go through, because a part-failure is never rounded up. `starterPacksSurfaceVisible` decides the signed-in surface, and the follow count behind it is TRI-STATE, so it rides the packs read itself and a null renders nothing. <a id="the-people-directory-is-discovery-and-a-starter-pack-is-not"></a>

- **The people directory is DISCOVERY, and a starter pack is not.** `lib/peopleDirectory.ts` owns both halves and is pure. `/api/profiles/directory?viewer=<handle>` drops the accounts that viewer already follows, so a mutual leaves with them, while somebody who follows YOU unreciprocated stays and reads "Follow back" and the viewer's own row stays, printed as "You". The viewer param discloses nothing new, because `/api/profiles/[handle]/following` is already public, and the follow read is TRI-STATE by way of null: a read that FAILED filters nothing. Discovery narrows what is SHOWN out of the page window, never which rows were examined, so the cursor keeps its meaning and a page may come back short with `alreadyFollowing` saying how much it took; a landed follow also takes its own card off the list in the browser. The empty line is `directoryEmptyLine` and has THREE states, because an all-followed list may not read as an empty city and a list with another page behind it may not claim it showed you everyone. The starter packs keep their followed members on purpose. A FOLLOW LIST names the person, so the follower and following routes answer `FollowListEntry` rows and `lib/followList.ts` is the ONE reader of that body (`parseFollowListEntry`, and `followListHandleSet` where a surface only asks whether the viewer already follows somebody). The name and the face are DECORATION: `followListEntries` (`lib/followListProjection.server.ts`) enriches in ONE round trip through `profileStore().getPublicCardsByHandles`, and a projection that could not answer costs a name and a face rather than emptying the list. A tombstoned row answers an empty card. <a id="an-add-link-needs-an-account-and-the-link-survives-making-one"></a>

- **An add link needs an ACCOUNT, and the link survives making one.** `/add/<handle>` is the growth link a drinker shares at the table, and it may never take the device's cached `pubmax_handle` as the adder. `lib/addLink.ts` is the whole policy and it is pure: the two doors, the one-shot `shouldAutoAdd` predicate, the receipt copy and its ways onward. FOUR rules ride with it. (1) `?auto=1` is the ONE query `safeInviteReturnTo` admits (`lib/inviteReturnTo.ts`), and it only performs the add when THIS DEVICE took a door FOR THIS HANDLE: `markAddLinkDoorTaken` writes a one-shot marker keyed by the target handle, `shouldAutoAdd` requires it, `consumeAddLinkDoorTaken` spends it. The marker is deliberately not per-tab, because a magic link finishes the sign-up in a FRESH TAB, and it is bounded by `ADD_LINK_DOOR_TTL_MS`; a crafted third-party `/add/<anyone>?auto=1` cannot auto-follow. (2) A SIGN-UP finishes on the claim surface, so `addLinkAwareDestination` threads the add link through as that surface's own `?returnTo=`, which `/u/you` and `AccountOnboarding` hand back; `arrivalDestination` alone would drop it, and `LoginPage` gives the password form `redirectTo` only when the page carries an explicit `?from=`. <a id="an-account-is-public-or-private-and-that-is-a-visible-choice-rather-than-a-prope"></a>

- **AN ACCOUNT IS PUBLIC OR PRIVATE, AND THAT IS A VISIBLE CHOICE RATHER THAN A PROPERTY OF A SURFACE.** The account-privacy wave in `docs/factory/roadmap.md`. Privacy here had always been per-surface and per-capability (a Plan through a member capability, a Crew through membership, a conversation through participation), so there was nowhere to answer "who can see me"; migration `0154` + rollback is that place and `lib/accountVisibility.ts` is the whole vocabulary, a PURE LEAF holding the closed word set, the default, the parse and every sentence the setting prints. SEVEN rules. (1) THE VOCABULARY IS CLOSED AND MIRRORED IN SQL, the `lib/drinks.ts` idiom: two words plus a CHECK that refuses a third, so a third answer is a migration rather than a value the column would happily take, and a boolean column full of `true` would have said nothing about what it was true of. (2) THE PARSE HAS TWO FAILURE DIRECTIONS AND THEY ARE OPPOSITE. An ABSENT value is the public default, because that is the shape of every row written before 0154 and nobody could have chosen private yet, so public STATES what those rows are. A word we do not RECOGNISE fails CLOSED to private, because it was written by something that is not this app and a word we cannot read is no licence to publish a bio. (3) THE PROJECTION IS AN ALLOW LIST. `lib/profileVisibility.ts` names the fields a limited card carries (the handle, the display name, the face, the founding mark, the choice itself and the row's dates) and copies only those, so a field added to `PublicProfile` tomorrow is withheld BY DEFAULT; a deny list is how the next public field leaks, which is the defect a second copy of `toPublicProfile`'s field list already caused once. Withheld are the bio, the city, the favourite drink, the interests, the workplace, the cover rotation and the linked socials. The handle, name and face stay because a friend at the table has to recognise whom they are adding and because the follow lists and the people directory already publish exactly those for every claimed account. (4) ONE SEAM DECIDES AND IT IS THE PLAN BOUNDARY'S TWIN. `resolveProfileProjection` (`lib/profileVisibilityBoundary.server.ts`) reads NO environment variable, because D01 cost the Plan boundary precisely that, and it FAILS CLOSED: no bearer, an unverifiable one, a store error on either side, or an account owning no handle each answer the limited card. It also costs a PUBLIC account nothing, the cheap synchronous question being asked first, so the ordinary read verifies no bearer, reads no follow edge and never spends the cover rotation read, which is handed over as a thunk for that reason. (5) A LOT IS THE APPROVED RELATION AND THERE IS NO FOLLOW REQUEST. The full card goes to the owner and to a MUTUAL follow, read through `lib/followRelation.ts` so that word is still decided in one place, and a one-way follower is a stranger. Ownership is read off `profiles.user_id` and never off handle TEXT (the messaging-channel F-1 rule), and the viewer comes from the BEARER and never from `?viewer=`, which is the follow control's own self-asserted convenience: it may decide what a button SAYS and never what a body CARRIES, which is also why the profile page's own read now sends a token once the device has a handle. (6) THE BODY CARRIES TWO FACTS AND THEY ARE DIFFERENT: `profile.visibility` is the CHOICE the account made and `projection` is which card THIS reader was handed, so `isLimitedProfileProjection` owns that discriminant the way `isPlanPreviewProjection` owns the Plan's, and no surface restates it. (7) THE CHOICE DOES NOT REACH A PRICE, and the control says so beside itself (`ACCOUNT_VISIBILITY_COPY.pricesStay`): a Pint Drop is evidence about a pub, it carries its handle on the map by design, and the standing rule is that we keep the prices. TWO CONSEQUENCES ELSEWHERE. A BOROUGH STARTER PACK REFUSES A PRIVATE ACCOUNT, because membership IS the disclosure: the pack's heading names the borough and `homeCity` is one of the withheld fields, so `selectBoroughPackMembers` drops them while the founding pack keeps them (a founding number is public by design and printed on a public wall) and the people directory keeps them too (it prints exactly the name and face a limited card already carries). AND THE WRITE REFUSES RATHER THAN LOSING THE CHOICE: the store's additive-rollout guard is the OPPOSITE of the receipt-photo guard beside it, because losing a photo is a cost and losing a privacy choice is a lie, so a visibility write with no column throws `ProfileVisibilityUnavailableError` and the route answers a 503 naming the choice. WHAT IS NOT COVERED YET is named rather than implied: the follower and following LISTS stay public (`/api/profiles/[handle]/followers` and `/following` are read unauthenticated by the feed's friends lane and by the people directory, so gating them is its own slice), the Social BLOCK is not read here (`docs/security/PERMISSION_MATRIX.md` records why), and the activity-history layer is the roadmap's next wave. THE CONTROL IS THE ONE FIELD IN THE EDITOR THAT IS NOT SNAPSHOT-ONCE, because `?edit=1` opens the editing surface on IDENTITY and the profile read lands a beat later: a snapshot taken in that window opens on the public default and then rides every save, so an owner who had chosen private and came back to fix a typo was republished by the typo. An untouched control displays whatever the row currently says and a save with nothing chosen and nothing read omits the key, which leaves the column alone. AND A CARD DOES NOT CROSS A BOUNDARY: `followKey` is the account and the handle together, so a sign-in, a sign-out and a walk to another profile all drop `stored`, the projection and the read state, the way `lib/surfaceDataCache.ts` drops its whole store.
