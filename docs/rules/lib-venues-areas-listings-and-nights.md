## Google Places venue content

Captain decision, 4 October 2026: "the remainiung 676 , paste from google , use google places to enrich our data , thats why we pay" and "COPY THE DATA ... copy everything from google". This lifts the earlier verify-only restriction for regular opening hours, formatted address, national phone number and website, with Maps Platform terms risk accepted. The extras packs also copy rating, rating count, price level, editorial summary, the pub amenity booleans, and accessibility and payment options, every field billed under the one Enterprise + Atmosphere request; `PLACES_EXTRAS_FIELD_MASK` in `lib/placesEnrichment.ts` is the list. It does not change the photograph licence rule below.

`npm run enrich:google-places -- --dry-run --usage` reads current monthly usage and projects spend. Live collection uses `--write --exclusive` after other shared-key jobs finish. `--pack=` picks one pack, and each pack owns its output, checkpoint, `inputHash` and spend ledger: `london` (the default) and `london_extras` read only previously verified place ids from `data/places_verification/london.json`, and `uk_cities` and `uk_cities_extras` read them from `data/places_verification/uk_cities.json`, so the UK-cities ledger neither changes the London pack's `inputHash` nor draws on its cap. London packs prioritise the hours report's incomparable pubs, then mismatches, then remaining London pubs; UK-city packs keep ledger order. One Enterprise call returns all core fields (hours, address, phone and website), so contact collection adds no second Details charge. Every attempt reserves its full tariff before the request, including failures: USD 0.020 for a core pack and USD 0.025 for an extras pack. A place-level failure (HTTP 404, or an HTTP 400 `INVALID_ARGUMENT` whose reason is not an `API_KEY_*` reason) is recorded in `errors`, the row is done for that push and the run continues. Any other failure, including an API key 400, stops the run with the attempt counted and the row left pending, so a broken key or quota cannot spend the budget. Every live run, stopped or not, ends by printing the push's `failedRows`, and the dry run prints them too. Error bodies are classified in memory and never logged. The London pack's cap is USD 85 per calendar month (UTC), cumulative across the first push and every refresh, and each attempt counts against the month it is reserved in, even when a run crosses midnight at a month end, following the captain's raised USD 150 total cap. October 2026 has USD 23.94 of room left after the first push's USD 61.06. The `uk_cities`, `london_extras` and `uk_cities_extras` packs share one USD 28 task cap that spans resumes, clones and calendar months and does not reset; the UK-city core push spent all of it, so the extras packs are unrun until the captain raises it. Daily quota overrides are restored and checked after success, failure or a handled signal.

The committed pack is the spend ledger. A clone without the gitignored checkpoint seeds its resume from the pack's attempts, completed rows and errors, and the run uses whichever of pack and checkpoint records more attempts. Without `--refresh` the command resumes the current push and never re-requests a row that push already attempted. `--refresh` starts a new push only when a copied row is older than 30 days and the current push has no budgeted rows left. It keeps every attempt in the cumulative `attemptedCalls` and the month's `monthAttemptedCalls`, and re-requests rows that are missing or were more than 30 days old at the new push's `runStartedAt`, including rows that failed in an earlier push.

Each `data/places_enrichment*.json` pack holds each returned field with `source: "google_places"` and that request's `observedAt`, and each row carries the same request `observedAt`, so a paid response with no usable field still completes its row. A missing field is omitted. A resumed run keeps completed fields' original dates. `lib/placesEnrichment.ts` owns conversion, priority and spend arithmetic; `lib/venuePlacesEnrichment.ts` applies fields independently. A copied field past 30 days keeps showing with its own `observedAt` date until a refresh replaces it, and the sheets credit every copied field, core or extras, as "Google Places · Checked <date>". A Google price level never becomes a pint price, and only a stated `true` option produces an accessibility or payment chip. The Google details panel, with its call and website links, renders only for a venue that has Google Places content. Pub website details can also appear without Google content, as described in the [product features](../../README.md#features). Copied hours set `venue.openingHours`, and so open state, busyness and get-in, only within 30 days. Invalid and future-dated values cannot replace usable values from another source. The dataset's registry stamp is the oldest copied row across every published pack (London, UK cities and both extras packs), so a newer row or pack cannot hide an older one. The freshness spine reads it from `data/places_enrichment_stamp.json`, a small head (oldest `observedAt`, and each pack's input hash, oldest `observedAt`, spend and summary) that every runner save, whatever its pack, and every `npm run build:places-enrichment` derive from the packs, so no freshness request parses a full pack and the stamp cannot drift from them. Its staleness is advisory in `check:freshness`: an overdue refresh is a visible mark and does not fail verify.

`npm run build:places-enrichment` derives one runtime file per canonical OSM identity, and the freshness stamp, from every committed pack without fetching or restamping it. Rows with the same venue id and Google place id merge, the newer observation of each field winning, and a conflicting place id stays a separate row so the reader refuses the ambiguous match; dev and build run it before starting Next. The server reads only requested identity files, caches successful lookups, and never parses the full Places pack on a cold request. The server applies content to curated detail through exact OSM identity, keyed by `canonicalOsmId`, and the base-pub sheet reads it through its existing harvest-overlay request. Opening hours reach the venue sheet at any age and the detail opening-state calculation only while fresh. Address, telephone and website pass through existing contact and URL guards. No copied content enters slim pins, price rows or price bands. The original verification artifacts remain verdict-only; their content fence is scoped to those artifacts. - **WHAT WE KNOW ABOUT A PUB IS SAID IN STATES, AND A BOOLEAN CANNOT HOLD ONE.** Astra finding F03, measured on production 6 September 2026 over `GET /api/venue/venue-p7p18j`: the phone column held `"\u{1F310} https://www.lsesu.com/social/three-tuns/"`, every amenity answered `false` over blank source columns, and the get-in answer said `"likely"` ("Two of you should get in fine") over `isOpen: "unknown"` and `reportCount: 0`. One cause: a venue record carries a fact the source STATED, a fact nobody recorded and a reading we DERIVED, and all three left the building as plain values. `lib/venueTruth.ts` is the ONE owner and a PURE LEAF (it imports `lib/haversine.ts` and `lib/httpUrl.ts` and nothing else), holding `VENUE_TRUTH_DISTINCTIONS`, the seven pairs no reader may merge. FIVE rules. (1) CONTACTS ARE PUBLISHED ONLY WHEN THEY PARSE: `venueContactContract` answers a field only when the raw value is the thing its column claims to be, a `tel:` is built from digits it understood and never from an edited value, and a contact is the FIRST VALUE THAT PARSES rather than the first non-blank one, because a pub's rows are one pub and 478 of the 852 pubs holding any phone value lead with something that is not a number, and `app/api/venue/[id]/route.ts` STRIPS `phone_number`, `email`, `website` and `booking_link` off every price row on the wire, because a caller reading one is a caller reading an unchecked value. THE STATUS IS THE ONLY AMENITY ANSWER ON THE WIRE: that route strips the `amenities` booleans too, because the body shipped `"food": false` beside `"food": "unknown"` about one pub and an API caller has no "a false means not known to be true" rule to read it with. The record every filter and score reads is rebuilt in the browser by `venueFromDetailPayload` (`lib/venues.ts`), the ONE reader of that payload, where only a `known-true` becomes true; the four page and photograph URLs on a price row deliberately stay, each being read through a validator at the point of use (`firstHttp`, the image host allow-list) rather than trusted. (2) A BLANK IS UNKNOWN, NEVER FALSE, AND SO IS A VALUE SAYING NOBODY ANSWERED ("N/A" and its siblings), whose leading `n` the no-shaped rule used to read as a stated absence: the bundled dataset's ten amenity columns carry only yes-shaped values and blanks over 3,760 rows, so every `false` the product printed was an invented negative; `amenityStatusFromValue` reads a leading yes with its qualifier (`yes (fri & sat)`), a leading no as a stated absence, and a value answering a DIFFERENT question (`Dog friendly` in the cocktails column) as unknown. `venueAmenityStatus` (`lib/venues.ts`) applies it at both layers, a slim-built venue's `false` reading unknown. The `Venue` record's own `amenities` booleans are UNTOUCHED, because every filter and score already reads a false as "not known to be true". A surface that PRINTS one asks for the status: an unknown renders nothing and the whole row hides, the idiom the accessibility chips beside it already follow, and the chip wears their brass rather than green, since only stated facts render now and the cheap price band is the one thing green may mean on that sheet. (3) A POSITIVE GET-IN ANSWER IS GATED ON EVIDENCE: `getInConfidence` is `evidenced` only with a known-open door AND a fresh community report, `pattern-only` for the clock heuristic (which is about the hour rather than this pub and corroborates nothing), and `unknown` when the door is unknown; `canGroupGetIn` answers `fit: "unknown"` and `GET_IN_CHECK_LABEL` there. The size-based answers (`book-ahead`, `unlikely`, `uncertain`) are about the GROUP rather than the door and are ungated. (4) AN AREA'S RADIUS IS HOW FAR IT REACHES, NOT WHERE A PUB IS: `venueAreaClaim` is the ONE geometry (`nightAreaForPoint` delegates to it, so which area LISTS a pub never moved) and answers `inside` inside `AREA_CORE_RADIUS_FRACTION` (0.75) of the curated radius, `nearby` in the outer band, `unplaced` otherwise. Measured over the 1,995 shipped slim rows: a core pub names its own area in its own address 37.8% of the time against 23.4% in the band, and the band costs 167 rows (21%) the stronger word. /today marks such a row `AREA_NEARBY_ROW_TAG` ("Just outside", the relation to the PLACE, because that card says "near you" about the reader), and its HEADING follows the rows: `todayPintsHeading` says "around" when more than half of them are outer-band and keeps "in" otherwise, a tie keeping the stronger word, because a heading saying "in" over rows saying "outside" argues with itself. (5) A HARD CONSTRAINT IS SATISFIED ONLY BY A STATED PRESENCE, and the readers that narrow on one already say so in their own facts: `isKnownStepFree` (`lib/venueAccessibility.ts`) and the plan route evidence read a `true`, never a blank. The shelf pair `hardConstraintSatisfied` and `hardConstraintNotice` had no caller anywhere in the tree outside its own unit test, so it was deleted rather than kept as a third owner beside this leaf. THE SENTENCE STILL HAS AN OWNER, AND IT IS `accessibilityFilterSummary` (`lib/venueAccessibility.ts`): the map rail builds it and renders it inside the accessibility filter section (`components/map/ControlRail.tsx`), so a reader who narrows on step-free already reads "Only showing pubs with confirmed step-free entry. N confirmed so far; help by spilling what you know." What that summary does NOT yet say is the second half of the deleted notice, that an unlisted pub may qualify and nobody has checked. Issue #1639 (https://github.com/Singularityszn/pubmax/issues/1639) owns that one clause, through the `docs/VOICE.md` door. They now ship from their own pack, `data/osm/uk/uk_osm_unnamed_pubs.json` (`normalizeUnnamedOsmPubElement`: OSM id, position, address; no name key exists), NOT inside `data/osm/uk/uk_osm_pubs.json`, so no reader of that pack, and none of the hashes built over it, ever meets a nameless pub. FIVE rules. (1) A NAMELESS ROW IS A SIX-ELEMENT ROW WITH NAME `""`: `scripts/build_uk_base_shards.mjs` writes it with its stable `venue-uk-<ref>` id, so a save, a price and a cold deep link attach to it like to any base pub, and `lib/ukBasePubs.ts` decodes it as `name: "Pub"` plus `unnamed: true` (the key exists ONLY on an unnamed pub, so a named pub's record and feature are unchanged). A bar with no name stays malformed. (2) IT DRAWS AT STREET ZOOM ONLY, UNLESS IT IS SELECTED: `uk-base-point` filters unnamed pubs out, and `uk-base-unnamed-point` draws them through `ukBaseUnnamedFilter`, which holds them to `UK_BASE_UNNAMED_MIN_ZOOM` (16) except the selected id, so a tapped, saved or deep-linked one keeps its pin under its ring at any base zoom; its provisional badge follows the same filter. The label is the generic "Pub". (3) IT IS NOT A NAME: `searchUkBasePubsByName` and `buildUkBasePubListModel` skip it, so a query of "pub" never lists a street of them and the list total does not count them. The pack never reaches the national name search, curated lists or Plans. (4) THE SHEET SAYS SO: `UnverifiedPubSheet` shows "We don't know this pub's name yet." under the "Pub" heading, and the price form still works. (5) NAMED-ONLY CONSUMERS STAY NAMED-ONLY: the Night Area builder (`isBasePubRow`) and the UK price estimate bundle skip a row with name `""`, and `ukBaseVenueIdAliases` retires a departed one under the label "Pub", so a refresh that drops one never fails the build. Pins: `__tests__/ukBaseUnnamedPubs.test.ts` (decode, feature round trip, search, list, sheet, normalizer, committed shards), `__tests__/mapSymbolCollision.test.ts` (layer, zoom, filter, order, deep-linked selection); data map `public/data/uk_base/README.md`.

<a id="a-night-area-outside-london-is-derived-and-it-may-claim-only-what-osm-states"></a>

- **A Night Area outside London is DERIVED, and it may claim only what OSM states.** London's twenty patches stay hand-curated in `lib/nightAreas.ts`. Manchester, Birmingham, Leeds and Bristol get theirs from the OpenStreetMap base layer: `npm run fetch:city-places` writes the `place=suburb|neighbourhood|quarter|city` nodes to `data/osm/cities/place_nodes.json`, and `npm run build:city-night-areas` clusters the committed `public/data/uk_base` pubs around them into `public/data/night_areas/uk_cities.json`, which `lib/nightAreas.ts` imports. FIVE rules. (1) The base layer holds no price, no opening hour and no station, so a derived area arrives `discovered` with an EMPTY `transportAnchors` list and every one of those in `missingEvidence`: `validateNightAreaCatalogue` therefore admits an empty anchor list and still refuses a blank one, and nothing derived can be route ready, publish a priced landing or enter the sitemap. (2) The base layer's own `public/data/uk_base/places.json` is folded out of `addr:*` tags on pub rows and names eight localities in the whole of Birmingham, which is why the names come from place NODES instead. (3) The city centre is taken first, whatever its reach, because the densest pubs in a city ARE its centre and picking the densest NODE there named Manchester's middle "Gay Village"; a `suburb` then outranks a `neighbourhood` or a `quarter`. (4) The pub COUNT follows the RADIUS: a member outside the capped radius is dropped from the count rather than the radius stretched, so every counted pub is inside its own circle. (5) `NIGHT_AREA_SLUGS` is now `LONDON_NIGHT_AREA_SLUGS` plus `DERIVED_NIGHT_AREA_SLUGS`, and a table that is LONDON'S (the weather points in `lib/weatherAreaCoords.ts`, the late-food evidence in `lib/lateFood.ts`, the Exa matchers, the /today weather loop) is keyed on the London half alone, or an area in another city reads as an empty London row. A picker takes `nightAreasByCity()` and groups under the city, because two cities can name a patch the same thing. Adding Birmingham and Leeds as CityIds also means a row in `lib/cityBounds.mjs`, `lib/cityVenuePacks.mjs`, `lib/cities.ts`, `lib/cityCapabilities.ts` and BOTH venue-id prefix tables (`lib/cityVenueId.mjs` and `lib/cityVenueIds.ts`): a city missing from the first gets a null venue id and its whole pack collapses to one pub. Pins: `__tests__/cityNightAreas.test.ts`, `__tests__/nightAreas.test.ts`, `__tests__/llandudnoPack.test.ts`.
