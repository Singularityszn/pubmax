# Builders and publishers

Moved from [`scripts/AGENTS.md`](../../scripts/AGENTS.md). Authoritative policy detail lives here; the area index stays short.

<a id="the-hyped-pubs-publish-is-one-command-and-it-fetches-nothing"></a>

- **THE HYPED-PUBS PUBLISH IS ONE COMMAND, AND IT FETCHES NOTHING.** `npm run ingest:hyped-pubs` (`scripts/hyped-pubs-ingest.mjs`) reads a hand-written research file, validates every row, matches what it can to a curated venue and writes `public/data/hyped/london.json`. It reads no network at all, so the source-permission fence has nothing to gate: the links in a row are printed for a reader to follow, never fetched by us. FOUR rules. Every refusal is COUNTED in the run report rather than repaired, so tomorrow's research gets better rather than quietly shorter. A stated venue id no curated venue answers to is a refusal, not a warning. An ambiguous name is left unmatched. And an empty publish over a file that already carries rows is refused unless `--allow-empty` says it is meant, the rule `scripts/build_pint_index_snapshot.mjs` already takes. `--check` validates the PUBLISHED file without writing. Pin: `__tests__/hypedPubsIngest.test.ts`.

<a id="the-pint-index-publishes-what-drinkers-confirmed-and-the-producer-is-a-script"></a>

- **The Pint Index PUBLISHES what drinkers confirmed, and the producer is a script.** `lib/pintIndexFromConfirmations.ts` builds the live snapshot from confirmed Pint Drops and `npm run build:pint-index-snapshot` writes `public/data/pint_index_snapshot.json`, which was hand-written and empty because nothing produced it. `lib/pintIndex.ts` admission is UNCHANGED and is the gate: the script validates and dies rather than write a snapshot the site would refuse. FOUR rules. (1) Only a LIVE confirmation may be cited, through the same `confirmationIsLive` the venue sheet reads, so the pubs the Index dates and the pubs a standing calls Confirmed are one set. (2) An observation is dated to the NIGHT THE PRICE WAS SEEN, never the day it was confirmed. (3) Every drop is counted somewhere: `PINT_INDEX_EXCLUSION_REASONS` gives an unresolvable pub, a point outside every borough and an unpriced row their own reason and count. (4) The script REFUSES rather than publish an empty Index over a real one: no durable store, a failed read, or a confirmed-drop read at `MAX_INDEX_CONFIRMED_DROPS` each stop it, and a read that answered with nothing is honestly `empty`. While that published file stays empty, the freshness registry carries no staleness budget: a 2,160h clock would go red on 14 October 2026, and moving `generatedAt` forward would claim a collection that did not happen. The budget returns, as `user-cadence` and 2,160h, in the same change that publishes the first observation. Missions point at the pubs the Index cannot date: the `undated` field on `VenueMissionRows` is a TIE-BREAK inside a reason and never a promotion over a stronger one, it reaches no DTO, and the route reads it in ONE `listConfirmedVenueIds` call for the whole page. Pins: `__tests__/pintIndexFromConfirmations.test.ts`, `__tests__/priceEvidenceMissions.test.ts`.

<a id="a-slim-rebuild-that-drops-a-shipped-famous-venue-fails"></a>

- **A SLIM REBUILD THAT DROPS A SHIPPED FAMOUS VENUE FAILS.** `scripts/build_slim_index.mjs` keeps a famous seed row only while `isCurrentFamousVenue` (`scripts/lib/currentFamousVenue.mjs`) says its verification window is open and it has a price anchor, and it stamps the slim payload with that same clock. `npm run build:slim`, which `build`, CI and the events refresh run, rebuilds at the committed `public/data/venues_slim.json` `generatedAt` and never reads the wall clock, so a calendar day alone cannot fail a build or a deploy. Only `npm run refresh:slim` moves the clock: run it after the seed is re-verified or a famous seed row is added, and commit the slim it writes. A `build:slim` that finds a seed row observed after the committed stamp fails and names that next step, rather than withholding the row. A refresh whose clock would omit a venue the last slim shipped, or keep none from a non-empty seed, throws before any write. Rows already lapsed at the last stamp stay out and do not fail the rebuild. A seed row whose price anchor a curator removed is withheld on purpose, so it leaves the slim without failing the rebuild. To retire a venue on purpose, delete its row from the seed and add its id to `data/famous_venues/removed.json` in the same change: a listed id may leave the slim, every other shipped id is still guarded, and the list never excuses a row that is still in the seed but has lapsed. Pin: `__tests__/famousVenuesSeed.test.ts`.

<a id="the-historic-directory-publishes-through-three-gates-and-each-one-refuses-rather"></a>

- **THE HISTORIC DIRECTORY PUBLISHES THROUGH THREE GATES, AND EACH ONE REFUSES RATHER THAN REWRITES.** Captain's audit 2026-09-05 (F05, F06, F07), over three cards that each told a stranger something untrue. `public/data/heritage_cache.json` is the source of truth and `scripts/build_historic_index.mjs` is the ONE generator; every gate runs there on the way in AND again in `scripts/validate-data.mjs` over the artifact that ships, so a hand-edited file cannot walk around the generator. A refused fact is QUARANTINED and named in the build report, never edited, so it is fixed at the cache by a person; a record with nothing publishable left is withheld WHOLE, because no pub beats the wrong pub. (1) WHO THE WORDS WERE WRITTEN FOR: `lib/heritageLanguageGate.mjs` is a closed rule table, one rule per class with the reason it refuses, over every string a reader sees. The Queens Arms published "a useful Victorian reference stop for the seeded heritage route". `lib/curation.ts` carries the same texts and is swept too. (2) WHICH PUB THE WORDS ARE ABOUT: facts are keyed by pub NAME and London has several of nearly every name, so one key collects facts about several pubs and the join hangs them all on whichever venue came first. `lib/heritagePlaceConflict.mjs` refuses a fact naming a borough other than the joined venue's, reading the sentence and the place a wiki reference disambiguates itself by; the venue row is the geographic authority, because the card's coordinates, map link and borough all come from it. It catches a STATED contradiction alone, which is what makes it safe unreviewed. `lib/londonBoroughNames.mjs` holds the 33 names once, for the app and the plain-node scripts alike. (3) WHAT THE DATE IS A DATE OF: `lib/heritageDate.mjs` types a date as value + precision + type over a closed set, reading the cue from the CLAUSE holding the year and letting the NEAREST cue speak. Only `founding`, `first_mention` and `construction` are age evidence, and `era` (the field every oldest-first ordering and age filter reads) carries a value only for those, so The Captain Kidd's 1701, the year the pirate it is named after was hanged, orders nothing. Unknown stays unknown. Every stated date prints through `dateLabel`, which names its type, so no year on a card stands bare. ONE GOTCHA: `scripts/build_slim_index.mjs` keeps its OWN `CURATED_VENUES` mirror of `lib/curation.ts`, so editing one without the other desyncs the slim index's own `hasStory` hint from the runtime heritage filter; `__tests__/venuesSlim.test.ts` holds them to each other. Pins: `__tests__/heritageLanguageGate.test.ts`, `__tests__/heritagePlaceConflict.test.ts`, `__tests__/heritageDate.test.ts`, `__tests__/historicIndex.test.ts`; proof `docs/proof/heritage-data/`.
