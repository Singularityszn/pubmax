# Auth and account routes

Moved from [`app/AGENTS.md`](../../app/AGENTS.md). Authoritative policy detail lives here; the area index stays short.

<a id="a-moderator-door-refuses-the-document-and-login-names-nobody-until-the-session-a"></a>

- **A moderator door refuses the DOCUMENT, and /login names nobody until the session answers.** (1) `GET /admin` is gated before the console mounts: `app/admin/page.tsx` hands `headers()` to `canOpenAdminDocument` (`lib/adminAuth.ts`) and calls `unauthorized()`, so an anonymous request gets a 401 whose body is the token form alone. That gate reads the SAME credential as the API gate (`isModerator`), both doors spend ONE session module (`lib/adminSessionClient.ts`), and `readAdminSessionState` answers three ways so a browser that REFUSED the cookie reads apart from a read we could not run. The cookie is `SameSite=Lax`, not Strict, because the navigation to `/admin` has to carry it. The 401 body is not a dead end, and a console notice carries its own tone (`lib/adminNotice.ts`) rather than being classified by matching its own copy. (2) `/login` may NOT say "Welcome back" to somebody it has never met: `lib/loginPageFraming.ts` owns the head copy and holds the first-time line while a hinted session is still resolving, with `aria-busy` on the SHAPE and the screen-reader line OUTSIDE it. The same leaf owns the session hint (`loginPageHasSessionHint`): the HttpOnly resume cookie or a provider callback landing, read by `app/login/page.tsx`, or a Supabase session key in localStorage, read only on a client-side mount so a hydrated email door is never swapped for a skeleton. A hint holds the skeleton until the session answers, so a signed-in reader never sees the form flash; a reader with no hint gets the email door and its settled head in the first HTML, and the social provider slot sits below the field, reserved while the provider read is in flight, so the field never moves. `/sign-in` is a 308 to `/login` in `proxy.ts`; `/signin` stays. Pins: `__tests__/adminDocumentGuard.test.ts`, `__tests__/adminSessionClient.test.ts`, `__tests__/adminSessionRoute.test.ts`, `__tests__/loginPageFraming.test.ts`, `__tests__/loginPage.test.ts`, `__tests__/loginSkeletonAnnouncement.test.ts`, `e2e/admin-document-guard.spec.ts`.

<a id="dedicated-login-alias-signin-owns-the-email-link-flow-as-a-first-class-page"></a>

- **Dedicated `/login` (alias `/signin`) owns the email-link flow as a first-class page.** Phone nav Sign in navigates there; desktop may keep the header popover. The browser session lives in evictable localStorage, so a durable HttpOnly resume cookie mirrors the refresh token (`lib/authSessionResume.ts`, route `/api/auth/session`, client seam `lib/authSessionResumeClient.ts`), and sign-out is the only place that deletes it. Under `next dev` only, a non-supabase.co `NEXT_PUBLIC_SUPABASE_URL` origin is admitted into CSP `connect-src` (`proxy.ts`); production never widens. Malformed resume-cookie data reads as absent at every decode boundary, and `authResumeCookieFromHeader` guards its own `decodeURIComponent` because `verifySupabaseSessionFromRequest` calls it before its verification `try`. Pins: `__tests__/authSessionRoute.test.ts`, `__tests__/authSessionResume.test.ts`. Do not touch `components/auth/AuthProvider.tsx` token-fragment paths without coordinating the auth-hardening lane.

<a id="a-password-is-created-behind-a-session-and-only-ever-spent-without-one"></a>

- **A password is CREATED behind a session and only ever SPENT without one.** Setting one is `supabase.auth.updateUser({ password })` from a signed-in browser (`components/auth/SetAccountPassword.tsx`, mounted in `PubmaxxAccountHub`): no route of ours is in the path, and a form that could set a password for a NAMED HANDLE with no session is account takeover however it is worded. `lib/passwordPolicy.ts` is the ONE module that says what a password must be and the WORDS for it, shared by the hint, the live ticks (`components/auth/PasswordPolicyHint.tsx`, shown BEFORE anybody types) and the refusal. CREATION and SIGN-IN are two questions: `/api/auth/handle-password` applies the length floor alone, resolves handle to account through `normalizeHandle`, and answers ONE 401 shape for an unknown handle, a wrong password, a too-short password and a banned account alike, with the way out riding under EVERY failure, never conditionally. GoTrue reports `user_banned` before it checks the password, so this route answers that the same way it answers a wrong password and does not say the account is banned (`lib/handlePasswordSignIn.ts`). The community-guidelines notice is shown only after the auth server confirms a ban on a session. Whether an account HAS a password is TRI-STATE, and `public.account_has_password` (migration `0099` + rollback; service-role EXECUTE only, or it is an oracle) answers it through `/api/identity/handle/current`. HAS means its OWNER set one: GoTrue writes a random hash when an email-link sign-up creates the account, so a non-empty hash alone answered true and the hub asked those accounts for a current password they never had. Migration `0173` + rollback records the set in the private `account_password_set` table from a trigger on GoTrue's users table that fires only when an UPDATE changes the hash, and backfills it with every account that holds a hash when it is applied, so no existing account loses "Change password" and the rule covers only sign-ups after the apply (an earlier email-link sign-up still needs the current password or a recovery link); no route of ours writes it. Pins: `__tests__/passwordPolicy.test.ts`, `__tests__/passwordPolicyHint.test.ts`, `__tests__/setAccountPassword.test.ts`, `__tests__/handlePasswordSignIn.test.ts`, `__tests__/handlePasswordRoute.test.ts`, `__tests__/accountHasPasswordMigration.test.ts`, `__tests__/accountHasPasswordEffective.test.ts`, `e2e/account-password.spec.ts`.

<a id="an-account-leaves-in-two-phases-the-storage-api-owns-the-bytes-the-trigger-owns-"></a>

- **AN ACCOUNT LEAVES IN TWO PHASES: THE STORAGE API OWNS THE BYTES, THE TRIGGER OWNS THE ROWS.** Contribution battle test D01 (5 Sep 2026): `DELETE /api/account` answered 503 for EVERY account, because the `0078` tombstone trigger deleted from the storage objects table directly and Supabase refuses that at the STATEMENT level (`protect_objects_delete`, SQLSTATE 42501) whether or not a row matches; behind it the Social account's binding to the auth user (`0071`) was `on delete restrict`. Migration `0145` + rollback takes every storage delete out of the trigger, moves the binding to `on delete set null`, and SUSPENDS and unbinds the Social account row rather than deleting it, because the Crew tables reference it with restrict. `deleteOwnAccount` (`lib/accountDeletion.server.ts`) is THREE PHASES and the order is the rule: it COLLECTS every object key while the wall photo rows and message columns that name them still exist, DELETES the auth row, and only then REMOVES the bytes through the Storage API. `lib/accountOwnedObjects.ts` is the ONE table of what an account owns (the avatar and cover folders, the owner's Moment folder, wall and message photo keys with their staging twins), and `lib/nightMomentMedia.ts` reads its prefix from there, because D09 was the upload path and the tombstone naming two different sets. A FAILURE BEFORE THE AUTH ROW GOES REMOVES NOTHING (review finding F-5, which REVERSES the order `0145`'s own header describes): the first cut removed the bytes first, so an auth failure answered "Your account could not be deleted. Try again." over a LIVE account whose every photo was already gone and whose wall photos stayed on public walls as broken images. The keys must be READ before the trigger clears the rows that name them, and reading is its own phase; that was never an argument for removing first. The cost of the new order is ORPHANED BYTES when a removal fails after the account is gone: they are logged as `account.delete_objects_orphaned`, no surface can serve one (the rows that named them are gone), the outcome stays the auth row's rather than a 503 over a deleted account, and a retry still removes everything the folder walk lists by PREFIX. A MESSAGE PHOTO IS ASKED FOR BY PROFILE AND BY HANDLE (F-4): `messages.sender_handle` is text stamped at send time and the rename path never rewrites it, so a handle-only join left every photo an account sent under an older handle in the bucket and fetchable; migration `0151` + rollback adds `messages.sender_profile_id`, backfills it through `profile_handle_aliases`, stamps it on INSERT from a database trigger (never from the send path, which knows only the handle and would pay a round trip on the hottest write), and the tombstone trigger asks BOTH identities, the handle half kept for a row the backfill could not resolve and safe because a retired handle is never re-issued. The store drops to the handle alone on a PostgREST 42703, which is the pre-0151 behaviour rather than a refused deletion. A second DELETE is 410 Gone carrying `deleted: true`. Never put a SQL delete of storage objects back in a trigger: Supabase's own guide says a row deleted by SQL leaves its bytes orphaned. The fixture cluster carries no such guard, which is how the hole stayed green, so `__tests__/accountRemovalMigrationEffective.test.ts` installs a replica and proves 42501 before `0145` and success after. The portable copy is the door beside it: `GET /api/account/export` (`lib/accountExport.ts` owns the document and the words, `lib/accountExport.server.ts` reads through the stores that own each lane) answers the verified bearer's own profile fields, private card, Memories, Moments, prices, Pint Drops, visit reports, crowd reports, Social posts, wall photos, cover rotation, saved pubs, Wanted list, linked socials, check-ins, follow list, Night Profile and sent messages, and REFUSES the whole file when a lane could not be read rather than hand over a partial one as complete. A profile read that threw marks the profile lane and every profile- or handle-keyed lane unavailable, never empty. EVERY OWNER-KEYED STORE IS A LANE OR A NAMED EXCLUSION: the first cut shipped four lanes and left ten kinds of the person's own data out of a file the surface calls "your data", so `__tests__/accountExport.test.ts` walks every `lib/*Store*.ts` module and fails on one that is neither exported nor argued about in a sentence, with a SHRINK-ONLY named-gap list for content that is the person's and still has no owner-keyed read. A linked social is exported through `publicSocialConnection`, never the stored row, because that row holds the OAuth ciphertext. Pins: `__tests__/accountDeletionStore.test.ts`, `__tests__/accountOwnedObjects.test.ts`, `__tests__/accountDeletionRoute.test.ts`, `__tests__/accountExport.test.ts`, `__tests__/accountExportRoute.test.ts`, `__tests__/accountSurfaceStoreDoors.test.tsx`, `e2e/account-store-doors.spec.ts`; proof `docs/proof/account-deletion-real/`.

<a id="a-private-night-can-be-taken-back-and-only-its-owner-takes-it"></a>

- **A PRIVATE NIGHT CAN BE TAKEN BACK, AND ONLY ITS OWNER TAKES IT.** The contribution battle test of 5 September 2026 (D06) found no removal door anywhere under `app/api/night-*`: a Memory, a Moment and their photos could only ever accumulate, and consent withdrawal after publication was the one reduction that existed. `DELETE /api/night-memories/[id]` and `DELETE /api/night-moments/[id]` are those doors, and `removeNightMemory` / `removeNightMoment` (`lib/nightMemoryStore.ts`, riding `selectStore` because that module's inline-branch count may only shrink) are the policy. FOUR rules. (1) OWNERSHIP IS CHECKED AT THE TABLE: the delete statement carries the owner id, so a row that is not the caller's is never matched, and somebody else's Memory answers the SAME 404 an unknown id answers. (2) A published Story keeps the path it has: a Memory it stands on, and a Moment inside it, are 409s that name consent withdrawal, and a Memory holding a CONTRIBUTOR's Moment is refused too, because the `on delete cascade` from migration 0028 would take their Moment with it. (3) THE BYTES LEAVE WITH THE ROWS: the store answers with the storage keys it removed and the ROUTE deletes them through `removeNightMomentPhoto`, the split the Moment POST already uses for the upload. A key is signed or deleted only when `nightMomentKeyBelongsToOwner` says it sits under that owner's Moment prefix. JSON cannot name a key. The multipart branch sets it from the upload alone. (4) In the studio the shelf lists each Memory and the held Memory's Moments, and Remove is TWO BEATS, an inline confirm rather than a dialog. Pins: `__tests__/nightMemoryRemoval.test.ts` (owner, other account, anonymous, both refusals), `__tests__/nightMomentObjectKey.test.ts` (a JSON key is dropped; a foreign key is not signed and not deleted), `e2e/night-memory-removal.spec.ts`.
