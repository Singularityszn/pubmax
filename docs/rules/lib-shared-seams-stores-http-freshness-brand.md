<a id="the-nightly-enrichment-cron-is-safe-to-fail-and-safe-to-retry-and-its-cursor-is-"></a>

- **THE NIGHTLY ENRICHMENT CRON IS SAFE TO FAIL AND SAFE TO RETRY, AND ITS CURSOR IS AN ADVANCEMENT.** Production answered 502 at 03:15:13 on 2026-09-05 when one Exa search hit its 12,000 ms request deadline during Birmingham enrichment. The run had NO durable state: `startIndexForCity` derived the start index from the calendar day, and the `nextIndex 102` in the progress record was the index of the venue that had just FAILED, reported unadvanced and read back by nothing. So the failed venue was neither retried nor recorded, the other nine queries of the night went unspent, and one venue's timeout was the whole city's night. `lib/cityEnrichmentCheckpoint.ts` is the policy and it is a pure leaf: the cursor only ever advances past a venue whose outcome was RECORDED, and a venue whose search failed is recorded in `deferred`, keyed by OSM id because an index names a different pub after every pack rebuild. FIVE numbers, all in that module: `MAX_VENUE_ATTEMPTS` 3 is every query a venue may ever cost before it is TERMINAL, `VENUE_RETRY_BACKOFF_MS` is the backoff per attempt, `RETRY_QUERY_BUDGET` 4 of the run's 10 keeps a poisoned retry queue from starving fresh coverage, `CONSECUTIVE_VENUE_FAILURE_LIMIT` 3 calls a provider outage rather than burning an attempt on every pub it touches, and `CITY_ENRICHMENT_LEASE_MS` 150,000 outlives the 120 s function so a crashed run blocks nothing for long. THREE rules ride with it. (1) A FAILURE ABOUT US IS NOT A FAILURE ABOUT THE PUB: `runLevelFailure` keeps an exhausted gateway budget and an abort off a venue's attempts, and `runCityEnrichment`'s new `onVenueError` seam (default `abort`, and the London nightly CLI pass opts into `continue`) records the failed outcome BEFORE it decides, or the venue that ends a run is a venue nobody hears about again. (2) THE LEASE IS ONE WRITE AND THE COMMIT IS GUARDED ON IT (`lib/cityEnrichmentCheckpointStore.server.ts`, migration `0142` + rollback): the claim is a conditional UPDATE matching only a null or expired lease, and a commit carries `lease_owner = ours`, so a run whose lease expired mid-flight cannot overwrite the run that took over. A checkpoint read we could not run SKIPS the night rather than spending without one. (3) THE CRON PUBLISHES NOTHING, and says so as `published: 0`: every price and page it finds goes to the function log, the reviewed price lanes are untouched, and the checkpoint table carries no price, drink or observation column. `GET /api/admin/city-enrichment` is where a partial run is inspectable and `POST { action: "requeue", city }` is the retry path a terminal refusal is recorded with. RECORDING A DEFERRAL IS HALF A PROMISE, AND THE OTHER HALF IS THAT THE QUEUE IS REAL AND DRAINS (Astra F04, 6 Sep 2026, a second 502 with three Edinburgh venues deferred and recovery unproven). FOUR rules were added. (1) DURABILITY IS OBSERVED FROM THE WRITE, NEVER INFERRED FROM THE KEY: the old claim was `isSupabaseConfigured()`, which says nothing about whether `0142` was applied, so a deployment with keys and no table wrote every deferral to the memory fallback and reported `checkpointDurable: true` over a queue that dies with the function instance. `CheckpointRead` now carries where a read came from, the commit's own answer rides the run outcome, and the pair (`durable` observed, `expectedDurable` configured) DISAGREEING is the alarm. `checkpointDurable` is TRI-STATE, because a night where every city declined to spend wrote nothing and that is not memory. (2) THE PER-PROVIDER BUDGET BINDS THE PROVIDER THAT SERVES AN OUTAGE: `TavilyProvider` took `maxCalls`, counted against it and never applied it, so the ceiling bounded only the primary on exactly the nights every query fell through to the fallback. (3) A FAILURE ABOUT US IS CHARGED TO NOBODY: the core records a `failed` outcome BEFORE `onVenueError` decides, so an exhausted budget spent the boundary venue's attempts for a search nobody put; `onUnaskedVenue` names those venues and the checkpoint charges them nothing and does not pass them. (4) THE QUEUE AGE IS THE METRIC A DEFERRAL COUNT DOES NOT GIVE YOU: "three deferred" reads the same whether the queue drains nightly or has been stuck since the first outage, so `deferredQueueAgeMs` measures from the FIRST failure (a venue re-failed nightly never looks new), answers null for an empty queue rather than zero, and `DEFERRED_QUEUE_AGE_ALERT_MS` 72 hours is three nights of the 30 min / 6 h / 24 h ladder. Backoff also takes up to `VENUE_RETRY_JITTER_RATIO` 25% OFF each step, derived from the venue's own id, because every venue one failed batch defers is stamped at the same instant and shared one retry time to the millisecond; it only ever makes a retry EARLIER. A terminal refusal is logged on BOTH exits, since the night a venue is refused for the third time is very often a night the whole run refuses. Pins: `__tests__/cityEnrichmentCheckpoint.test.ts`, `__tests__/cityEnrichmentResilience.test.ts` (five injected faults, every provider stubbed), `__tests__/cityEnrichmentQueueRecovery.test.ts` (the lifecycle: a deferred venue publishes once or reaches a visible terminal state), `__tests__/cityEnrichmentDurabilityAlert.test.ts`, `__tests__/cityEnrichmentAdminRoute.test.ts`, `__tests__/cityEnrichmentProgressMigration.test.ts`. Operator path: `docs/CRON_PLANE_RUNBOOK.md` "City enrichment: the retry queue".

<a id="context-dev-is-a-fetch-layer-never-a-permission-and-one-wrapper-owns-every-call"></a>

- **Context.dev is a FETCH LAYER, NEVER A PERMISSION, and one wrapper owns every call.** `CONTEXT_DEV_API_KEY` is server-only and has no `NEXT_PUBLIC_` prefix by design; `.env.example` says what reads it. `lib/contextDev.ts` is the implementation, and there is no app door: nothing in `app/` imports it. It carries no `server-only` marker so a plain-node CLI can import it, which is also why every specifier inside the lane is RELATIVE with its extension. If an app caller appears, `__tests__/serverOnlyGuard.test.ts` is where to demand the door. The official context.dev SDK (npm, pinned exact) is the TRANSPORT, so endpoint paths, parameter names and response shapes come from the vendor; the wrapper owns what the SDK cannot know. FOUR rules. (1) THE GATE. Every URL-taking call asks `isHarvestableOperatorUrl` (`lib/harvest/sourcePolicy.ts`) first, and a refused host is refused whatever a caller passes. A host the table already records a permission for (`hasRecordedHarvestPermission`, derived from allowed rows alone, so a row refused for `publishes-no-web-price` inherits nothing) needs no second question; EVERY other host must arrive with the live `RobotsChecker` from `lib/harvest/robots.ts` or the call is `ROBOTS_UNCHECKED` and unsent. Both halves run BEFORE a credit is spent, `searchWeb` applies the same fence to what comes BACK, and `batchSubmit` refuses the WHOLE list when one URL is refused rather than dropping pages a caller thinks it submitted. (2) THE RETRY POLICY IS OURS ALONE: the SDK client is built with `maxRetries: 0`, because its own retries would spend budget nothing counted and wait past `CONTEXT_DEV_MAX_RETRY_AFTER_MS`. `Retry-After` is honoured on 429, 408 and 5xx take bounded backoff, a validation answer is never retried, and a 2xx carrying no useful body is `EMPTY_BODY` and never retried either. (3) SPEND IS BOUNDED: one `createContextDevBudget()` per run counts REQUESTS including retries, and the pinned SDK catalog distinguishes a one-credit scrape or URL map from JSON extraction, which adds four credits when it succeeds. `extract` forces `maxAgeMs: 0` and requests JSON and Markdown in one fresh scrape, returning that page as its only analyzed URL; a response marked `isPartial: true`, or a JSON answer without same-scrape Markdown or the final URL, fails with `EMPTY_BODY` without retry. The events lane publishes a row only when its title, venue, date and stated time appear together in one supported Markdown event record: a single line, a level 2-6 heading card explicitly naming the extracted event title, or a list item with indented continuation lines. Ordinary section headings never join following lines into an event card. Blank lines may continue a title heading card or indented list item; another heading, list item, or semicolon starts a separate record. A record stating conflicting calendar dates fails closed; repeated references to the same day are allowed. The extracted year must appear in the date evidence. Date-only output is rejected when the record states a clock. Timed output needs one explicit start or one unlabelled clock without a doors time; end clocks never qualify. Stated GMT, UTC, BST and numeric offsets take precedence over London local time; unsupported explicit zones are rejected. Unstructured multiline prose and ambiguous cross-record captures are not grounded. Prices need complete monetary tokens labelled as tickets, entry, admission or price. Source ids need an explicit `event id` or `source id` label; a venue ID does not qualify. Unsupported optional facts are discarded. Source credit uses the registered page; a final URL or supplied event URL with credentials or a different protocol or host rejects the capture or row. A rejected event makes the source replacement incomplete, preserving its held rows and timestamps. The removed extraction arguments `factCheck` and `maxPages` have no v3 equivalent. Other fetch calls accept `maxAgeMs` when freshness is part of the claim the answer carries. (4) NO KEY IS NOT AN ERROR: every call answers `{ status: "not-configured" }` and sends nothing. Endpoints: `scrapeMarkdown`, `scrapeHtml`, `sitemapUrls`, `crawlMarkdown`, `extract`, `searchWeb`, `brandRetrieve`, `batchSubmit`. Lanes: the events refresh (`lib/events/contextDevProvider.ts`) and, behind `PUBMAX_UK_PRICES_CONTEXT_DEV=1` plus a key, the UK price reader `scripts/harvest/uk-prices/context-dev.mjs`, which hands its Markdown to the SAME `lib/harvest/ukPriceCrawl.ts` rules the served and rendered lanes use and answers in render.mjs's outcome vocabulary. Docs at https://docs.context.dev, which serves Markdown for any page given a .md suffix. Tests mock the transport through `fetchImpl`; `__tests__/contextDevLiveProof.test.ts` is the one live call and it SKIPS without a key. Pins: `__tests__/contextDev.server.test.ts`, `__tests__/contextDevGate.test.ts`, `__tests__/contextDevPriceLane.test.ts`, `__tests__/contextDevProvider.test.ts`, `__tests__/contextDevEventsRefresh.test.ts`.

<a id="stale-and-cannot-tell-are-two-findings-and-an-alert-may-never-merge-them"></a>

- **"Stale" and "cannot tell" are two findings, and an alert may never merge them.** The freshness spine (`lib/freshness.ts`) reports a feed whose DATA is over budget separately from one whose age it could not measure, and `resolveStamp` gives every failure mode its own sentence naming the artifact. `lib/freshnessNotify.ts` logs them as two groups and the cron answers `stale` and `unresolved` separately. Never let an unmeasurable feed read as fresh, and never let it count as stale either: merging them is how eleven blind spots hid two real breaches for weeks. A failed refresh is not an observation: `app/api/cron/refresh-whats-on/route.ts` refreshes bounded lanes plus configured Ticketmaster and Skiddle rows into `whats_on_listings` (migration `0119`), leaves failed lanes unchanged, and never stamps combined `feed_freshness`; `ok:false`, `stamped:false` and `observedAt:null` name a failed configured lane, while an unconfigured official lane does not block bounded refreshes. Readers prefer that store and fall back to bundled `public/data/whats_on` files (`preferDurableWhatsOn`); expired rows never serve. A THIRD finding sits inside the budget and is a NAMING question, never an alarm: past `SNAPSHOT_AFTER_DAYS` (30) a POINT-IN-TIME feed is named a `snapshot` rather than called fresh, and `classNamesSnapshots` is the one predicate that says which classes those are. It covers `episodic` and `user-cadence`, because a hand-collected bundle and a feed that grows only as drinkers arrive both describe their last observation rather than tonight; a `cron` or `live` feed is refreshed FOR us, so an old one stays a budget question. It renames only what would have read "fresh", so no budget moves and `hasBreach` stays false. A FOURTH state is a lane that is CLOSED rather than late: a dataset declared `class: "snapshot"` with `stalenessBudgetHours: null` reports `snapshot` from the moment it is dated, because nothing may lawfully advance it and its collection day is the whole claim. The BUDGET carries that declaration, not the class alone, so a snapshot-class lane that keeps a budget (`area_news`) can still be re-collected and keeps its stale finding. Captain ruling 2026-09-05 over `drink_price_updates`, whose only permitted source (Wetherspoons) publishes no per-drink web prices: a budget there was a promise nobody could keep and it reported stale for ageing exactly as designed. `untracked` therefore keeps its own meaning, "nothing was dated", and never swallows a date a reader needs. The WORDS are owned once, by `SNAPSHOT_CAPTION_PREFIX` / `formatSnapshotFrom` in `lib/dataFreshness.ts`, which `formatPintDatasetSnapshot()` and the venue Drinks row caption both read, so a closed lane never grows a second vocabulary or a staleness warning about doing what it was ruled to do. `scripts/check_freshness.mjs` mirrors the same rules dependency-free, this one included. GitHub events-refresh workflows stay in the tree for when Actions billing returns. Pins: `__tests__/freshness.test.ts`, `__tests__/whatsOnListings.test.ts`, `__tests__/whatsOnListingStore.test.ts`, `__tests__/whatsOnListingsServer.test.ts`, `__tests__/whatsOnRefresh.test.ts`, `__tests__/cronRefreshWhatsOnRoute.test.ts`, `__tests__/whatsOnListingsMigration.test.ts`.

The module comment beside it claimed the address was a SECONDARY signal paired with an account, which was true of the write routes and false of exactly the four where money leaves. TWO halves, and the second is the load-bearing one. (1) `lib/clientIpTrust.ts` is the whole trust boundary and a pure leaf importing nothing: a platform header first (`x-vercel-forwarded-for`, then `x-real-ip`), and only then the RIGHT-MOST `x-forwarded-for` entry, which is what the hop nearest us appended rather than what the caller wrote. A candidate must be address SHAPED, so `unknown` (a legal header value) can never become a bucket of its own. `clientIp` in `lib/supabase.ts` is the caller for every route that already reaches Supabase, and the `/ingest` proxy (`app/ingest/[...path]/route.ts`) calls `resolveClientIp` directly so a telemetry request traces no Supabase client into its bundle; a source fence keeps the `split(",")[0]` reading out of the tree. That choice is what caps the ceilings in the low thousands, because the older shape stores one timestamp array per key; a lane that ever needs a six-figure ceiling is the day to add the counter. <a id="a-response-you-decide-not-to-read-is-a-request-that-never-finishes"></a>

- **A response you decide not to read is a request that never finishes.** A Next route handler answers `Transfer-Encoding: chunked` with no `Content-Length`, so Chromium cannot know the body ended until somebody drains it: `if (!res.ok) return;` leaves the stream open, the request never reaches `requestfinished`, and every Playwright `waitForLoadState("networkidle")` on that page spends its whole budget while every unit test stays green. `discardBody` (`lib/responseBody.ts`) is the one way to say you are done, and the rule is one sentence: BETWEEN learning a response's status and reading its body, every exit lets the body go. `__tests__/unreadResponseBody.test.ts` sweeps the browser-reachable modules and its header names the two shapes it deliberately does not catch.

<a id="a-message-is-one-request-and-the-other-side-hears-it-on-a-broadcast"></a>

- **A MESSAGE IS ONE REQUEST, AND THE OTHER SIDE HEARS IT ON A BROADCAST.** Captain 2026-09-05 ("the messaging is slow"): measured on a local production build against a local Supabase stack, a sent bubble took two round trips to appear (POST, then a full GET with the composer disabled), the other side saw it up to ten seconds later, and every open thread polled every ten seconds whether anyone was looking. The `messages` table is RLS deny-all and is NOT in the realtime publication (0019), so the old `postgres_changes` channel joined and heard nothing; the thread lived on its poll. FIVE rules. (1) DELIVERY IS A SERVER BROADCAST, NEVER A ROW READ: `lib/messagesBroadcast.server.ts` posts a payload-free signal to Realtime's HTTP endpoint on the topics `lib/messagesTopics.ts` names (thread, and each participant's inbox), after the row is stored, never as a reason to fail the send, and never on the response's critical path (`deferMessagesSignal`, which claims the promise then hands it to `after`); `lib/messagesRealtime.ts` listens on `broadcast` events, owns EVERY poll timer (fallback cadence without a socket, a slow safety poll with one, none while the tab is hidden, one refetch the moment it is shown), and awaits the lazy client so a cold open upgrades to realtime instead of polling for the life of the page. Signals trigger participant-gated reads; no content crosses the socket. `MessagesInboxClient` coalesces ordinary initial, focus, realtime and poll refreshes while a read is pending, so a slow response can still publish. Successful conversation creation supersedes that read immediately; account changes, hidden panes and unmounts retire its result. (2) A SEND IS ONE REQUEST: the outbox bubble (#1498) is already on screen, and the POST's own answer is the stored row that replaces it, so nothing is refetched to show your own message; a body with no row falls back to the gated refetch. (3) A READ IS A READ: `listMessages` writes nothing, `markRead` is asked by the thread route alone and only when something unread was received, and a count above zero broadcasts `read` to refresh the sender's receipt state. (4) THE INBOX IS TWO BATCHED READS, not one per conversation: an unread scan and a newest-first window over every conversation id (`INBOX_LAST_MESSAGE_WINDOW`), with a per-conversation fallback only when either window filled; migration `0143` + rollback (a partial index on unread rows) is a speed migration nothing depends on. Batching moved the BLAST RADIUS, so `listConversations` answers an `InboxRead`, never a bare list: ONLY the conversation-rows read may empty the inbox, each batched read is caught where it happens, a cap is a WINDOW rather than a filter (the unread scan is ORDERED, and every count the filled scan could have cut short is re-asked on its own), `ConversationDTO.unread` is ABSENT rather than 0 when it could not be counted, and the body carries `status: "degraded"` which `MessagesInboxClient` words apart from a read that did not answer at all. (5) THE BEARER IS VERIFIED ONCE PER REQUEST: `verifyCallerAuth` asks GoTrue (the `localOnly` JWKS lane is `DELETE /api/account`'s alone, see `docs/rules/app-api-contract-and-rate-limits.md`) and shares that one verification, a failure included, with every default-lane caller on the same `Request` object, so `callerUserId`, `callerAuthIdentity`, `resolveMessageHandle` and `gateHandleAction` cost one GoTrue round trip between them; the messaging routes still hand the verified user id to `gateHandleAction`.
