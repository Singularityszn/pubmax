# Saves, nudges, rounds, reports and Pub Pal

Moved from [`lib/AGENTS.md`](../../lib/AGENTS.md). Authoritative policy detail lives here; the area index stays short.

<a id="a-visit-report-is-an-account-of-one-visit-never-a-venue-rating"></a>

- **A Visit Report is an account of one visit, never a venue rating.** `lib/visitReports.ts` owns the dated account and the closed observations; `components/visits/VisitReportPanel.tsx` is the shared reader and composer. Public reads carry `ready` or `degraded`, because a failed lookup may never read as no visits, and `/api/visit-reports?contributor=<handle>` is the leaderboard count seam. A row prints the VISIT date and nothing else, so the lane sorts on `visitedAt` with `createdAt` as the tie-break, and `resolveVisitedAt` owns the age ceiling and the no-future rule with the composer's `min`/`max` mirroring them. Reader flags only queue a row, only a moderator hides it, hiding never deletes its provenance, and a hidden row keeps its own moderator lane (`GET ?status=hidden`). Pins: `__tests__/visitReportsRoute.test.ts`, `__tests__/visitReportsStore.test.ts`, `e2e/visit-reports.spec.ts`.

<a id="a-crowd-occupancy-report-is-a-now-reading-about-seats-never-a-remembered-night"></a>

- **A crowd occupancy report is a NOW reading about seats, never a remembered night.** `lib/occupancy.ts` owns the three buttons, the now and retake windows and the explicit map onto Visit Report busyness, so the two tenses cannot invent a fourth word. Trust is derived on READ: only reports inside the now window may answer now, older rows stay for the forecast and never paint a now surface, and the printed reporter figure counts DISTINCT accounts, never rows. Writes are signed-in only, idempotent per account per pub per retake window, and land in `venue_occupancy_reports` (migration `0107` + rollback) through `lib/occupancyStore.ts`. RLS grants the browser nothing, and GET/POST `/api/venues/[id]/occupancy` is the only seam: GET is public and fail-soft (`degraded`, never "no reports") through `resolveCanonicalVenueId`, POST is `callerUserId` plus `isLimited` through `resolveWritableVenueId` (`lib/venueWriteTarget.server.ts`), the ONE resolver every community write shares with `/api/price-submit`. That route also owns the flag and hide pair (migration `0109` + rollback): reporting never auto-hides, hide never deletes, and `report_count` is a DISTINCT reporter count, so `venue_occupancy_flags.actor_hash` is NOT NULL with an `anonymous` sentinel. Either deploy order is safe, because the store drops to 0107's columns on a PostgREST 42703 rather than 503-ing every tap. The venue sheet is one row (`VenueOccupancyRow` + `useVenueOccupancy`), the sign-in door carries `from=/map?sel=<venueId>`, and a write whose read-back degrades still thanks via `occupancyWriteReceiptLine`. Pub Pal `report_occupancy` proposes, then POSTs here on confirm. Analytics carry no venue id, handle or coordinates. Pins: `__tests__/occupancy*.test.ts`, `e2e/occupancy.spec.ts`.

<a id="a-wanted-is-a-private-place-you-mean-to-try-never-a-scrape-of-instagram-saves"></a>

- **A Wanted is a private place you mean to try, never a scrape of Instagram Saves.** Paste-only capture (`lib/wanted.ts`, store `lib/wantedStore.ts`, resolve `lib/wantedResolve.server.ts` against curated plus national UK base search). The source URL is provenance and is never fetched server-side from Instagram or TikTok. Solo Wanted only in Wave A: no swipe feed, no streaks. Owner-only reads via `/api/wanted`; fulfilment is quiet when presence, check-in or plan arrival lands at the venue. UI: You (`WantedList`), venue sheet (`SaveForNightButton`), plan describe-first (`WantedPlanChips`). Migration `0093` + rollback; firstmate applies. Pins: `__tests__/wanted*.test.ts`, `e2e/wanted-wave-a.spec.ts`.

<a id="step-out-is-one-owed-weekly-push-never-a-streak-or-drink-more-nudge"></a>

- **Step Out is one owed weekly push, never a streak or drink-more nudge.** Opt-in preference default OFF (`lib/stepOutNudgeStore.ts`, You then Notifications via `StepOutNudgePref`), at most one web push per week per subscription (`canSendStepOutNudge`). Delivery reuses VAPID rails (`lib/webPush.ts`, `lib/pushSender.ts`); cron `/api/cron/step-out-nudge` and `npm run push:step-out` follow `scripts/push/sendDailyBrief.mjs`. Payload priority is `lib/stepOutNudgeSelect.server.ts`, and it skips when nothing is owed. Never "haven't been out" copy. iOS opt-in copy names Home Screen install. Migration `0094` + rollback; firstmate applies. Pins: `__tests__/stepOutNudge*.test.ts`, `e2e/step-out-nudge.spec.ts`; runbook `docs/WEB_PUSH.md`.

<a id="a-cheap-pint-ping-is-one-weekday-5pm-ask-never-growth-mail"></a>

- **A cheap-pint ping is one weekday 5pm ask, never growth mail.** Captain 2026-08-19: after the first completed Pint Drop or saved favourite pint, offer ONE lifetime weekday 5pm web push naming a listed `cheapestPrice` (`lib/cheapPintPingSelect.server.ts` over `rankNearMe` and `getPricedVenues()`), never community or invented figures. Policy is `lib/cheapPintPing.ts`; prefs share `step_out_nudge_prefs` (`lib/stepOutNudgeStore.ts`, migration `0111` + rollback; captain applies) with Step Out on the same push token. Prompt once via `CheapPintPingPrompt` and `lib/cheapPintPingPrompt.ts`; decline is durable and there is no follow-up. Cron `/api/cron/cheap-pint-ping`. Pins: `__tests__/cheapPintPing*.test.ts`.

<a id="community-venue-signals-are-observations-never-venue-facts"></a>

- **Community venue signals are observations, never venue facts.** `lib/communityVenueSignals.ts` owns the closed vocabulary, trust states and copy for character, access, door policy and whether people are eating. They travel through the existing `/api/price-submit` and `lib/communityPriceStore.ts` actor, attribution, rate-limit and corroboration seams. Character copy must name drinkers' judgement. Step-free entrance and step-free toilets are separate signals; each stays visibly unknown until corroborated, and a single report may add detail but never turn unknown into confirmed access, at ANY age, because ageing weakens a report and may only ever move it to the supporting line. What a reading surface may branch on is `CommunityVenueSignalTrust` (`unknown` | `reported` | `established`), never the sentence: the collapsed access summary in `components/map/VenueCommunitySignals.tsx` used to compare copy, so a wording change would have promoted a pub nobody had checked. Signals share the price table, so the price scans narrow to `drink_category is not null` (a row cap is a window, not a filter), and they share the price MODERATION path too, with `freshestVenueSignals` as the single filter so a hidden signal leaves the sheet, the corroboration count and the established answer together. Contributor totals are derived on the server from the same observation rows. Pins: `__tests__/communityVenueSignals.test.ts`, `__tests__/venueCommunitySignals.test.ts`, `__tests__/communityPriceModeration.test.ts`.

<a id="a-round-records-spend-never-debt"></a>

- **A Round records spend, never debt.** `lib/rounds.ts` owns immutable buying turns and derives rotation from their payer order. A plain total stays inside the Round diary. Itemised drink lines reach the community-price store only for a signed-in account with a claimed public handle; anonymous lines stay private in the diary. Membership resolves through stable profile ownership, so a handle rename cannot strand a member or retry. Each line persists its promotion state, so dependency failures retry idempotently and only `promoted` lines claim community-price status; the latest line from one account for each venue and drink category owns that key, and earlier same-key lines become `superseded`, stay in the diary and stop claiming live status. Older rows without durable outcome evidence stay neutral as `legacy_unknown`, never relabelled. Promoted lines can affect map price surfaces only through `mergeCommunityPriceSignals`. Never add balances, shares, IOUs, settlement or debt totals to this model. A drink line is a first-party observation, so a known price may only PRE-FILL the composer's drink row, and the remaining gate on what reaches `submitCommunityPrice` is PROVENANCE, never the figure: `RoundSpendItemSource` records whether a line is the drinker's own claim or a figure lifted off the seeded demo menu, and a demo line stays in the diary labelled rather than dropped. Value equality is the wrong fence, because a drinker who really paid what a demo menu quotes is still observing it. Pin: `__tests__/roundsRoute.test.ts`.

<a id="ask-tool-selection-is-regex-when-keyless-and-a-typesafe-choice-when-keyed"></a>

- **Ask tool selection is regex when keyless and a TypeSafe Choice when keyed.** `lib/ask/router.ts` stays the deterministic cascade and the fixture source. Trailing sentence punctuation is stripped before `in` / `near` place extraction so asks like "near Soho?" still resolve the neighbourhood. `lib/ask/routerJudged.ts` asks one Choice over the tool set plus `none`, plus speculative venue, area and `wantsMap` questions in the same 4s `systemOneOutcome` call. Code finds the venue shortlist (`lib/ask/routerCandidates.ts`, cap 12). A timeout or a malformed answer falls back to regex with a drop reason in the TypeSafe timing line, never a 500. Thresholds live in `lib/ask/routerPolicy.ts` and are cited from `__tests__/fixtures/typesafe/ask-router-probabilities.json`. Pins: `__tests__/askRouter.test.ts`, `__tests__/askRouterJudged.test.ts`.

<a id="concierge-intent-is-typesafe-when-keyed-regex-when-not"></a>

- **Concierge intent is TypeSafe when keyed, regex when not.** `lib/concierge/intent.ts` parses a free-text night request. The mood regexes, number-word table, area rule and cheap = £6 in `lib/concierge/intentPolicy.ts` are the keyless fallback. The keyless area (`deterministicAreaInText`) is the first known area named after in, near, around or at, before a night-out noun, or as the whole request, and the lookahead area phrase only when no known area is named that way. With `TYPESAFE_API_KEY`, one System One call (`lib/ai/typesafe.server.ts`, lane `typesafe`) asks a Noul per mood and Choices for area, group size and budget over candidates CODE found in the text. A chosen area still has to appear verbatim in the request (`validateJudgedIntent`). Thresholds are cited from `__tests__/fixtures/typesafe/conciergeIntentProbabilities.json`. What's-on kind detection in `lib/concierge/whatsOn.ts` stays regex. Pins: `__tests__/conciergeIntent.test.ts`.

<a id="pub-pal-answers-in-writing-with-no-keys-and-voice-is-one-optional-grant-it-must-"></a>

- **Pub Pal typed chat answers keylessly; voice is the ElevenLabs grant.** The browser cannot replace the system prompt: grounding stays in the agent base prompt, which holds no `{{dynamic}}` slot because a voice browser starts its own session from the signed URL, and persona reaches voice only as the greeting and the voice id. When ElevenLabs is configured, `/api/pub-pal/chat` requires a signed-in session, which `lib/palChatClient.ts` presents through `authedActionFetch`, and the `pub-pal-chat` spend ceiling. Tool turns carry `owner_id` (migration 0169, which the captain applies), expire two minutes after the user's last line (a tool result never extends that window), and the `/api/cron/purge-pub-pal-turns` cron deletes expired rows every minute. Without `ELEVENLABS_API_KEY` and `ELEVENLABS_PUB_PAL_AGENT_ID`, `POST /api/pub-pal/chat` runs the same grounded `runAsk` tool path as map Ask (`skipModel: true`, no OpenRouter). When both ElevenLabs values are set, typed chat uses the shared agent in text-only mode and voice uses it over WebRTC. Map Ask keeps `/api/ask` with no ElevenLabs keys. The tool allowlist is ADR 0014, widened by the concierge wave with `cheapest_pint_near`, `tonight_now`, `venue_drinks`, `find_desk` and `report_occupancy`. Policy and every word they print is `lib/ask/conciergeTools.ts` (pure), handlers `lib/ask/conciergeTools.server.ts`, and `lib/ask/toolContract.ts` holds the shape so a handler module can be imported BY `lib/ask/tools.ts` without importing it back. FOUR rules. (1) No tool derives a figure: `cheapest_pint_near` is the existing `rankNearMe` and `rankBoroughCheapest` over the listed index and takes a pub or an area, NEVER a viewer point, so nothing crosses the `lib/geo.ts` egress seam. `extractArea` strips trailing time and group qualifiers, and a place-shaped word the pack knows (`isPlaceShapedWord`) may not land on a pub by PREFIX or substring, though an EXACT name still wins. When no borough row matched but the needle names a night area the map pack knows (`nightAreaForMapQuery`), the handler ranks from that area's centre without inventing a viewer anchor. (2) `find_desk` ships holding nothing and says so: it reads only the widened rows through `lib/ask/deskVenues.server.ts`, a second reader of the same city pack that never sees a pub row, and refuses an ask carrying pub or pint wording; a short follow-up routes on the CURRENT ask first (`refineRoutedAskQuery`) and only borrows the prior turn's place. `report_occupancy` is confirm-gated (ADR 0006): the tool proposes, the client POSTs `/api/venues/[id]/occupancy` on confirm, and `occupancyStoreState()` is the one switch that can roll the confirm back to "unbuilt". (3) Every empty line separates "nobody has logged this" from "we could not look". (4) Typed chat (`lib/palElevenLabsChat.server.ts`) is one HTTP turn per ask: initiation clears the agent's configured `first_message`, and an `agent_response` before the user's `user_message` is ignored, because the voice greeting would otherwise become the JSON answer. When the ElevenLabs `conversation_id` arrives, typed chat registers the full ask in `pubPalToolTurnStore` before sending `user_message`, finishes on a settle timer (a reply is the answer once no tool event follows it for 1.2 s, or 0.4 s after `agent_response_complete`), so it never depends on that event and a deploy and an agent re-run are safe in either order. After a tool turn it polls until webhooks append cards, proposals or hints, then reads the turn so `/api/pub-pal/chat` can return `toolsUsed` from the store. A caller that sends `Accept: application/x-ndjson` gets the reply text as `agent_chat_response_part` events arrive (`lib/palChatStream.ts` owns the wire format), a `reset` when what was shown was a checking line, and one `final` event with the JSON path's body; every fence, the sign-in check and the spend ceiling run before the stream opens, and any other caller gets one JSON body. One bounded helper, `lib/palElevenLabsSignedUrl.server.ts`, issues the signed URL for chat and voice alike, and `npm run pubpal:agent -- --check` reads the live agent and tools and exits 1 on drift. A follow-up sends the previous answer's conversation id as `threadId`; the server reads the signed-in owner's own row for it and folds those earlier asks into the `user_message`, never into the system prompt, and never from browser-sent turns. VOICE is env-gated per deployment: `GET /api/pub-pal/voice-token` answers one boolean about configuration and reads no account, so `PubPalVoice` renders TRI-STATE and shows one honest line plus the writing door instead of a Start button that would answer 503. Webhook tools correlate through `lib/pubPalToolTurnStore.ts` (durable when Supabase is configured). `lib/pubPalToolInvoke.server.ts` prefers the stored turn query over a short ElevenLabs webhook fragment (`resolvePubPalToolQuery`) and fills empty webhook args from the deterministic router (`enrichPubPalToolArgs`) before calling the same handlers as `/api/ask`. Voice binds the conversation when the signed URL is issued. `/api/pub-pal/tool-turn` only refreshes that owned row or appends the signed-in user's own line, so get-home fencing sees recent user wording. Webhook routes declare `maxDuration` 30; the agent script sets each tool's `response_timeout_secs` to 28 and typed chat waits up to 28 seconds for the turn (`CHAT_TIMEOUT_MS`). The live session cap is ONE number, `PAL_VOICE_MAX_SESSION_SECONDS` in `lib/palVoiceCap.mjs`, read by the provisioner, the browser timer and the billing clamp alike. `scripts/pubpal/create-elevenlabs-agent.mjs` (`npm run pubpal:agent`) is the idempotent provisioner and `docs/PUB_PAL_SETUP.md` the captain's runbook. The `lib/palRecall.ts` recall line is IN-THREAD ONLY. Confirmed Pal memories reach the agent read-only through `lib/palConfirmedMemories.server.ts`, and writing a memory stays confirm-gated: the Pal-only `recall_memories` and `propose_memory` webhooks, and the rolling session summary, are described in `docs/PUB_PAL_SETUP.md`.
