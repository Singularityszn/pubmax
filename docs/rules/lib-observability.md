<a id="model-call-tracing-is-one-inert-server-leaf"></a>

- **Model-call tracing is one inert server leaf.** `lib/observability/arize.ts` is the only tracing module, registered once from the root `instrumentation.ts`, and it stays a no-op unless BOTH `ARIZE_API_KEY` and `ARIZE_SPACE_KEY` are set, so keyless dev, tests and CI send nothing. Every direct model HTTP call in `lib/` goes through `traceArizeModelCall` / `traceArizeModelLoop`, whose spans carry the model, tokens, latency and a static `metadata.route` tag chosen at the call site, and whose prompt and completion values are capped at 2048 characters. The AI SDK `generateText` gateway call is traced by the AI SDK telemetry bridge instead: its spans carry `functionId` (`gen_ai.agent.name`), not `metadata.route`, and no length cap. Prompts and completions are masked for emails and handles, at write time in the helpers and for every span in the `MaskingSpanExporter`, and the moderation adapters record NO input at all because their requests carry signed image URLs. The keyed path also registers an `OpenAIInstrumentation` (`@arizeai/openinference-instrumentation-openai`), which patches the `openai` npm SDK on require; NOTHING in this app imports that SDK yet, so it emits no span today and the `openai` dependency exists only so the patch target resolves. Independently of the Arize keys, every model request made through those two helpers (each loop round is one) ends by sending PostHog one `$ai_generation` (`lib/posthog/posthogAiCapture.ts`: model, provider, latency, token counts, error flag and the same static route tag, never prompt or completion text) under a fixed server `distinct_id`; it sends nothing when no PostHog project token is set. Tracing never enters a client bundle: the root `instrumentation-client.ts` is PostHog only. Fence: `__tests__/arizeTracing.test.ts`, `__tests__/arizeTracingRegistration.test.ts`. Operator setup: `docs/observability/arize.md`.

<a id="an-alert-leaves-the-process-through-one-webhook-and-unset-is-silent"></a>

- **AN ALERT LEAVES THE PROCESS THROUGH ONE WEBHOOK, AND UNSET IS SILENT.** The audit of 6 October 2026 found `[ALERT]` lines (a stale feed, a moderation backlog, a spent paid budget) that went to runtime logs nobody read. `lib/alertSink.ts` posts one line to the https URL in `PUBMAX_ALERT_WEBHOOK_URL`. It is called from `lib/log.ts` (every error-level event, plus the warn events in `ALERT_WARN_EVENTS`, today the paid-spend ceiling event and `event: "rate_limit.fail_open"`, because the abuse floor is per instance while it fires), `lib/freshnessNotify.ts`, `lib/socialModerationNotify.ts` and the `enrich-city-pubs` cron. FIVE rules. (1) UNSET IS SILENT: no request and no log line. (2) THE URL IS A SECRET: it is in `lib/productionSecretEnvNames.ts`, only https is accepted, and it is never logged or echoed. (3) IT CANNOT BECOME THE INCIDENT: one send per source per 15 minutes per instance with a suppressed count on the next message, at most 30 an hour, a 3 second timeout, no throw, and no call to `log()` from inside the sink. (4) THE BODY CARRIES `content` for Discord and `text` for Slack. (5) NO USER DATA LEAVES (captain, 6 October 2026): the webhook is not a processor the privacy page names, so `log()` posts the event name, level and time alone, never its context fields or error text, the other callers post system text only (counts, feed ids, city names), the off-platform backup posts a fixed line, and the sink adds the deployment id. `.github/workflows/alert-on-failure.yml` watches every scheduled workflow through `workflow_run`, so the pull request workflows keep no secrets context, and posts the run link to the `PUBMAX_ALERT_WEBHOOK_URL` repository secret, passing quietly when it is absent. It watches the workflows a production `deployment_status` starts as well, because those run with nobody at the terminal too: ops review OPS-9 found Production smoke and API performance outside the list and the job's `if` admitting only `schedule`, so a failed smoke after a Git-integration deploy alerted nobody. The `if` admits `schedule` and `deployment_status` and nothing else; a hand-dispatched run has its dispatcher watching (`npm run release:prod` reads the smoke verdict itself), and a Preview status skips those workflows' jobs, which is not a failure. Pin: `__tests__/alertSink.test.ts`, which fails a scheduled or `deployment_status` workflow the watcher does not name.

<a id="map-time-to-pins-is-measured-in-the-field"></a>

- **MAP TIME-TO-PINS IS MEASURED IN THE FIELD.** The `pubmax:*` marks proved the first pin on one rig, but nothing reported them from real visitors, so a p99 had no source. `lib/mapLoadTiming.ts` sends one `map_load_timing` event per `PubMap` mount through the PostHog browser SDK. Its shape is closed in `lib/mapLoadTimingEvent.ts` and rebuilt again in `before_send`. FOUR rules. (1) ONE VISIT, ONE OUTCOME: `painted` at the first `pubmax:pins-visible`, `timeout` 30 s after the map's first render, or `abandoned` on `pagehide` (by beacon) or unmount. A visit that times out or leaves is the tail, so it is reported and never dropped: an exit before the SDK has loaded waits in one consent-scoped localStorage row and the next consented page sends it under its own timestamp. (2) THE CLOCK IS NAVIGATION START, and a milestone is the first mark at or after this visit's first render, so an in-app return never reuses an older visit's marks. (3) CONSENT AND DNT GATE IT through `analyticsCollectionAllowed`, and it adds no request before the pins. (4) NO FREE TEXT: every field is a closed enum, a boolean or a clamped integer. Query and field meanings: `docs/analytics/MAP_LOAD_TIMING.md`. Pin: `__tests__/mapLoadTiming.test.ts`.

<a id="an-unhandled-server-error-is-one-structured-line-and-it-names-the-template"></a>

- **AN UNHANDLED SERVER ERROR IS ONE STRUCTURED LINE, AND IT NAMES THE TEMPLATE.** The infra audit of 18 October 2026 found no `onRequestError` export: a route, render or action that threw reached only Next's own stderr dump, so it made no alert and was gone with Vercel's short log retention. The root `instrumentation.ts` now exports `onRequestError`, which hands every captured server error to `lib/requestErrorReport.ts`. That leaf writes ONE error-level `event: "request.unhandled"` line, so the alert webhook hears it through `log()`. THREE rules. (1) THE ROUTE IS THE FILE TEMPLATE (`/api/profiles/[handle]`), never the request path, so a handle, an id or a query string never reaches the line. (2) THE ERROR GIVES ITS TYPE AND REACT'S DIGEST, never its message, because a PostgREST message can echo row values. (3) `x-vercel-id` IS THE CORRELATION ID: the same field rides `event: "http.request"` in `lib/routeObservability.ts`, so a line joins the Vercel request log. On Node the hook also reports to PostHog error tracking with the template and no message text. The hook never throws. Pins: `__tests__/requestErrorReport.test.ts`, `__tests__/routeObservability.test.ts`.
