# API contract and rate limits

Moved from [`app/AGENTS.md`](../../app/AGENTS.md). Authoritative policy detail lives here; the area index stays short.

<a id="the-daily-price-cap-has-two-enforcers-and-it-is-a-route-s-rule-rather-than-the-t"></a>

- **The daily price cap has TWO enforcers, and it is a ROUTE's rule rather than the table's.** Pentest finding F-1: `hasPricedDropToday` followed by `create` is a check-then-insert with nothing underneath it, so a concurrent burst walked straight through the stated "one price per pub each day" rule (eight simultaneous priced POSTs, six rows, one authority key, so nothing corroborated and nothing moved). The pre-check STAYS and stays deliberately fail-open, because it gives the ordinary refusal without spending a failed insert; the hard guard behind it is `pint_drops_priced_day_unique_idx` (migration `0141` + rollback). THREE rules. (1) THE BUCKET IS A COLUMN, never an expression: `timezone(text, timestamptz)` is only STABLE so a London day cannot anchor an index, and a UTC day is the WRONG day in both directions under BST, so the writer stamps `price_day` with the same `londonDayKey()` the pre-check compares against and the two enforcers cannot read one day differently. The migration's backfill claims the EARLIEST row of each existing bucket, because the rows the finding is about are already in the table and a naive backfill would fail the index build. (2) THE CAP GOVERNS THE LANE THAT STATES IT: `create` takes `underDailyPriceCap` (`PintDropCreateOptions`) and only `POST /api/pint-drops` opts in, because `POST /api/price-submit` pairs a Pint Drop with every community price a drinker sends and takes several from one account at one pub in one day on purpose, with its own rate limiter as the brake. A guard over every row would refuse the second of those. Whether the pairing lane should share the cap is an open product question, not a bug. (3) ONE SENTENCE: `DAILY_PRICE_CAP_REFUSAL` is spent by the pre-check and by the `PintDropDailyCapError` the store throws, so a drinker cannot tell which enforcer turned them away, and that refusal logs as `pint_drops.daily_cap_conflict` rather than as an outage. Pins: `__tests__/pintDropDailyCapAtomicEffective.test.ts` (real PostgreSQL 16, eight writers released at one instant, before and after the migration), `__tests__/pintDropDailyDedupe.test.ts`, `__tests__/pintDrops.test.ts`.

<a id="an-api-error-is-one-envelope-and-every-mutating-route-is-rate-limited"></a>

- **An API error is one envelope, and every mutating route is rate limited.** Every 4xx and 5xx JSON body from `app/api` goes through `publicApiError` (`lib/apiError.ts`; `publicApiErrorFromStatus` when a shared gate decided the status), and extra reader-visible fields ride `compatibilityFields`, never a bespoke shape. A 2xx fail-soft payload may carry an `error` field beside real data; that is not an error response. Cron routes authenticate with `assertCronRequest` (`lib/cronAuth.ts`) instead of a limiter; every other mutating route consults `isLimited` (`lib/pintDrops.ts`, per-IP keys, neighbours' budgets) or a named delegation such as `socialCrewActor`. `__tests__/theLocalErrorContract.test.ts` sweeps every route plus one level of local helper imports and fails on a rogue emitter or an unlimited mutating route. A MUTATING ROUTE OUTSIDE `app/api` IS STILL A MUTATING ROUTE: `/ingest` (`app/ingest/[...path]/route.ts`, the owned PostHog proxy) lets any caller POST up to 1 MB into the billed EU project, so it spends a per-instance in-memory `ingestRateLimited` budget keyed on the hashed address (240 a minute, named in `__tests__/posthogProxyRoute.test.ts`) before it reads a body - not the durable `isLimited`, because the proxy must make no Supabase call at request time and the durable limiter's degraded mode tightens to 3 a minute during the very outage the telemetry reports. That budget lives in the leaf `lib/ingestRateLimit.ts`, and the route reaches its caller's address through the pure leaves `lib/clientIpTrust.ts` and `lib/rateLimitHash.ts` rather than `lib/supabase.ts`, so the Supabase client is not traced into the bundle of the route every browser event and asset fetch hits. The limiter imports nothing, compares before it records so a refused address cannot grow its own window, and drops a key once every hit in it has expired so a flood of distinct addresses leaves no permanent entry behind (`__tests__/ingestRateLimit.test.ts`) - and the same sweep reads it because it now walks the whole `app` tree rather than `app/api` alone, which is how the proxy shipped unauthenticated and unlimited in the first place. It is not an envelope route, because a browser SDK reads its status and never a JSON body, and it keeps its origin pin, its content-type allow-list and its 1 MB cap.

<a id="an-unknown-address-answers-the-envelope-and-a-delete-still-answers-after-the-acc"></a>

- **AN UNKNOWN ADDRESS ANSWERS THE ENVELOPE, AND A DELETE STILL ANSWERS AFTER THE ACCOUNT HAS GONE.** Two API contract slips verification scout verify-preview-4 measured on a production build (section 7.3 and observation 9), and each is a rule rather than a patch. (1) NEXT TREATS A FORM-ENCODED OR MULTIPART POST TO A PATH NO ROUTE HANDLER CLAIMS AS A SERVER ACTION INVOCATION: it looks the action id up in the body, finds none and throws, so a mistyped multipart `POST /api/avatar` answered a 500 HTML page (`Failed to find Server Action`) while the same address answered 404 to a GET. THE CONTENT TYPE DECIDED THE ANSWER, which is a promise no caller can read. `app/api/[[...unmatched]]/route.ts` is the API tree's own 404: an OPTIONAL catch-all, so bare `/api` is claimed too, sitting below every real route and answering one `publicApiError(..., 404)` for every method. Because a handler MATCHES, the Server Action lookup never runs. It is a REFUSAL and not a write surface, so it takes no authority boundary and spends no rate-limit budget (one on an unknown address would make a typo cost more than a real request), and both tree-wide fences record that as a PROOF rather than a listing: the route may import nothing but `@/lib/apiError` and each handler's whole reachable source must be the single refusal call. Scope is `/api` alone, because the flat envelope is a contract with a CALLER and a browser is owed `app/not-found.tsx`. (2) A DELETE IS IDEMPOTENT, SO ITS DOOR MUST ANSWER AFTER THE AUTH ROW IT NAMES HAS GONE: `DELETE /api/account` resolved its caller with `callerUserId`, which asks GoTrue for the ACCOUNT, so the first delete removed the row and every repeat with the same unexpired bearer read as `user_not_found` and answered 401, leaving the documented 410 `already-gone` unreachable for the life of the door. It asks `verifyCallerAuth(request, { localOnly: true })`, the local JWKS lane, so a deleted account is still NAMED by its own token; the seam in `__tests__/accountDeletionRoute.test.ts` records the options it was asked with, so a return to the account lane fails there. THAT OPTION IS THIS DOOR'S ALONE, AND THE DEFAULT IS REVOCATION (review finding F-3): #1501 made the local lane the DEFAULT to spare a messaging poll a round trip, and `getClaims` checks a signature and an `exp` and nothing else, so a token whose account had just deleted itself still passed the contribution gate on every price write, the Social 18+ gate, both plan-seat claims and the session refresh for the rest of its hour - while the messaging routes it was written for never took the saving, `callerUserId` needing account metadata and always having asked GoTrue. `verifyCallerAuth` asks GoTrue unless a caller passes `{ localOnly: true }`, and `__tests__/authServerVerification.test.ts` sweeps `app`, `lib` and `components` so exactly one file may. A verification we could not RUN is its own answer, a retryable 503 `AUTH_UNAVAILABLE`, because `callerUserId` collapsed absent, invalid and unavailable into one null and telling somebody who is signed in that they are not is the one thing this door may not say. Pins: `__tests__/apiUnmatchedRoute.test.ts`, `__tests__/accountDeletionRoute.test.ts`, `__tests__/writeSurfaceCertification.test.ts`, `__tests__/theLocalErrorContract.test.ts`; proof `docs/proof/api-envelope-contracts/`.

<a id="the-health-route-asks-the-database-and-an-uptime-monitor-reads-its-status-code"></a>

- **THE HEALTH ROUTE ASKS THE DATABASE, AND AN UPTIME MONITOR READS ITS STATUS CODE.** `/api/version` answers from memory, so it stayed green through any Supabase outage. `GET /api/health` (`app/api/health/route.ts`, probe in `lib/healthProbe.server.ts`) reads one row of `rate_limits` through the admin client every store uses: 200 `{ ok, deploymentId, database }` when the query answers, 503 `DATABASE_UNAVAILABLE` in the flat error envelope when it fails or passes 4 seconds. THREE rules. (1) A KEYLESS DEV PROCESS IS HEALTHY AND A KEYLESS PRODUCTION PROCESS IS DOWN, because `requiresSupabaseStore` refuses the in-memory fallback there. (2) THE ANSWER IS HELD FOR 15 SECONDS PER INSTANCE, so a monitor or a loop costs the database one read per window, and the route needs no rate limiter of its own. (3) IT NAMES THE DEPLOYMENT AND NOTHING ELSE: no host, no error text, no table. Runbook `docs/DEPLOYMENT.md` "Uptime monitor". Pin: `__tests__/healthRoute.test.ts`.
