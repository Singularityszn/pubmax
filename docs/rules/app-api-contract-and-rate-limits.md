# API contract and rate limits

<a id="the-daily-price-cap-has-two-enforcers-and-it-is-a-route-s-rule-rather-than-the-t"></a>

The daily price cap is selected by the caller and enforced inside `lib/pintDropsStore.ts`. `POST /api/pint-drops` passes `underDailyPriceCap: true`. A new priced observation is limited to one per venue, identity and London day. An exact keyed replay returns the saved drop before the cap refuses a new observation. The replay contract is below.

Both store backends resolve replay versus cap before creating a row. The Supabase pre-check remains fail-open on a read failure. It includes existing priced rows without `price_day`, including rows paired through `POST /api/price-submit`. That pairing route does not opt into the cap and retains its own rate limiter. Whether it should share the cap remains a product decision.

The durable concurrency guard is `pint_drops_priced_day_unique_idx` (migration `0141` and its rollback). The writer stamps `price_day` with `londonDayKey()`, using the same London day as the pre-check. A UTC day would disagree during BST. The bucket is a column because `timezone(text, timestamptz)` is only STABLE and cannot anchor the index. The migration backfills the earliest row in each existing bucket so older duplicates do not prevent index creation. Without `price_day`, the schema fallback retains only the pre-check's protection.

Every insert attempt, including schema fallbacks, resolves a unique violation against the saved row before applying the cap. A matching replay succeeds. A changed replay conflicts. Otherwise, a daily-cap violation throws `PintDropDailyCapError`. The route maps that error to `DAILY_PRICE_CAP_REFUSAL` with status `409`. Insert-time cap refusals log as `pint_drops.daily_cap_conflict`, rather than storage outages.

Regression coverage: `__tests__/pintDropDailyCapAtomicEffective.test.ts`, `__tests__/pintDropDailyDedupe.test.ts`, `__tests__/pintDrops.test.ts` and `__tests__/pintDropsStore.test.ts`.

## Keyed Pint Drop and Round creation

`POST /api/pint-drops` and `POST /api/rounds` accept `clientRequestId` in their request bodies. `lib/clientRequestKey.server.ts` accepts 16 to 128 ASCII letters, digits, dots, underscores, colons or hyphens. A valid key produces a signed, deterministic row ID scoped to the request kind and actor. Pint Drops use the verified account ID when available, otherwise the resolved handle. Round creation uses the resolved handle. Missing or invalid keys retain the existing unkeyed creation behaviour.

A new row returns `201`. An exact replay returns the saved result with `200`. Reusing the key with conflicting details returns `409 IDEMPOTENCY_CONFLICT`. A valid keyed request without trusted signing returns retryable `503 UNAVAILABLE` before creation. The [signing configuration](../../.env.example) owns secret requirements and fallback rules. Changing the signing secret changes derived row IDs, so retries cannot recognise rows created under the previous secret.

`sameCreatedDrop` in `lib/pintDropsStore.ts` owns Pint Drop replay matching for both backends, lookups and creation. It compares venue, account authority, price, drink, measure, measure label, note, era, visibility, vibe tags, leave-by time and last-train decision. Authenticated matching uses account authority, so a handle rename does not prevent replay. Without account authority, the normalised handle must match. Vibe-tag order and equivalent timestamp formats do not change the match.

Each photo slot, pint, venue and receipt, compares attachment presence against the stored photo key. Photo bytes are not compared. An added or removed slot conflicts. A receipt that failed to upload leaves no stored key, so resending that attachment conflicts. A successful Pint Drop replay does not repeat confirmation, notification or bill-check work.

Round creation matches the stored creator handle and title. Durable creation and replay complete creator membership and confirm it appears in the returned state before reporting success. A membership failure returns `503`, allowing the same keyed retry to finish creation.

The map Pint Drop composer and retained Spill retries send their attempt's key. Older retained Spill entries without a key remain unkeyed. `RoundStarter` retains its key after failure while the handle, title and ordered seed-stop IDs remain unchanged. It clears the attempt on success or an identity-owner change. Reloading the starter does not preserve the attempt.

Regression coverage: `__tests__/pintDrops.test.ts`, `__tests__/pintDropsStore.test.ts`, `__tests__/optimisticSpillPost.test.ts`, `__tests__/roundStarterRetry.test.tsx`, `__tests__/roundsRoute.test.ts` and `__tests__/roundsReceiptStore.test.ts`.

<a id="an-api-error-is-one-envelope-and-every-mutating-route-is-rate-limited"></a>

- **An API error is one envelope, and every mutating route is rate limited.** Every 4xx and 5xx JSON body from `app/api` goes through `publicApiError` (`lib/apiError.ts`; `publicApiErrorFromStatus` when a shared gate decided the status), and extra reader-visible fields ride `compatibilityFields`, never a bespoke shape. A 2xx fail-soft payload may carry an `error` field beside real data; that is not an error response. Cron routes authenticate with `assertCronRequest` (`lib/cronAuth.ts`) instead of a limiter; every other mutating route consults `isLimited` (`lib/pintDrops.ts`, per-IP keys, neighbours' budgets) or a named delegation such as `socialCrewActor`. `__tests__/theLocalErrorContract.test.ts` sweeps every route plus one level of local helper imports and fails on a rogue emitter or an unlimited mutating route. A MUTATING ROUTE OUTSIDE `app/api` IS STILL A MUTATING ROUTE: `/ingest` (`app/ingest/[...path]/route.ts`, the owned PostHog proxy) lets any caller POST up to 1 MB into the billed EU project, so it spends a per-instance in-memory `ingestRateLimited` budget keyed on the hashed address (240 a minute, named in `__tests__/posthogProxyRoute.test.ts`) before it reads a body - not the durable `isLimited`, because the proxy must make no Supabase call at request time and the durable limiter's degraded mode tightens to 3 a minute during the very outage the telemetry reports. That budget lives in the leaf `lib/ingestRateLimit.ts`, and the route reaches its caller's address through the pure leaves `lib/clientIpTrust.ts` and `lib/rateLimitHash.ts` rather than `lib/supabase.ts`, so the Supabase client is not traced into the bundle of the route every browser event and asset fetch hits. The limiter imports nothing, compares before it records so a refused address cannot grow its own window, and drops a key once every hit in it has expired so a flood of distinct addresses leaves no permanent entry behind (`__tests__/ingestRateLimit.test.ts`) - and the same sweep reads it because it now walks the whole `app` tree rather than `app/api` alone, which is how the proxy shipped unauthenticated and unlimited in the first place. It is not an envelope route, because a browser SDK reads its status and never a JSON body, and it keeps its origin pin, its content-type allow-list and its 1 MB cap.

<a id="an-unknown-address-answers-the-envelope-and-a-delete-still-answers-after-the-acc"></a>

- **AN UNKNOWN ADDRESS ANSWERS THE ENVELOPE, AND A DELETE STILL ANSWERS AFTER THE ACCOUNT HAS GONE.** Two API contract slips verification scout verify-preview-4 measured on a production build (section 7.3 and observation 9), and each is a rule rather than a patch. (1) NEXT TREATS A FORM-ENCODED OR MULTIPART POST TO A PATH NO ROUTE HANDLER CLAIMS AS A SERVER ACTION INVOCATION: it looks the action id up in the body, finds none and throws, so a mistyped multipart `POST /api/avatar` answered a 500 HTML page (`Failed to find Server Action`) while the same address answered 404 to a GET. THE CONTENT TYPE DECIDED THE ANSWER, which is a promise no caller can read. `app/api/[[...unmatched]]/route.ts` is the API tree's own 404: an OPTIONAL catch-all, so bare `/api` is claimed too, sitting below every real route and answering one `publicApiError(..., 404)` for every method. Because a handler MATCHES, the Server Action lookup never runs. It is a REFUSAL and not a write surface, so it takes no authority boundary and spends no rate-limit budget (one on an unknown address would make a typo cost more than a real request), and both tree-wide fences record that as a PROOF rather than a listing: the route may import nothing but `@/lib/apiError` and each handler's whole reachable source must be the single refusal call. Scope is `/api` alone, because the flat envelope is a contract with a CALLER and a browser is owed `app/not-found.tsx`. (2) The [account deletion rule](app-auth-and-account-routes.md#an-account-leaves-in-two-phases-the-storage-api-owns-the-bytes-the-trigger-owns-) owns repeat deletion, caller verification and signing compatibility. Pins: `__tests__/apiUnmatchedRoute.test.ts`, `__tests__/accountDeletionRoute.test.ts`, `__tests__/writeSurfaceCertification.test.ts`, `__tests__/theLocalErrorContract.test.ts`; proof docs/proof/api-envelope-contracts/ (git history).

<a id="the-health-route-asks-the-database-and-an-uptime-monitor-reads-its-status-code"></a>

- **THE HEALTH ROUTE ASKS THE DATABASE, AND AN UPTIME MONITOR READS ITS STATUS CODE.** `/api/version` answers from memory, so it stayed green through any Supabase outage. `GET /api/health` (`app/api/health/route.ts`, probe in `lib/healthProbe.server.ts`) reads one row of `rate_limits` through the admin client every store uses: 200 `{ ok, deploymentId, database }` when the query answers, 503 `DATABASE_UNAVAILABLE` in the flat error envelope when it fails or passes 4 seconds. THREE rules. (1) A KEYLESS DEV PROCESS IS HEALTHY AND A KEYLESS PRODUCTION PROCESS IS DOWN, because `requiresSupabaseStore` refuses the in-memory fallback there. (2) THE ANSWER IS HELD FOR 15 SECONDS PER INSTANCE, so a monitor or a loop costs the database one read per window, and the route needs no rate limiter of its own. (3) IT NAMES THE DEPLOYMENT AND NOTHING ELSE: no host, no error text, no table. Runbook `docs/DEPLOYMENT.md` "Uptime monitor". Pin: `__tests__/healthRoute.test.ts`.
