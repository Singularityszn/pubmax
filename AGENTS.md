# AGENTS.md

## Cursor Cloud specific instructions

PubMaxing is a single Next.js 16 (App Router, React 19, TypeScript) web app — a price-aware London pub-crawl planner with a MapLibre 3-D map. There is one service.

- **Factory docs:** See [`docs/factory/`](docs/factory/) for PUBMAXX vision and roadmap.

- **A moderator door refuses the DOCUMENT, and /login names nobody until the session answers.** Two laws from the same audit lane. (1) `GET /admin` is gated before the console mounts: `app/admin/page.tsx` hands `headers()` to `canOpenAdminDocument` (`lib/adminAuth.ts`) and calls `unauthorized()`, so an anonymous request gets a 401 whose body is the token form alone - client-side gating around a 200 shell was the defect. The gate reads the SAME credential as the API gate (`isModerator`), off a header list rather than a whole `Request`, because Next hands a page a sealed adapter. Both admin doors then spend ONE session module (`lib/adminSessionClient.ts`): a 200 from the POST is not a session, so `readAdminSessionState` confirms the cookie landed and answers three ways - `anonymous` after a POST means the browser REFUSED to keep it, which is a different sentence from `unknown`, a read we could not run. That cookie is `SameSite=Lax`, not Strict, precisely BECAUSE the gate moved onto the document: the top-level navigation to `/admin` now has to carry it, and Strict withholds it on a cross-site one. The 401 body is not a dead end (SiteNav plus `Back to the map`), and a console notice carries its own tone (`lib/adminNotice.ts`) rather than being classified by matching its own copy. (2) `/login` may NOT say "Welcome back" to somebody it has never met: `lib/loginPageFraming.ts` owns the head copy and holds the first-time line until the live session answers, and while it resolves the card's shape stands in with `aria-busy` on the SHAPE and the screen-reader line OUTSIDE it, filled after mount because a live region announces a change and `aria-busy` suppresses one. `/sign-in` is a 308 to `/login` in `proxy.ts` and `/signin` stays. Pins: `__tests__/adminDocumentGuard.test.ts`, `__tests__/adminSessionClient.test.ts`, `__tests__/adminSessionRoute.test.ts`, `__tests__/loginPageFraming.test.ts`, `__tests__/loginSkeletonAnnouncement.test.ts` (the one jsdom file, because effects are the whole point), `e2e/admin-document-guard.spec.ts`.
- **Dedicated `/login` (alias `/signin`) owns the email-link flow as a first-class page.** Phone nav Sign in navigates there; desktop may keep the header popover. The browser session lives in evictable localStorage, so a durable HttpOnly resume cookie (`lib/authSessionResume.ts`, route `/api/auth/session`, client seam `lib/authSessionResumeClient.ts`) mirrors the refresh token: AuthProvider persists it on every auth event, redeems it when the browser boots with no local session, and a dead token surfaces the welcome-back one-tap path on `/login` instead of a cold form. - **A password is CREATED behind a session and only ever SPENT without one.** Setting one is `supabase.auth.updateUser({ password })` from a signed-in browser (`components/auth/SetAccountPassword.tsx`, mounted in `PubmaxxAccountHub`), because GoTrue binds that call to the caller's own JWT; no route of ours is in the path, the password never reaches our tables or our logs, and a form that could set a password for a NAMED HANDLE with no session is account takeover however it is worded. `lib/passwordPolicy.ts` is the ONE module that says what a password must be (8 characters, a capital, a number, a special) and the WORDS for it, so the hint, the live ticks (`components/auth/PasswordPolicyHint.tsx`, shown BEFORE anybody types) and the refusal cannot drift. CREATION and SIGN-IN are two questions: the character rules govern what a person may choose, and `/api/auth/handle-password` applies the length floor alone, because refusing an older password at our own door locks an owner out rather than protecting them. That route resolves handle to account through `normalizeHandle`, so "Karan" is "karan", and answers ONE 401 shape for an unknown handle, a wrong password and a too-short one alike; the way out (`No password yet? …`) rides under EVERY failure, never conditionally, or the line itself would answer whether a handle exists. - **The signed-in account is the only identity authority on a device.** `lib/deviceAccountIdentity.ts` owns the closed set of device artifacts that speak for an account (`pubmax_handle` first, which roughly 28 readers treat as "you") plus the `pubmax_account_owner` stamp saying whose they are. `AuthProvider.updateSession` binds that stamp on EVERY auth event, before any child re-renders; a different account - or an UNSTAMPED device, which proves nothing - loses the whole set in one atomic pass and the canonical read re-establishes it. Sign-out drops the set and the stamp together. That order is the contract: a sign-out that cleared only the session left `@karan` behind for the next account to be called by. Identity is TRI-STATE, so `useAuth().identityResolved` separates "no handle" from "not asked yet" and a surface that NAMES or ROUTES the viewer renders neutral until the live session answers - never a device cache, and never a confident "nobody" from a read that failed. Both such readers share `components/auth/useViewerHandle.ts`, because the rule was got wrong twice independently (the You tab and the Today greeting). A device-only artifact stays device-scoped: a Night Profile MIRRORED off an account carries `source: "account"` and leaves with it, one typed here stays. Writes announce themselves (`DEVICE_IDENTITY_CHANGED_EVENT`) because a same-tab `localStorage` write raises no `storage` event, which is why a stale handle used to survive until a full page load. Separately, every browser write to an actor-gated route sends its bearer token so the SERVER derives the actor (`resolveMessageHandle` + `gateHandleAction`); a bare `fetch` made a signed-in drinker's own handle read as a hijack and 403. `__tests__/gatedActorAuth.test.ts` is the tree-wide fence. Pins: `__tests__/deviceAccountIdentity.test.ts`, `__tests__/gatedActorAuth.test.ts`, `__tests__/followRoute.test.ts`, `e2e/account-switch-identity.spec.ts`.
- **A device may hold several accounts, and exactly one of them owns it.** The browser Supabase client holds ONE session, so a second sign-in used to destroy the first: two accounts meant an email link every time. `lib/deviceAccountSessions.ts` is the lane - one `localStorage` key, one REFRESH token per account id, capped at `MAX_DEVICE_ACCOUNTS`, newest active first - and it is deliberately OUTSIDE `DEVICE_IDENTITY_LOCAL_KEYS`, because that set is dropped whole on every account change and dropping this one would delete the other accounts. It is safe outside only because every row names its own account id, nothing reads "who is signed in" from it, and a row is only ever activated by minting THAT row's own session. The swap is `lib/deviceAccountSwitch.ts` and it is the smallest possible thing: exchange the stored refresh token at GoTrue's own `/auth/v1/token`, then `supabase.auth.setSession`, so the ordinary auth event reaches `AuthProvider.updateSession` and the ONE atomic device-identity pass runs unchanged. Never refresh through the live client instead (`auth.refreshSession` tears the stored session down when a refresh fails and the access token has expired, so a dead token on the account you are switching TO would sign you out of the one you are switching FROM). The durable resume cookie is untouched by the switcher: it mirrors the ACTIVE account only, and it follows a switch the same way it follows every sign-in - SIGNED_IN re-persists, and `inheritedResumeEmail` already refuses to carry the previous account's address across because the account id differs. An outcome is THREE-WAY: a token GoTrue REFUSED is deleted on the spot and its row stays reading "Signed out" (a sign-in we cannot do silently is not an account that was never here), while a read we could not run keeps the token. Sign-out is SCOPED (`SignOutScope`): "this account" drops its row and hands the device to the next remembered account, "all accounts" empties the lane, and the scope is only offered when the device holds more than one - with one, the two are the same act. `clearPersistedSession` is AWAITED in sign-out, because a DELETE still in flight would land after the next account's persist. UI: `components/auth/AccountDeviceControls.tsx` is the ONE control (list, Add account, both ways out), shared by the nav card and by /login's signed-in card, because `.siteNavBar .authUser` is hidden at 640px and /login is therefore the account home on a phone. `/login?add=1` is the only thing that makes a live session see the form instead of the "you are signed in" card. A held profile card carries the HANDLE it is about, or a switch leaves the previous account's face above the new account's @handle. Pins: `__tests__/deviceAccountSessions.test.ts`, `__tests__/deviceAccountSwitch.test.ts` (including the fences that this module binds no identity and touches no cookie), `__tests__/accountSwitcherRender.test.ts`, `__tests__/loginAddAccount.test.ts`, `e2e/account-switch-identity.spec.ts`. That spec answers its own resume-cookie persist in every test that does not ASSERT the cookie: `/api/auth/session` is rate limited per IP (60 persists an hour) and every signed-in page load in every worker spends one, so the suite used to exhaust it and read a rate limit as a broken feature.
