# AGENTS.md

## Cursor Cloud specific instructions

PubMaxing is a single Next.js 16 (App Router, React 19, TypeScript) web app — a price-aware London pub-crawl planner with a MapLibre 3-D map. There is one service.

- **Factory docs:** See [`docs/factory/`](docs/factory/) for PUBMAXX vision and roadmap.

- **Dedicated `/login` (alias `/signin`) owns the email-link flow as a first-class page.** Phone nav Sign in navigates there; desktop may keep the header popover. The browser session lives in evictable localStorage, so a durable HttpOnly resume cookie (`lib/authSessionResume.ts`, route `/api/auth/session`, client seam `lib/authSessionResumeClient.ts`) mirrors the refresh token: AuthProvider persists it on every auth event, redeems it when the browser boots with no local session, and a dead token surfaces the welcome-back one-tap path on `/login` instead of a cold form. Sign-out is the only place that deletes the cookie. Under `next dev` only, a non-supabase.co `NEXT_PUBLIC_SUPABASE_URL` origin is admitted into CSP `connect-src` (proxy.ts) so a local GoTrue (`supabase start`, or a stub) can drive real browser sign-in; production never widens. `__tests__/authSessionRoute.test.ts` pins the restart-restore regression. Do not touch `AuthProvider.tsx` token-fragment paths without coordinating the auth-hardening lane.
- **A password is CREATED behind a session and only ever SPENT without one.** Setting one is `supabase.auth.updateUser({ password })` from a signed-in browser (`components/auth/SetAccountPassword.tsx`, mounted in `PubmaxxAccountHub`), because GoTrue binds that call to the caller's own JWT; no route of ours is in the path, the password never reaches our tables or our logs, and a form that could set a password for a NAMED HANDLE with no session is account takeover however it is worded. `lib/passwordPolicy.ts` is the ONE module that says what a password must be (8 characters, a capital, a number, a special) and the WORDS for it, so the hint, the live ticks (`components/auth/PasswordPolicyHint.tsx`, shown BEFORE anybody types) and the refusal cannot drift. CREATION and SIGN-IN are two questions: the character rules govern what a person may choose, and `/api/auth/handle-password` applies the length floor alone, because refusing an older password at our own door locks an owner out rather than protecting them. That route resolves handle to account through `normalizeHandle`, so "Karan" is "karan", and answers ONE 401 shape for an unknown handle, a wrong password and a too-short one alike; the way out (`No password yet? …`) rides under EVERY failure, never conditionally, or the line itself would answer whether a handle exists. Whether an account HAS a password is TRI-STATE: `auth.users.encrypted_password` is unreachable over PostgREST and GoTrue's user object carries no such field, so `public.account_has_password` (migration `0099` + rollback; captain applies; service-role EXECUTE only, or it is an oracle) answers one boolean through `/api/identity/handle/current`, and a read that could not answer names NEITHER state rather than telling an owner with a password to create one. Pins: `__tests__/passwordPolicy.test.ts`, `__tests__/passwordPolicyHint.test.ts`, `__tests__/setAccountPassword.test.ts`, `__tests__/handlePasswordSignIn.test.ts`, `__tests__/handlePasswordRoute.test.ts`, `__tests__/accountHasPasswordMigration.test.ts`, `e2e/account-password.spec.ts`.
- **The signed-in account is the only identity authority on a device.** `lib/deviceAccountIdentity.ts` owns the closed set of device artifacts that speak for an account (`pubmax_handle` first, which roughly 28 readers treat as "you") plus the `pubmax_account_owner` stamp saying whose they are. `AuthProvider.updateSession` binds that stamp on EVERY auth event, before any child re-renders; a different account - or an UNSTAMPED device, which proves nothing - loses the whole set in one atomic pass and the canonical read re-establishes it. Sign-out drops the set and the stamp together. That order is the contract: a sign-out that cleared only the session left `@karan` behind for the next account to be called by. Identity is TRI-STATE, so `useAuth().identityResolved` separates "no handle" from "not asked yet" and a surface that NAMES or ROUTES the viewer renders neutral until the live session answers - never a device cache, and never a confident "nobody" from a read that failed. Both such readers share `components/auth/useViewerHandle.ts`, because the rule was got wrong twice independently (the You tab and the Today greeting). A device-only artifact stays device-scoped: a Night Profile MIRRORED off an account carries `source: "account"` and leaves with it, one typed here stays. Writes announce themselves (`DEVICE_IDENTITY_CHANGED_EVENT`) because a same-tab `localStorage` write raises no `storage` event, which is why a stale handle used to survive until a full page load. Separately, every browser write to an actor-gated route sends its bearer token so the SERVER derives the actor (`resolveMessageHandle` + `gateHandleAction`); a bare `fetch` made a signed-in drinker's own handle read as a hijack and 403. `__tests__/gatedActorAuth.test.ts` is the tree-wide fence. Pins: `__tests__/deviceAccountIdentity.test.ts`, `__tests__/gatedActorAuth.test.ts`, `__tests__/followRoute.test.ts`, `e2e/account-switch-identity.spec.ts`.
- **A device may hold several accounts, and exactly one of them owns it.** The browser Supabase client holds ONE session, so a second sign-in used to destroy the first: two accounts meant an email link every time. `lib/deviceAccountSessions.ts` is the lane - one `localStorage` key, one REFRESH token per account id, capped at `MAX_DEVICE_ACCOUNTS`, newest active first - and it is deliberately OUTSIDE `DEVICE_IDENTITY_LOCAL_KEYS`, because that set is dropped whole on every account change and dropping this one would delete the other accounts. It is safe outside only because every row names its own account id, nothing reads "who is signed in" from it, and a row is only ever activated by minting THAT row's own session. The swap is `lib/deviceAccountSwitch.ts` and it is the smallest possible thing: exchange the stored refresh token at GoTrue's own `/auth/v1/token`, then `supabase.auth.setSession`, so the ordinary auth event reaches `AuthProvider.updateSession` and the ONE atomic device-identity pass runs unchanged. Never refresh through the live client instead (`auth.refreshSession` tears the stored session down when a refresh fails and the access token has expired, so a dead token on the account you are switching TO would sign you out of the one you are switching FROM). The durable resume cookie is untouched by the switcher: it mirrors the ACTIVE account only, and it follows a switch the same way it follows every sign-in - SIGNED_IN re-persists, and `inheritedResumeEmail` already refuses to carry the previous account's address across because the account id differs. An outcome is THREE-WAY: a token GoTrue REFUSED is deleted on the spot and its row stays reading "Signed out" (a sign-in we cannot do silently is not an account that was never here), while a read we could not run keeps the token. Sign-out is SCOPED (`SignOutScope`): "this account" drops its row and hands the device to the next remembered account, "all accounts" empties the lane, and the scope is only offered when the device holds more than one - with one, the two are the same act. `clearPersistedSession` is AWAITED in sign-out, because a DELETE still in flight would land after the next account's persist. UI: `components/auth/AccountDeviceControls.tsx` is the ONE control (list, Add account, both ways out), shared by the nav card and by /login's signed-in card, because `.siteNavBar .authUser` is hidden at 640px and /login is therefore the account home on a phone. `/login?add=1` is the only thing that makes a live session see the form instead of the "you are signed in" card. A held profile card carries the HANDLE it is about, or a switch leaves the previous account's face above the new account's @handle. Pins: `__tests__/deviceAccountSessions.test.ts`, `__tests__/deviceAccountSwitch.test.ts` (including the fences that this module binds no identity and touches no cookie), `__tests__/accountSwitcherRender.test.ts`, `__tests__/loginAddAccount.test.ts`, `e2e/account-switch-identity.spec.ts`. That spec answers its own resume-cookie persist in every test that does not ASSERT the cookie: `/api/auth/session` is rate limited per IP (60 persists an hour) and every signed-in page load in every worker spends one, so the suite used to exhaust it and read a rate limit as a broken feature.

- **Storage takes a Blob, and a write proves itself.** `@supabase/storage-js` builds a multipart body for a Blob and ONLY for a Blob; every other body is handed to the runtime's `fetch` raw, and on Vercel that string-decoded our JPEG into UTF-8 (leading `ef bf bd`) while still answering 200. So `uploadUploadedImageObject` in `lib/uploadedImage.server.ts` is the ONE writer behind the avatar, the cover, a pub wall photo and a feed photo - never call `.storage.from(...).upload(...)` with a Buffer. Because a mangled write is invisible until a serve 404 days later, promotion reads its own serving key back through the shared reader (`proveUploadedImageWrite`) and refuses the upload with `PROCESSING_FAILED`, deleting the object. That proof is TRI-STATE like the scan is advisory: only bytes we DID read and that are not ours are `corrupt`; a read we could not run is `unproven` and costs an owner nothing. Pins: `__tests__/profileImageServeJourney.test.ts`, whose fake bucket mangles a non-Blob body exactly as the runtime did, so reverting the wrap fails it.

- **The safety scan on an owned image is ADVISORY, and the moderator lane is the net.** `lib/uploadedImageScan.server.ts` is the ONE policy every owned-image surface shares - the avatar, the cover and a pub wall photo. The sharpest trap is vocabulary: `inferNightContext` turns "walk" or "tube" into a `transportConstraint`, and `selectGroundedPlanRoute` (`lib/planRouteOptimizer.ts`) refuses outright the moment a context carries one, so "river walk ..." 422s while "riverside ..." builds. A chip LABEL may still say walk, because a label never reaches the optimizer. `__tests__/cultureCrawlGenerateRoute.test.ts` sends the real body; `__tests__/cultureCrawl.test.ts` pins the empty-transportConstraints rule.
- **A Culture Crawl waypoint is a thing to see, never a Stop.** `lib/cultureCrawl.ts` owns the closed chip ids, the closed free-thing lanes and their copy; `lib/cultureCrawl.server.ts` reads the ambient POI layer (static import, so Next traces it) and returns the whole `cultureOpener` response fragment, absent entirely for an ordinary outing. The waypoint carries only what the POI record holds - name, its own category, the straight-line distance to the first pub - so it never enters the Stops, the grounding proof, the price lanes or the three-Stop count, and `components/plan/PlanCultureOpener.tsx` renders it unnumbered with no swap and no remove. The layer has no hours and no admission field, so the copy names what is missing rather than implying an open door; a lane with nothing in range says it found nothing instead of substituting a nearest anything. A name filter is a read of the record, not a claim: the gallery lane only lands on a POI whose OWN name says gallery or museum. Pins: `__tests__/cultureCrawl*.test.ts`.
- **Manual planner testing is stateful and constraint-sensitive.** `/api/plans/generate` returns `422` with "No three-stop route ... meets every must-have need with the information available" (not a crash) when the intake carries must-have needs (e.g. access or a hard budget ceiling) that the area's data can't satisfy - it is honest scarcity, not a broken environment. The intake also persists across sessions in `localStorage` (`pubmax:plan-intake:v1`) and a route draft in `pubmaxx:plan-route-draft:v1`, so a prior run's constraints silently leak into the next and make repeat generations flaky. Manual UI planner tests should run in a fresh/incognito profile; a low-constraint free-text request via "Describe instead" (e.g. `Quiet in Clapham for 4, not pricey`) reliably yields a priced three-stop plan keyless. The e2e specs clear this state with `addInitScript` instead.
- **A browser test never guesses where a pin is.** The pins paint through the MapLibre canvas, so a spec cannot find one in the DOM, and a grid of taps hunting for one is a race the test loses under parallel workers. `components/map/canvas/paintedPinProbe.ts` publishes `paintedMapTapPoints` on `window`: the viewport point of every pin and cluster the map is drawing right now, each checked to have survived symbol collision, to re-query to the same mark, and to carry no app chrome on top of it. It is unconditional, like the `pubmax:pin-reveal` event beside it, because the browser suite runs a production build. The map opens with the pubs gathered, so a spec that wants a pin opens a cluster first. `__tests__/paintedPinProbe.test.ts` pins the gates and `e2e/mobile-map-chrome-fit.spec.ts` walks them.
- **Honest path anti-goals (London night OS first).** Do not ship a Twitter-for-pubs growth engine; do not market multi-city splash without London density; do not add Stripe Checkout / payments theatre before venue trust density; do not build AI that fabricates prices, hours, or pub lore (heritage and plan generate fail closed to grounded / scarcity answers); do not claim “we beat Stripe” in marketing or investor copy. THREE STANDING COMMITMENTS ride with these. (1) A REFERRAL IS A MARK OF HONOUR, NEVER A FEATURE: a milestone confers recognition and nothing in the product may branch on it, the founding-member law applied to a second status (`lib/referrals.ts`, fence `__tests__/referralMarkLaw.test.ts`). The old capability-grant model is deleted, not switched off, in TypeScript and in SQL. (2) THE ANNUAL YEAR IN PINTS WRAP IS FREE FOREVER: it is a person's own year read back to them, so it may never sit behind a price, a tier, a referral count or an account upgrade. (3) FIRST REVENUE COMES FROM VENUES, NEVER DRINKERS: a drinker pays for nothing, and no drinker-facing paywall, membership or metered read may be built before the venue rail earns. Platform prep is ADR-only: `docs/adr/0011-venue-operator-rail.md`, `docs/adr/0012-entitlement-ledger-contract.md`. Ops checklist: `docs/growth/HORIZON0_OPS_CHECKLIST.md`. Extend `docs/plans/PLG_STRATEGY.md` waves rather than inventing a parallel roadmap.

- **A pub photo wall is a photo wall, and a crosspost is a promise.** Every venue carries a community wall (`lib/venuePhotos.ts` owns the policy: 100 photos per ACCOUNT per venue, an optional tag from the one drink taxonomy, an optional 140-character caption, portrait crop). It is never a price lane: nothing on a wall reaches `mergeCommunityPriceSignals`, pin colour, cheapest buckets or the Pint Index. The bytes take the SAME journey the owned profile images take, now extracted to `lib/uploadedImage.server.ts` so the asserted EXIF strip cannot drift between them: staging, signed URL, the scan adapter, and promotion to `venue-photos/{venueId}/{photoId}.jpg` unless the scan REFUSED. The cap counts LIVE rows, so a moderator hide gives the slot back (a removal is not a spent slot); reporting queues and never hides; hiding never deletes and keeps its own lane. The author is stored as the stable `profile:{uuid}` actor and printed through the ONE public projection (`publicProfileFromRecord`), so a handle rename never strands a photo and the founding mark cannot fall off a second field list. "Also share to your feed" answers on a three-way scale (`VenuePhotoCrosspostState`), never a boolean: the feed write goes through the existing Social post machinery behind `requireVerifiedSocialActor`, so the wall buys no lane around Social's own gate, and a feed failure is reported rather than failing the wall the photo already reached. Migration 0098 repeats the object-key shape, the taxonomy and the actor binding, and extends the tombstone trigger to take an author's wall photos and their bytes with them. `__tests__/venuePhotos*.test.ts` and `e2e/venue-photo-wall.spec.ts` pin these apart.

- **A message bubble's WIDTH is the row's business, and a message photo is the one owned image that is not public.** THE BUBBLE FIRST, because it is a rule and not a styling choice: `.messageLine` (`app/messages/messages.css`) carries `max-width: 75%` plus `width: fit-content`, and `.messageBubble` may name no percentage but 100%. The limit used to sit on the bubble, whose containing block was a shrink-to-fit wrapper the bubble had just sized, so every bubble was clamped to 78% of its OWN natural width and `overflow-wrap: anywhere` broke mid-word to obey - the first live DM on production drew "Yo!!" as one character per line in a 42px box. `fit-content` is the other half: it floors on the AVAILABLE width where a flex item's automatic minimum floors on min-content, which under `anywhere` is one character. THE ATTACHMENT SECOND: `lib/messageAttachments.ts` is the pure closed set (`photo` | `venue`), the storage keys, and every word these surfaces print. A photo takes the ENTIRE owned-image journey (`lib/messagePhotoMedia.server.ts` over `lib/uploadedImage.server.ts`: staging, EXIF strip, advisory scan, Blob write, write-side proof) onto `messages/{conversationId}/{messageId}.jpg`, and its bytes are NOT public - `lib/messagePhotoServe.server.ts` re-applies `requireLinkedActor` plus the participant pair, answers `private, no-store`, and the thread reads it through `authedFetch` into an object URL (`components/messages/MessagePhoto.tsx`) because an `<img src>` cannot carry a bearer. REPORTING is the takedown: a flagged message loses its attachment in the ONE projection both store backends read (`rowToAttachment` in `lib/messagesStore.ts`), so the thread, the serve route and the corroborating read stop together. A SHARED PUB stores a venue id and nothing else - no coordinate of any kind, so the viewer-coordinate egress law is untouched - and `lib/messageVenueCards.server.ts` resolves name, area and (pub kinds only, curated sourced lane only, drink NAMED) a figure on every read, because a price frozen into a message is an undated claim nobody can correct. The curated matcher behind "which pub did you mean" is shared with Wanted (`lib/curatedVenueSearch.server.ts`, route `/api/venue-search`).
