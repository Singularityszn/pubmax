- **AN ACCOUNT LEAVES IN TWO PHASES: THE STORAGE API OWNS THE BYTES, THE TRIGGER OWNS THE ROWS.** Contribution battle test D01 (5 Sep 2026): `DELETE /api/account` answered 503 for EVERY account, because the `0078` tombstone trigger deleted from the storage objects table directly and Supabase refuses that at the STATEMENT level (`protect_objects_delete`, SQLSTATE 42501) whether or not a row matches; behind it the Social account's binding to the auth user (`0071`) was `on delete restrict`. Migration `0145` + rollback takes every storage delete out of the trigger, moves the binding to `on delete set null`, and SUSPENDS and unbinds the Social account row rather than deleting it, because the Crew tables reference it with restrict. `deleteOwnAccount` (`lib/accountDeletion.server.ts`) is THREE PHASES and the order is the rule: it COLLECTS every object key while the wall photo rows and message columns that name them still exist, DELETES the auth row, and only then REMOVES the bytes through the Storage API. `lib/accountOwnedObjects.ts` is the ONE table of what an account owns (the avatar and cover folders, the owner's Moment folder, wall and message photo keys with their staging twins), and `lib/nightMomentMedia.ts` reads its prefix from there, because D09 was the upload path and the tombstone naming two different sets. A FAILURE BEFORE THE AUTH ROW GOES REMOVES NOTHING (review finding F-5, which REVERSES the order `0145`'s own header describes): the first cut removed the bytes first, so an auth failure answered "Your account could not be deleted. Try again." over a LIVE account whose every photo was already gone and whose wall photos stayed on public walls as broken images. The keys must be READ before the trigger clears the rows that name them, and reading is its own phase; that was never an argument for removing first. The cost of the new order is ORPHANED BYTES when a removal fails after the account is gone: they are logged as `account.delete_objects_orphaned`, no surface can serve one (the rows that named them are gone), the outcome stays the auth row's rather than a 503 over a deleted account, and a retry still removes everything the folder walk lists by PREFIX. ## API contract and rate limits

- **The daily price cap has TWO enforcers, and it is a ROUTE's rule rather than the table's.** Pentest finding F-1: `hasPricedDropToday` followed by `create` is a check-then-insert with nothing underneath it, so a concurrent burst walked straight through the stated "one price per pub each day" rule (eight simultaneous priced POSTs, six rows, one authority key, so nothing corroborated and nothing moved). The pre-check STAYS and stays deliberately fail-open, because it gives the ordinary refusal without spending a failed insert; the hard guard behind it is `pint_drops_priced_day_unique_idx` (migration `0141` + rollback). THREE rules. (1) THE BUCKET IS A COLUMN, never an expression: `timezone(text, timestamptz)` is only STABLE so a London day cannot anchor an index, and a UTC day is the WRONG day in both directions under BST, so the writer stamps `price_day` with the same `londonDayKey()` the pre-check compares against and the two enforcers cannot read one day differently. The migration's backfill claims the EARLIEST row of each existing bucket, because the rows the finding is about are already in the table and a naive backfill would fail the index build. (2) THE CAP GOVERNS THE LANE THAT STATES IT: `create` takes `underDailyPriceCap` (`PintDropCreateOptions`) and only `POST /api/pint-drops` opts in, because `POST /api/price-submit` pairs a Pint Drop with every community price a drinker sends and takes several from one account at one pub in one day on purpose, with its own rate limiter as the brake. A guard over every row would refuse the second of those. Whether the pairing lane should share the cap is an open product question, not a bug. (3) ONE SENTENCE: `DAILY_PRICE_CAP_REFUSAL` is spent by the pre-check and by the `PintDropDailyCapError` the store throws, so a drinker cannot tell which enforcer turned them away, and that refusal logs as `pint_drops.daily_cap_conflict` rather than as an outage. Pins: `__tests__/pintDropDailyCapAtomicEffective.test.ts` (real PostgreSQL 16, eight writers released at one instant, before and after the migration), `__tests__/pintDropDailyDedupe.test.ts`, `__tests__/pintDrops.test.ts`. Detail: [`../docs/rules/app-api-contract-and-rate-limits.md#the-daily-price-cap-has-two-enforcers-and-it-is-a-route-s-rule-rather-than-the-t`](../docs/rules/app-api-contract-and-rate-limits.md#the-daily-price-cap-has-two-enforcers-and-it-is-a-route-s-rule-rather-than-the-t).
- **An API error is one envelope, and every mutating route is rate limited.** Every 4xx and 5xx JSON body from `app/api` goes through `publicApiError` (`lib/apiError.ts`; `publicApiErrorFromStatus` when a shared gate decided the status), and extra reader-visible fields ride `compatibilityFields`, never a bespoke shape. A 2xx fail-soft payload may carry an `error` field beside real data; that is not an error response. Cron routes authenticate with `assertCronRequest` (`lib/cronAuth.ts`) instead of a limiter; every other mutating route consults `isLimited` (`lib/pintDrops.ts`, per-IP keys, neighbours' budgets) or a named delegation such as `socialCrewActor`. `__tests__/theLocalErrorContract.test.ts` sweeps every route plus one level of local helper imports and fails on a rogue emitter or an unlimited mutating route. A MUTATING ROUTE OUTSIDE `app/api` IS STILL A MUTATING ROUTE: `/ingest` (`app/ingest/[...path]/route.ts`, the owned PostHog proxy) lets any caller POST up to 1 MB into the billed EU project, so it spends a per-instance in-memory `ingestRateLimited` budget keyed on the hashed address (240 a minute, named in `__tests__/posthogProxyRoute.test.ts`) before it reads a body - not the durable `isLimited`, because the proxy must make no Supabase call at request time and the durable limiter's degraded mode tightens to 3 a minute during the very outage the telemetry reports. That budget lives in the leaf `lib/ingestRateLimit.ts`, and the route reaches its caller's address through the pure leaves `lib/clientIpTrust.ts` and `lib/rateLimitHash.ts` rather than `lib/supabase.ts`, so the Supabase client is not traced into the bundle of the route every browser event and asset fetch hits. The limiter imports nothing, compares before it records so a refused address cannot grow its own window, and drops a key once every hit in it has expired so a flood of distinct addresses leaves no permanent entry behind (`__tests__/ingestRateLimit.test.ts`) - and the same sweep reads it because it now walks the whole `app` tree rather than `app/api` alone, which is how the proxy shipped unauthenticated and unlimited in the first place. It is not an envelope route, because a browser SDK reads its status and never a JSON body, and it keeps its origin pin, its content-type allow-list and its 1 MB cap. Detail: [`../docs/rules/app-api-contract-and-rate-limits.md#an-api-error-is-one-envelope-and-every-mutating-route-is-rate-limited`](../docs/rules/app-api-contract-and-rate-limits.md#an-api-error-is-one-envelope-and-every-mutating-route-is-rate-limited).
- **Exactly five documents are exempt from the nonce, and the list is the fence.** Captain decision 2026-08-09, widened 2026-09-05 ("Widen"): `CDN_CACHED_DOCUMENT_PATHS` in `proxy.ts` names `/`, `/map`, `/tonight`, `/today` and `/near`, which take `script-src 'unsafe-inline'` in exchange for being prerendered and held by the CDN; the inline slot is the ONLY thing that differs, and every other route keeps a fresh nonce. A route that resolves a session in its document (`/u/you`, `/messages`, `/admin`) may never join the list. THREE rules ride with it. (1) A prerendered document may read NOTHING per request (`force-static` makes that a build error, and it is also what stops the root layout's `headers()` nonce read pulling the route back to dynamic), and it may carry NOTHING personal, because one copy is handed to every stranger. (2) THE LIST AND THE PAGE FILES ARE ONE LIST READ TWO WAYS: a listed path whose page is not `force-static` renders per request under 'unsafe-inline' and buys nothing, and a `force-static` page outside the list is prerendered with no nonce in its scripts and then answered with a policy that demands one, so `__tests__/cdnCachedDocuments.test.ts` holds both directions. (3) THE ISR WINDOW IS SIZED TO THE CLOCK THE PAGE READS: `/tonight` and `/today` compose off the London hour (the greeting slot, the quiet-pint window) and revalidate every 300 s, while `/`, `/map` and `/near` read only bundled data and take 3600 s; do not lengthen the short ones, because a "Good morning" at ten past noon is the cost. So a `/map` request whose document really differs is rewritten by the proxy to `app/map/arrival` and rendered per request with the nonce intact; `lib/mapDocumentTwin.ts` owns that key list, and adding a key takes those requests off the CDN while dropping one silently serves a share link the wrong card. - **A ROUTE THAT SHIPS A DOCUMENT NOBODY KEEPS, AND THE HEADER THAT SAYS SO.** `/onboarding` is the native shell's one-time first-run surface and the web has no first-run surface at all: `FirstRunOnboardingGate` consumes a native-only, session-scoped handoff, so a web visit has always failed closed to "/". It did that in the BROWSER, after rendering and discarding a whole document, and on Slow 4G that was the worst LCP on the site at 4676 ms, the paint being the homepage hero arriving after the bounce (Astra's live walk, 7 Sep 2026, finding B6). `proxy.ts` turns away, with a 307 and no document, a document request that no page on this origin started. FOUR rules. (1) THE SIGNAL IS `Accept`, NOT NEXT'S OWN: this version of Next STRIPS both the `RSC` header and the `_rsc` query before middleware, measured on a production build, so neither can be read there. A browser document navigation sends `text/html,...` and every RSC navigation and prefetch sends `*/*`, which is why the shell's `router.replace` arrival from "/" (`components/native/AppEntryRoute.tsx`) is untouched. Accept also FAILS SAFE: an RSC fetch cannot start claiming to want HTML, so a future Next release cannot turn this rule on the shell's own arrival, where a header-name change could. (2) THE SHELL'S OWN DOCUMENT NAVIGATION PASSES: a fresh install leaves "/" with a location replace in `public/theme-init.js`, which is a document request. Turning it away sent every fresh install to the landing page with the first-run mark stamped, so onboarding never ran (7 to 14 Sep 2026). `Sec-Fetch-Site: same-origin` passes, and when that header is ABSENT (WKWebView before iOS 16.4, and the app targets 15.0) a Referer on the same host and scheme passes. When `Sec-Fetch-Site` is sent it decides alone, so a typed visit (`none`), a `same-site` and a `cross-site` navigation keep the 307 whatever Referer says. (3) 307 AND NEVER 308: a browser caches a permanent redirect, the shell is a remote-URL wrap of this same origin, and one cached 308 would take the first run away from every later install on that device. (4) THE PATH IS A LEAF: `ONBOARDING_PATH` lives in `lib/firstRunRoute.ts`, which imports nothing, because a middleware bundle may not drag the city tables, the Capacitor probe and the storage seams in behind one string; `lib/entryDecision.ts` re-exports it.
